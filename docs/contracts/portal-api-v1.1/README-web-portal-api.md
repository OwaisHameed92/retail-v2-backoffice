# SSPOS web portal API — the till's JSON contract (v1)

**For:** the developer building the SSPOS web portal, its API and its database.
**From:** the SSPOS till team. **Status:** contract v1, 2026-09-23 (task P4-65).

You build the portal and its API. We give you the exact JSON the till sends and expects back; when
your API is live we point a real HTTP transport at it (a separate task on our side). Nothing in the
till talks to you until the shop owner has set three things (section 1).

Everything in `docs/web-portal-api/samples/` and `docs/web-portal-api/schemas/` is **generated by
serialising the till's real C# types** with the till's own serializer settings
(`src/SSPOS.Application/Sync/SyncJson.cs`). A test
(`tests/SSPOS.Infrastructure.Tests/Sync/PortalContract/PortalContractTests.cs`) fails the build if a
file stops matching the code, so the samples are the truth; where this text and a sample disagree,
the sample wins. Parts marked **PROPOSAL** have no till type yet; they are our suggested shape and
we will build the till side to whatever we agree.

## 1. The three settings — nothing leaves the shop until all three are set

Settings → **Hub sync** (group 20), on each shop's main till:

| Setting | Key | Default | Meaning |
|---|---|---|---|
| Hub address | `sync.hub_url` | blank | Your API's base URL, e.g. `https://portal.example.co.uk`. HTTPS only. |
| Portal API key | `sync.hub_api_key` | blank | The key your portal issues for **this branch**. Masked on screen, never logged, never printed, never in a support bundle. |
| Cloud sync | `sync.hub_enabled` | **off** | The master switch. While off, the till opens no connection at all. |
| Sync every | `sync.interval_seconds` | 30 | Seconds between runs (10–3600). |
| Rows per batch | `sync.batch_size` | 5000 | Rows per push (100–5000; 5,000 is a hard ceiling). |

Owner's flow once your API is live: type the URL → paste the API key → switch Cloud sync on.

## 2. Company → Branch → Till (how the till is structured — build the portal the same way)

1. **Hierarchy.** Company → Branch (a shop) → Register (a till). Every row carries `companyId`; every
   branch-scoped row also carries `branchId`; every till-scoped row also carries `registerId`
   (`src/SSPOS.Domain/Common/Entity.cs`, `BranchEntity.cs`, `RegisterEntity.cs`). Every row has an
   `id` that is a **ULID made on the till** (`Entity.Id = Shared.Ulid.NewId()`), globally unique.
   **The portal must never re-key a row**; store the till's id as your primary key.
2. **Who talks to the portal: one sender per branch.** Inside a branch, the main till owns the branch
   database and hosts the embedded store server (`src/SSPOS.Server`); the other tills sell against
   that database over the shop LAN and keep only a cache and an emergency queue
   (`src/SSPOS.Client`, `src/SSPOS.Domain/Common/TillRole.cs`: `SingleTill`, `MainTill`,
   `SecondaryTill`). So **only the main till (or the only till) of each branch pushes and pulls**; a
   second till's sales reach you inside its branch's batches, carrying that till's `registerId`.
   The till enforces this (`src/SSPOS.Application/Sync/SyncSenderGate.cs`: a `SecondaryTill` is
   refused with `sync.wrong_till`). One branch = one connection = one cursor.
3. **Identification.** Every request carries the headers in section 3: the API key, company id,
   branch id, the sending register id, the contract version and the store protocol version
   (`src/SSPOS.Server/Contracts/StoreProtocol.cs`, `Version = 1`). The API key is **per branch**
   (`sync.hub_api_key` is a branch-scoped setting); issue one key per branch and reject a request
   whose `X-SSPOS-Branch-Id` is not the key's branch.
4. **Company-wide vs per branch.**
   - Company-wide (no `branchId` on the row): the master data in section 10 — products, barcodes,
     aliases, departments, categories, units, VAT rates, promotions, customers, users, roles,
     suppliers, payment types, reasons, accounts, price history.
   - Per branch (`BranchEntity`): `BranchProduct` (the branch's stock on hand and its optional
     `priceOverride` — `src/SSPOS.Domain/Catalogue/BranchProduct.cs`), `ZReport`, `CustomerOrder`,
     `Register`, `SyncConflict` and other branch rows.
   - Per till (`RegisterEntity`): `Sale`, `Shift`, `StockMovement`. Sales are numbered **per till**
     (`Register.NextSaleNo` / `NextRefundNo`, `src/SSPOS.Domain/Common/Register.cs`); receipt numbers
     look like `LDS-01-000482` = branch code, till code, sale number (`Register.ReceiptPrefix`).
     Two tills may both have a sale number 17; `(registerId, number)` and `id` are unique, `number`
     alone is not.
   - Down to **all branches**: rows with `branchId: ""` (company-wide master data). Down to **one
     branch**: rows with that branch's id (e.g. a web order for that shop).
5. **Cursors are per branch.** The push cursor (`seq`) is the branch database's own ChangeLog
   sequence; Leeds and Bradford both have a `seq` 5120 and they are different rows. Key everything
   by `(branchId, seq)`. The pull cursor (`since`) is per branch too
   (`src/SSPOS.Domain/Sync/SyncState.cs`, one row per branch). **A pull must never return another
   branch's till-owned rows**, only company-wide rows and rows addressed to the caller's branch.
6. **Samples.** `samples/push-request.json` (Leeds, sent by Leeds till 1),
   `push-request.second-till.json` (a sale rung on Leeds till 2 — still sent by Leeds till 1, same
   `branchId`, `seq` carries on, `registerId` is till 2) and `push-request.second-branch.json`
   (Bradford: other `branchId`, its own `seq` numbers).

## 3. Transport

| | |
|---|---|
| Protocol | HTTPS only (TLS 1.2+). The till refuses `http://`. |
| Auth | `Authorization: Bearer <sync.hub_api_key>` on every request. |
| Identity headers | `X-SSPOS-Company-Id`, `X-SSPOS-Branch-Id`, `X-SSPOS-Register-Id` (the sending till), `X-SSPOS-Contract: 1`, `X-SSPOS-Store-Protocol: 1`, `X-SSPOS-App-Version: 3.x.y` |
| Content type | `application/json; charset=utf-8` both ways |
| Compression | Push body is **gzip** (`Content-Encoding: gzip`) — `SyncBatch.Pack` gzips it. Replies may be gzip if the till sends `Accept-Encoding: gzip`. |
| Push size | ≤ 5,000 rows per request (`SyncBatcher.MaxRowsPerBatch`), at most 5 batches per run. Allow request bodies up to 50 MB uncompressed. |
| Timeouts | Till waits 30 s for a reply, then treats it as a network failure and retries later. |
| Frequency | Every `sync.interval_seconds` (30 s) on the branch's main till (`src/SSPOS.Server/Hosting/SyncTimerHost.cs`; a tick does nothing while Cloud sync is off), at Close Shop, and on "Sync now" (Sync status screen). Order in a run: push, then pull (`src/SSPOS.Application/Sync/RunSync/RunSyncHandler.cs`). |

## 4. Endpoints

| Method + path | Purpose | Body | Reply |
|---|---|---|---|
| `GET /api/v1/sync/hello` | Check address + key. **PROPOSAL** | — | `samples/hello-reply.json` |
| `POST /api/v1/sync/push` | Till → portal: a batch of changed rows | `samples/push-request.json` (gzip) | `samples/push-reply.json` |
| `GET /api/v1/sync/pull?since={version}&max={n}` | Portal → till: changes after `since` | — | `samples/pull-reply.json` |

`since` = the highest `version` this branch has already applied (0 the first time); `max` = the
branch's `sync.batch_size` (≤ 5000). Paths are our suggestion; keep them or tell us yours.

## 5. The envelope — one changed row (`SyncChange`, both directions)

`src/SSPOS.Application/Sync/SyncChange.cs`. Schema: `schemas/sync-change.schema.json`.

| Field | JSON type | Push (till → portal) | Pull (portal → till) |
|---|---|---|---|
| `seq` | integer | Branch ChangeLog sequence, strictly increasing per branch | Always `0` |
| `entity` | string | Entity type name, e.g. `"Sale"` (PascalCase, as in section 10) | Same; plus `"WebOrder"` (section 12) |
| `entityId` | string (ULID) | The row's `id` | The row's `id` (a new row: a ULID you make) |
| `op` | `"I"` / `"U"` / `"D"` | Inserted / updated / soft-deleted | Same meaning |
| `version` | integer | The row's `rowVersion` after the change | **Your** change counter (see 7) |
| `companyId` | string (ULID) | Always set | Always set |
| `branchId` | string (ULID or `""`) | The row's branch; `""` on a company-wide row and on a child row (e.g. `SaleLine`). The sender is always the `X-SSPOS-Branch-Id` header. | `""` = every branch, else the one branch it is for |
| `registerId` | string (ULID or `""`) | The till, for till-scoped rows; `""` otherwise | `""` |
| `at` | string (date-time, UTC) | When it changed on the till | When it changed on the portal |
| `payload` | object or null | **The whole row** as `samples/entities/<Entity>.json` | The whole row, same shape |
| `key` | string | Derived `entity:entityId:version`; ignore it | Optional; the till ignores it |

**Upsert, not diff.** Every `I`/`U` row carries the complete row. Treat `I` and `U` as upserts by
`entityId` and keep the row with the highest `version`. `D` is a soft delete: the payload still
comes, with `deletedAt` set; keep the row and mark it deleted. The till never hard-deletes a synced
row.

## 6. JSON conventions (exactly what `SyncJson.Options` writes)

- **Names:** camelCase (`receiptNumber`, `vatTotal`). Reading is case-insensitive on the till.
- **Money:** a JSON **number in pounds sterling**, not pence: `5.15` = £5.15. Prices and totals have
  at most 2 decimal places, rounded half away from zero (`Domain/Common/Money.cs`). Cost prices
  (`costPrice`, `costAtSale`, `unitCost`) and quantities (`qty`, `qtyDelta`) may carry up to 4 dp.
  Parse them as decimal, never float. The till may write `1.45` or `1.4500` — same value.
- **Numbers:** the till always writes JSON numbers. It also reads a number sent as a string
  (`"5.15"`), which is why the schemas allow both; send numbers.
- **Percentages:** numbers, `20` = 20 % (`vatPercentage`, `percentage`).
- **Dates and times:** ISO-8601 UTC with `Z`, e.g. `2026-09-23T09:41:12Z` (UK time is shown only
  on screen). A date with no time is `"2026-09-26"`. Treat a date-time with no offset as UTC.
- **Ids:** 26-character ULID strings (`01K5VB000000000SR001000482`), Crockford base32. A missing
  optional id is `null`; a missing envelope id is `""`.
- **Enums:** written as camelCase names, never numbers (`"completed"`, `"over18"`, `"pcs"`).
  Every allowed value is in `samples/enums.json`; section 11 lists them.
- **Nulls:** written, not omitted. Every property in a sample is always present.
- **Embedded JSON strings:** a few columns hold a JSON document as a string (`receiptJson`,
  `linesJson`, `licensedHoursJson`). Store them as-is.
- **Derived members:** anything the till computes rather than stores (e.g. `key`, `isDeleted`,
  `balanceDue`) may appear; the till ignores them when reading.

## 7. Push — idempotent, ordered, acknowledged

- The till sends its oldest unsent rows first, `seq` ascending, one branch per request.
- Store rows **in `seq` order**, then reply with `acknowledgedSeq` = the highest `seq` you have safely
  stored with every lower `seq` of this batch also stored, and `accepted` = rows stored (a row you
  already had counts as accepted). Schema `schemas/push-reply.schema.json`.
- The till marks everything up to `acknowledgedSeq` as sent and resends the rest next run. Replying
  with less than the batch's highest `seq` is fine; the rest comes again.
- **Retries are normal.** A timeout or crash means the till sends the same batch again. The
  idempotency key of a row is `(entity, entityId, version)`; storing the same triple twice must
  change nothing and must give **the same reply**. Also dedupe by `(branchId, seq)`.
- A row whose `version` is lower than one you already hold is stale: accept it (count it) and keep
  the newer one.

## 8. Pull — versions and paging

- `version` on the pull side is **your** number: one counter per company (or per branch), strictly
  increasing, bumped on every change you want tills to see. It is not the row's `rowVersion`.
- Reply with rows whose `version > since` visible to the caller's branch (company-wide + that
  branch), **oldest first**, at most `max` rows; `highestVersion` = the largest `version` in
  `changes`; `hasMore` = true if more are waiting (the till pulls again straight away).
- The till skips any row with `version ≤ since`, and any `(entity, entityId, version)` it has seen, so
  resending is safe. An empty reply is `samples/pull-reply.empty.json`.
- If the shop changed a portal-owned row it has not yet pushed, the till records a **conflict**
  (Sync status screen): by default the owner of the entity wins (section 10) and a person confirms.

## 9. Errors and status codes

Every non-2xx reply has the body in `samples/error-reply.401.json` / `error-reply.422.json`
(`schemas/error-reply.schema.json`, **PROPOSAL**): `code`, `message` (en-GB, shown to the shop
owner), `traceId`, `retryAfterSeconds`, `rejectedKey`.

| Status | Meaning | Till does |
|---|---|---|
| 200 | OK | Moves its cursor. |
| 400 | Malformed request | Stops this run, shows `message`, retries next run. Rows are never dropped. |
| 401 / 403 | Bad or revoked key, or key not for this branch | Stops syncing and shows "API key rejected" until the key is changed. No retry storm. |
| 409 | Contract version not supported | Stops syncing, shows `message` (the till needs updating). |
| 413 | Batch too large | Retries next run with half the batch size. |
| 422 | A row cannot be stored; `rejectedKey` names it | Acknowledge the rows before it (reply 200 with the lower `acknowledgedSeq`) where you can; otherwise the till shows the row on the Sync status screen and retries next run. |
| 429 / 503 | Busy | Waits `retryAfterSeconds` (or its backoff 1, 2, 5, 10, 30, 60 s, `ReconnectPolicy`) and retries. |
| 5xx, timeout, no network | Portal down | Backoff and retry. The shop keeps trading; rows wait in the ChangeLog. |

## 11. What the portal must never do

1. Change or delete a completed sale, sale line, payment, refund, VAT row, journal row or audit row
   (`specs/invariants.md` rule 5: they are historically immutable; the till's database refuses such
   updates). Corrections are new rows made on the till (a refund, a void), never edits.
2. Send any till-owned entity down (section 10).
3. Send a price or money value with more than 2 decimal places.
4. Send a row with no `companyId`, or a branch row with no `branchId`.
5. Re-key a row, reuse an id for a different row, or send a numeric enum.
6. Send one branch's rows to another branch, or send `sync.hub_api_key` (or any secret) in a
   `Setting` row.

Enum values (camelCase, from `samples/enums.json`):
`unitType` pcs, kg, open · `ageRule` none, over16, over18, tobaccoGenerational, nicotine, lottery18,
knives18, fireworks18, solvents18, energyDrink16, paracetamol16 · `barcodeSource` internal,
supplier, plu, weighted, coupon, gs1 · `vatTreatment` apply, exempt, outOfScope ·
`negativeStockPolicy` allow, warn, block · `saleType` sale, refund, exchange, quote, training,
deposit · `saleStatus` open, held, completed, voided · `salePaymentStatus` approved, reversed,
recovered · `discountSource` manual, promotion, customerGroup, staff, coupon · `stockMovementType`
sale, refund, adjustment, received, wastage, transfer, stockTake, damaged, supplierReturn, expiry,
theft, openingStock, promotionSample · `customerOrderStatus` ordered, ready, collected, cancelled,
expired · `customerOrderPaymentKind` deposit, partPayment, collection, refund.

## 12. Web orders / click-and-collect — PROPOSAL

The till has customer orders (`src/SSPOS.Domain/Orders/CustomerOrder.cs`: deposit, ready, collect,
cancel, expire) but **no web-order message yet**. Proposed:

1. **Portal → till:** a pull row with `entity: "WebOrder"`, `branchId` = the collecting shop,
   payload `samples/web-order.json` (`schemas/web-order.schema.json`): `id` (your ULID — becomes the
   till's CustomerOrder id), `reference`, `customer`, `lines` (the till's own
   `CustomerOrderLineSnapshot`: productId, name, qty, unitPrice inc VAT, vatRateId, vatPercentage),
   `money` (`goodsTotal`, `paidOnline`, `paymentReference`), `collectBy`, `notes`, `placedAt`.
2. **Till:** creates a `CustomerOrder` with the same id, status `ordered`, and holds the stock.
3. **Till → portal:** every status change comes up as that `CustomerOrder` row
   (`samples/entities/CustomerOrder.json`): `ordered` → `ready` (picked; `readyAt`) → `collected`
   (`collectedAt`, `saleId` = the till sale that took the money) or `cancelled` / `expired`.
   Show the customer that status.
4. **Open question for the owner:** `paidOnline` must be `0.00` for now — every pound the till books
   is a real till sale, so money taken online needs its own tender design before we accept it.
   Cancelling from the web is not in v1: the customer rings the shop.

## 13. Entity payloads

**Every entity has a schema.** `schemas/entities/*.schema.json` is generated for every single
`Entity`-derived type in the till's EF model (all ~123 of them, wave E/P4-65) — walk
`src/SSPOS.Infrastructure/Persistence/SsposDbContext.cs`'s `DbSet<T>` properties for the full list,
or just read the schema folder. A hand-picked 12 also get a realistic **sample**:
`samples/entities/{Department, Category, VatRate, Product, ProductBarcode, Customer, Sale, SaleLine,
SalePayment, SaleVat, StockMovement, CustomerOrder}.json`. Every other entity has a schema only —
ask us for a sample of any you need, or build one from its schema; the schema is exhaustive (every
column, all required) either way.
The sample sale is 1 × Warburtons Toastie 800g £1.45 (zero-rated) + 2 × Coca-Cola 500ml £1.85
(20 %) = £5.15, VAT £0.62, paid by card. Child rows link by id: `saleLine.saleId`,
`salePayment.saleId`, `saleVat.saleId`, `stockMovement.refId`/`refLineId`. `saleVat` rows are the
VAT analysis per rate (`net + vat = gross`; the grosses add up to `sale.total`). Barcodes are valid
EAN-13 (`Domain/Catalogue/Barcode.GenerateInternal`, the shop's own `04…` range).
Other entities follow the same rules (all columns, camelCase).

Any table added to the till later appears here automatically with its owner, and the version
number in `X-SSPOS-Contract` does not change for additive tables.

## 14. How to test against the till

1. On a test PC run the till (`dotnet run --project src/SSPOS.Desktop`), sign in as the owner.
2. Settings → Hub sync: Hub address = your test API URL, Portal API key = a test key, Cloud sync = on.
3. Ring a sale, then Sync status → **Sync now** (or wait 30 s). Your `POST /api/v1/sync/push`
   should receive a body shaped like `samples/push-request.json`.
4. For a pull, have your API return `samples/pull-reply.json` verbatim from
   `GET /api/v1/sync/pull`; the Sync status screen shows the rows as applied (or as conflicts).
   Return `samples/pull-reply.empty.json` when nothing is new.
5. What the till shows and logs: the Sync status screen shows pending rows, last success, last
   error (your `message`) and conflicts. The log is
   `%ProgramData%\SSPOS\logs\*.log` (one line per run: rows pushed, acknowledged seq, rows pulled,
   highest version, or the error code). The API key is never written to the log.
6. Validate your own replies against `schemas/*.schema.json` (JSON Schema draft 2020-12).

Until the till's HTTPS transport is merged (our integration task), step 3 sends nothing: the till
ships with a null transport. Build and test your API against the samples and schemas meanwhile.

## 16. Known gaps (till side, fixed in the integration task)

- **No HTTPS transport yet.** `NullHubTransport` is registered (`src/SSPOS.Application/DependencyInjection.cs`);
  HTTPS-only, the headers, gzip, the status handling, the 30 s timeout and the log line in sections 3, 9
  and 14 are what it will do.
  Nothing reads `sync.hub_api_key` yet.
- **Rows that do not derive `Entity` never enter the ChangeLog**, so they cannot sync although
  `SyncOwnershipMap` lists them: `Setting` and `RolePermission`
  (`src/SSPOS.Infrastructure/Persistence/Interceptors/ChangeLogInterceptor.cs` only reads
  `Entries<Entity>()`). (`UnitConversion` was listed here too but no such entity exists; it was
  removed from `SyncOwnershipMap` in wave E.)
- **Child rows carry no branch or till of their own.** `SaleLine`, `SalePayment`, `SaleVat` and
  `CustomerOrderPayment` derive `Entity`, not `BranchEntity`; the ChangeLog
  writes `BranchId = ""` for them (`ChangeLogInterceptor.cs`) and the envelope's `branchId` /
  `registerId` are `""` too (`src/SSPOS.Infrastructure/Persistence/Sync/ChangeFeed.cs`). Use the
  `X-SSPOS-Branch-Id` header for the branch and the parent row for the till (`saleId` → `sale.registerId`).
- **Hard deletes are not logged** (`ChangeLogInterceptor` handles `Added`/`Modified` only). The till
  soft-deletes synced data, so this matters only if a hard delete is ever added.
- **Branch price overrides are till-owned.** `BranchProduct.priceOverride` sits on a branch-owned
  row with the stock figures, so the portal cannot set a per-branch price today; per-branch pricing
  from the portal needs its own portal-owned row.
- **Pull apply is not wired.** `NullHubEntityApplier` (`CanApply = false`) records pulled rows but
  writes nothing until the integration task maps each payload to its entity.
- **Web orders** (section 12) and the hello / error bodies (sections 4, 9) are proposals with no till
  code yet.
