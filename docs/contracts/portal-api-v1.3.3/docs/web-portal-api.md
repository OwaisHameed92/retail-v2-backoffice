# SSPOS web portal API — the till's JSON contract (v1)

**For:** the developer building the SSPOS web portal, its API and its database.
**From:** the SSPOS till team. **Status:** contract v1, 2026-09-23 (task P4-65); section 17 (licensing,
devices, onboarding, migration) and the defined `hello` / error bodies added 2026-09-26 (document revision 1.1 —
additive, `X-SSPOS-Contract` stays `1`); section 17.16 (a key carries the shop, open local keys, local keys
reported to the portal) added 2026-09-28 (revision 1.2 — additive).

**Machine-readable pack:** `docs/web-portal-api/openapi.yaml` (OpenAPI 3.1, every endpoint),
`docs/web-portal-api/SSPOS.postman_collection.json` + `SSPOS.postman_environment.json` (every call, sample
bodies, saved example replies usable as a mock server), `schemas/` + `samples/` (sync, generated) and
`licensing/schemas/` + `licensing/samples/` (section 17, hand-written, validated).

You build the portal and its API. We give you the exact JSON the till sends and expects back; when
your API is live we point a real HTTP transport at it (a separate task on our side). Nothing in the
till talks to you until the shop owner has set three things (section 1).

Everything in `docs/web-portal-api/samples/` and `docs/web-portal-api/schemas/` is **generated by
serialising the till's real C# types** with the till's own serializer settings
(`src/SSPOS.Application/Sync/SyncJson.cs`). A test
(`tests/SSPOS.Infrastructure.Tests/Sync/PortalContract/PortalContractTests.cs`) fails the build if a
file stops matching the code, so the samples are the truth; where this text and a sample disagree,
the sample wins. Parts marked **PROPOSAL** have no till type yet; they are our suggested shape and
we will build the till side to whatever we agree. The section 17 files under `docs/web-portal-api/licensing/`
are **not** generated: they are the agreed contract, written by hand and checked by a JSON Schema validator
(the contract test polices only `samples/` and `schemas/`, so it never flags them).

## 1. The three settings — nothing leaves the shop until all three are set

Settings → **Hub sync** (group 20), on each shop's main till:

| Setting | Key | Default | Meaning |
|---|---|---|---|
| Hub address | `sync.hub_url` | blank | Your API's base URL, e.g. `https://portal.example.co.uk`. HTTPS only. |
| Portal API key | `sync.hub_api_key` | blank | The key your portal issues for **this branch**. Masked on screen, never logged, never printed, never in a support bundle. |
| Cloud sync | `sync.hub_enabled` | **off** | The master switch. While off, the till opens no connection at all. |
| Sync every | `sync.interval_seconds` | 30 | Seconds between runs (10–3600). |
| Rows per batch | `sync.batch_size` | 5000 | Rows per push (100–5000; 5,000 is a hard ceiling). |

Owner's flow once your API is live: type the URL → paste the API key → switch Cloud sync on.

## 2. Company → Branch → Till (how the till is structured — build the portal the same way)

1. **Hierarchy.** Company → Branch (a shop) → Register (a till). Every row carries `companyId`; every
   branch-scoped row also carries `branchId`; every till-scoped row also carries `registerId`
   (`src/SSPOS.Domain/Common/Entity.cs`, `BranchEntity.cs`, `RegisterEntity.cs`). Every row has an
   `id` that is a **ULID made on the till** (`Entity.Id = Shared.Ulid.NewId()`), globally unique.
   **The portal must never re-key a row**; store the till's id as your primary key.
2. **Who talks to the portal: one sender per branch.** Inside a branch, the main till owns the branch
   database and hosts the embedded store server (`src/SSPOS.Server`); the other tills sell against
   that database over the shop LAN and keep only a cache and an emergency queue
   (`src/SSPOS.Client`, `src/SSPOS.Domain/Common/TillRole.cs`: `SingleTill`, `MainTill`,
   `SecondaryTill`). So **only the main till (or the only till) of each branch pushes and pulls**; a
   second till's sales reach you inside its branch's batches, carrying that till's `registerId`.
   The till enforces this (`src/SSPOS.Application/Sync/SyncSenderGate.cs`: a `SecondaryTill` is
   refused with `sync.wrong_till`). One branch = one connection = one cursor.
3. **Identification.** Every request carries the headers in section 3: the API key, company id,
   branch id, the sending register id, the contract version and the store protocol version
   (`src/SSPOS.Server/Contracts/StoreProtocol.cs`, `Version = 1`). The API key is **per branch**
   (`sync.hub_api_key` is a branch-scoped setting); issue one key per branch and reject a request
   whose `X-SSPOS-Branch-Id` is not the key's branch.
4. **Company-wide vs per branch.**
   - Company-wide (no `branchId` on the row): the master data in section 10 — products, barcodes,
     aliases, departments, categories, units, VAT rates, promotions, customers, users, roles,
     suppliers, payment types, reasons, accounts, price history.
   - Per branch (`BranchEntity`): `BranchProduct` (the branch's stock on hand and its optional
     `priceOverride` — `src/SSPOS.Domain/Catalogue/BranchProduct.cs`), `ZReport`, `CustomerOrder`,
     `Register`, `SyncConflict` and other branch rows.
   - Per till (`RegisterEntity`): `Sale`, `Shift`, `StockMovement`. Sales are numbered **per till**
     (`Register.NextSaleNo` / `NextRefundNo`, `src/SSPOS.Domain/Common/Register.cs`); receipt numbers
     look like `LDS-01-000482` = branch code, till code, sale number (`Register.ReceiptPrefix`).
     Two tills may both have a sale number 17; `(registerId, number)` and `id` are unique, `number`
     alone is not.
   - Down to **all branches**: rows with `branchId: ""` (company-wide master data). Down to **one
     branch**: rows with that branch's id (e.g. a web order for that shop).
5. **Cursors are per branch.** The push cursor (`seq`) is the branch database's own ChangeLog
   sequence; Leeds and Bradford both have a `seq` 5120 and they are different rows. Key everything
   by `(branchId, seq)`. The pull cursor (`since`) is per branch too
   (`src/SSPOS.Domain/Sync/SyncState.cs`, one row per branch). **A pull must never return another
   branch's till-owned rows**, only company-wide rows and rows addressed to the caller's branch.
6. **Samples.** `samples/push-request.json` (Leeds, sent by Leeds till 1),
   `push-request.second-till.json` (a sale rung on Leeds till 2 — still sent by Leeds till 1, same
   `branchId`, `seq` carries on, `registerId` is till 2) and `push-request.second-branch.json`
   (Bradford: other `branchId`, its own `seq` numbers).

## 3. Transport

| | |
|---|---|
| Protocol | HTTPS only (TLS 1.2+). The till refuses `http://`. |
| Auth | `Authorization: Bearer <sync.hub_api_key>` on every request. |
| Identity headers | `X-SSPOS-Company-Id`, `X-SSPOS-Branch-Id`, `X-SSPOS-Register-Id` (the sending till), `X-SSPOS-Contract: 1`, `X-SSPOS-Store-Protocol: 1`, `X-SSPOS-App-Version: 3.x.y` |
| Content type | `application/json; charset=utf-8` both ways |
| Compression | Push body is **gzip** (`Content-Encoding: gzip`) — `SyncBatch.Pack` gzips it. Replies may be gzip if the till sends `Accept-Encoding: gzip`. |
| Push size | ≤ 5,000 rows per request (`SyncBatcher.MaxRowsPerBatch`), at most 5 batches per run. Allow request bodies up to 50 MB uncompressed. |
| Timeouts | Till waits 30 s for a reply, then treats it as a network failure and retries later. |
| Frequency | Every `sync.interval_seconds` (30 s) on the branch's main till (`src/SSPOS.Server/Hosting/SyncTimerHost.cs`; a tick does nothing while Cloud sync is off), at Close Shop, and on "Sync now" (Sync status screen). Order in a run: push, then pull (`src/SSPOS.Application/Sync/RunSync/RunSyncHandler.cs`). |

## 4. Endpoints

| Method + path | Purpose | Body | Reply |
|---|---|---|---|
| `GET /api/v1/sync/hello` | Check address + key (section 4.1) | — | `samples/hello-reply.json` |
| `POST /api/v1/sync/push` | Till → portal: a batch of changed rows | `samples/push-request.json` (gzip) | `samples/push-reply.json` |
| `GET /api/v1/sync/pull?since={version}&max={n}` | Portal → till: changes after `since` | — | `samples/pull-reply.json` |
| `POST /api/v1/licence/activate` | **Per-till licence:** bind an e-mailed key to this PC, get its token | 17.15.1 | 17.15.1 |
| `POST /api/v1/devices/activate` | Link a till to an account (activation code) | 17.4 | 17.4 |
| `POST /api/v1/licence/validate` | Daily licence check + heartbeat | 17.5 | 17.5 |
| `POST /api/v1/licence/redeem` | A key typed at a linked till | 17.6 | 17.6 |
| `POST /api/v1/devices/deactivate` | Free a seat / transfer the main till | 17.7 | 17.7 |

`since` = the highest `version` this branch has already applied (0 the first time); `max` = the
branch's `sync.batch_size` (≤ 5000). The paths are fixed by this contract (the till has them built in);
a different host is fine (`sync.hub_url` / `hubUrl`).

### 4.1 `GET /api/v1/sync/hello` — defined

The till's **Test** key on Settings → Hub sync, and the first call after activation / migration. It proves
the address, the TLS certificate, the key and the key's branch in one round trip.

- **Request:** no body; `Authorization: Bearer <key>` and every section 3 header.
- **Reply 200** (`schemas/hello-reply.schema.json`, `samples/hello-reply.json`): `contractVersion` (1),
  `companyId` and `branchId` (the key's — the till checks they equal its own and shows a mismatch as "this key
  is for another install"), `branchName` (shown so the owner sees he pasted the right key), `serverTimeUtc` (the
  till warns when its clock is more than 5 minutes out), `maxBatchRows` (the most rows one push may carry,
  ≤ 5000; the till uses the smaller of this and `sync.batch_size`). New fields may be added.
- **Errors:** 401 `auth.invalid_key` / `auth.key_revoked`, 403 `auth.wrong_branch`, 409 `contract.unsupported`,
  426 `app.update_required`, 429 / 503 with `Retry-After`, 500. Body = section 9.

## 5. The envelope — one changed row (`SyncChange`, both directions)

`src/SSPOS.Application/Sync/SyncChange.cs`. Schema: `schemas/sync-change.schema.json`.

| Field | JSON type | Push (till → portal) | Pull (portal → till) |
|---|---|---|---|
| `seq` | integer | Branch ChangeLog sequence, strictly increasing per branch | Always `0` |
| `entity` | string | Entity type name, e.g. `"Sale"` (PascalCase, as in section 10) | Same; plus `"WebOrder"` (section 12) |
| `entityId` | string (ULID) | The row's `id` | The row's `id` (a new row: a ULID you make) |
| `op` | `"I"` / `"U"` / `"D"` | Inserted / updated / soft-deleted | Same meaning |
| `version` | integer | The row's `rowVersion` after the change | **Your** change counter (see 7) |
| `companyId` | string (ULID) | Always set | Always set |
| `branchId` | string (ULID or `""`) | The row's branch; `""` on a company-wide row and on a child row (e.g. `SaleLine`). The sender is always the `X-SSPOS-Branch-Id` header. | `""` = every branch, else the one branch it is for |
| `registerId` | string (ULID or `""`) | The till, for till-scoped rows; `""` otherwise | `""` |
| `at` | string (date-time, UTC) | When it changed on the till | When it changed on the portal |
| `payload` | object or null | **The whole row** as `samples/entities/<Entity>.json` | The whole row, same shape |
| `key` | string | Derived `entity:entityId:version`; ignore it | Optional; the till ignores it |

**Upsert, not diff.** Every `I`/`U` row carries the complete row. Treat `I` and `U` as upserts by
`entityId` and keep the row with the highest `version`. `D` is a soft delete: the payload still
comes, with `deletedAt` set; keep the row and mark it deleted. The till never hard-deletes a synced
row.

## 6. JSON conventions (exactly what `SyncJson.Options` writes)

- **Names:** camelCase (`receiptNumber`, `vatTotal`). Reading is case-insensitive on the till.
- **Money:** a JSON **number in pounds sterling**, not pence: `5.15` = £5.15. Prices and totals have
  at most 2 decimal places, rounded half away from zero (`Domain/Common/Money.cs`). Cost prices
  (`costPrice`, `costAtSale`, `unitCost`) and quantities (`qty`, `qtyDelta`) may carry up to 4 dp.
  Parse them as decimal, never float. The till may write `1.45` or `1.4500` — same value.
- **Numbers:** the till always writes JSON numbers. It also reads a number sent as a string
  (`"5.15"`), which is why the schemas allow both; send numbers.
- **Percentages:** numbers, `20` = 20 % (`vatPercentage`, `percentage`).
- **Dates and times:** ISO-8601 UTC with `Z`, e.g. `2026-09-23T09:41:12Z` (UK time is shown only
  on screen). A date with no time is `"2026-09-26"`. Treat a date-time with no offset as UTC.
- **Ids:** 26-character ULID strings (`01K5VB000000000SR001000482`), Crockford base32. A missing
  optional id is `null`; a missing envelope id is `""`.
- **Enums:** written as camelCase names, never numbers (`"completed"`, `"over18"`, `"pcs"`).
  Every allowed value is in `samples/enums.json`; section 11 lists them.
- **Nulls:** written, not omitted. Every property in a sample is always present.
- **Embedded JSON strings:** a few columns hold a JSON document as a string (`receiptJson`,
  `linesJson`, `licensedHoursJson`). Store them as-is.
- **Derived members:** anything the till computes rather than stores (e.g. `key`, `isDeleted`,
  `balanceDue`) may appear; the till ignores them when reading.

## 7. Push — idempotent, ordered, acknowledged

- The till sends its oldest unsent rows first, `seq` ascending, one branch per request.
- Store rows **in `seq` order**, then reply with `acknowledgedSeq` = the highest `seq` you have safely
  stored with every lower `seq` of this batch also stored, and `accepted` = rows stored (a row you
  already had counts as accepted). Schema `schemas/push-reply.schema.json`.
- The till marks everything up to `acknowledgedSeq` as sent and resends the rest next run. Replying
  with less than the batch's highest `seq` is fine; the rest comes again.
- **Retries are normal.** A timeout or crash means the till sends the same batch again. The
  idempotency key of a row is `(entity, entityId, version)`; storing the same triple twice must
  change nothing and must give **the same reply**. Also dedupe by `(branchId, seq)`.
- A row whose `version` is lower than one you already hold is stale: accept it (count it) and keep
  the newer one.

## 8. Pull — versions and paging

- `version` on the pull side is **your** number: one counter per company (or per branch), strictly
  increasing, bumped on every change you want tills to see. It is not the row's `rowVersion`.
- Reply with rows whose `version > since` visible to the caller's branch (company-wide + that
  branch), **oldest first**, at most `max` rows; `highestVersion` = the largest `version` in
  `changes`; `hasMore` = true if more are waiting (the till pulls again straight away).
- The till skips any row with `version ≤ since`, and any `(entity, entityId, version)` it has seen, so
  resending is safe. An empty reply is `samples/pull-reply.empty.json`.
- If the shop changed a portal-owned row it has not yet pushed, the till records a **conflict**
  (Sync status screen): by default the owner of the entity wins (section 10) and a person confirms.

## 9. Errors and status codes

Every non-2xx reply has the body in `samples/error-reply.401.json` / `error-reply.422.json`
(`schemas/error-reply.schema.json`, defined): `code`, `message` (en-GB, shown to the shop
owner), `traceId`, `retryAfterSeconds`, `rejectedKey`, and optionally `details` (an open object of
machine-readable extras — `licensing/schemas/error-reply.schema.json`). Every code, on every endpoint, is
listed in section 17.12 and in `licensing/samples/error-codes.json`. 429 and 503 also carry a `Retry-After`
header. A code the till does not know is handled by its HTTP status as below.

| Status | Meaning | Till does |
|---|---|---|
| 200 | OK | Moves its cursor. |
| 400 | Malformed request | Stops this run, shows `message`, retries next run. Rows are never dropped. |
| 401 / 403 | Bad or revoked key, or key not for this branch | Stops syncing and shows "API key rejected" until the key is changed. No retry storm. |
| 409 | Contract version not supported | Stops syncing, shows `message` (the till needs updating). |
| 413 | Batch too large | Retries next run with half the batch size. |
| 422 | A row cannot be stored; `rejectedKey` names it | Acknowledge the rows before it (reply 200 with the lower `acknowledgedSeq`) where you can; otherwise the till shows the row on the Sync status screen and retries next run. |
| 429 / 503 | Busy | Waits `retryAfterSeconds` (or its backoff 1, 2, 5, 10, 30, 60 s, `ReconnectPolicy`) and retries. |
| 5xx, timeout, no network | Portal down | Backoff and retry. The shop keeps trading; rows wait in the ChangeLog. |

## 11. What the portal must never do

1. Change or delete a completed sale, sale line, payment, refund, VAT row, journal row or audit row
   (`specs/invariants.md` rule 5: they are historically immutable; the till's database refuses such
   updates). Corrections are new rows made on the till (a refund, a void), never edits.
2. Send any till-owned entity down (section 10).
3. Send a price or money value with more than 2 decimal places.
4. Send a row with no `companyId`, or a branch row with no `branchId`.
5. Re-key a row, reuse an id for a different row, or send a numeric enum.
6. Send one branch's rows to another branch, or send `sync.hub_api_key` (or any secret) in a
   `Setting` row.

Enum values (camelCase, from `samples/enums.json`):
`unitType` pcs, kg, open · `ageRule` none, over16, over18, tobaccoGenerational, nicotine, lottery18,
knives18, fireworks18, solvents18, energyDrink16, paracetamol16 · `barcodeSource` internal,

deposit · `saleStatus` open, held, completed, voided · `salePaymentStatus` approved, reversed,

## 12. Web orders / click-and-collect — PROPOSAL

The till has customer orders (`src/SSPOS.Domain/Orders/CustomerOrder.cs`: deposit, ready, collect,
cancel, expire) but **no web-order message yet**. Proposed:

1. **Portal → till:** a pull row with `entity: "WebOrder"`, `branchId` = the collecting shop,
   payload `samples/web-order.json` (`schemas/web-order.schema.json`): `id` (your ULID — becomes the
   till's CustomerOrder id), `reference`, `customer`, `lines` (the till's own
   `CustomerOrderLineSnapshot`: productId, name, qty, unitPrice inc VAT, vatRateId, vatPercentage),
   `money` (`goodsTotal`, `paidOnline`, `paymentReference`), `collectBy`, `notes`, `placedAt`.
2. **Till:** creates a `CustomerOrder` with the same id, status `ordered`, and holds the stock.
3. **Till → portal:** every status change comes up as that `CustomerOrder` row
   (`samples/entities/CustomerOrder.json`): `ordered` → `ready` (picked; `readyAt`) → `collected`
   (`collectedAt`, `saleId` = the till sale that took the money) or `cancelled` / `expired`.
   Show the customer that status.
4. **Open question for the owner:** `paidOnline` must be `0.00` for now — every pound the till books
   is a real till sale, so money taken online needs its own tender design before we accept it.
   Cancelling from the web is not in v1: the customer rings the shop.

## 13. Entity payloads

**Every entity has a schema.** `schemas/entities/*.schema.json` is generated for every single
`Entity`-derived type in the till's EF model (all ~123 of them, wave E/P4-65) — walk
`src/SSPOS.Infrastructure/Persistence/SsposDbContext.cs`'s `DbSet<T>` properties for the full list,
or just read the schema folder. A hand-picked 12 also get a realistic **sample**:
`samples/entities/{Department, Category, VatRate, Product, ProductBarcode, Customer, Sale, SaleLine,
SalePayment, SaleVat, StockMovement, CustomerOrder}.json`. Every other entity has a schema only —
ask us for a sample of any you need, or build one from its schema; the schema is exhaustive (every
column, all required) either way.
The sample sale is 1 × Warburtons Toastie 800g £1.45 (zero-rated) + 2 × Coca-Cola 500ml £1.85
(20 %) = £5.15, VAT £0.62, paid by card. Child rows link by id: `saleLine.saleId`,
`salePayment.saleId`, `saleVat.saleId`, `stockMovement.refId`/`refLineId`. `saleVat` rows are the
VAT analysis per rate (`net + vat = gross`; the grosses add up to `sale.total`). Barcodes are valid
EAN-13 (`Domain/Catalogue/Barcode.GenerateInternal`, the shop's own `04…` range).
Other entities follow the same rules (all columns, camelCase).

Any table added to the till later appears here automatically with its owner, and the version
number in `X-SSPOS-Contract` does not change for additive tables.

## 14. How to test against the till

1. On a test PC run the till (`dotnet run --project src/SSPOS.Desktop`), sign in as the owner.
2. Settings → Hub sync: Hub address = your test API URL, Portal API key = a test key, Cloud sync = on.
3. Ring a sale, then Sync status → **Sync now** (or wait 30 s). Your `POST /api/v1/sync/push`
   should receive a body shaped like `samples/push-request.json`.
4. For a pull, have your API return `samples/pull-reply.json` verbatim from
   `GET /api/v1/sync/pull`; the Sync status screen shows the rows as applied (or as conflicts).
   Return `samples/pull-reply.empty.json` when nothing is new.
5. What the till shows and logs: the Sync status screen shows pending rows, last success, last
   error (your `message`) and conflicts. The log is
   `%ProgramData%\SSPOS\logs\*.log` (one line per run: rows pushed, acknowledged seq, rows pulled,
   highest version, or the error code). The API key is never written to the log.
6. Validate your own replies against `schemas/*.schema.json` (JSON Schema draft 2020-12).

The till's HTTPS transport is built (section 16): step 3 really calls your API. Until your server is up, test
against the samples, the schemas and a Postman mock server.

only, applied without a ChangeLog row (no echo), identical content = no write, a version ≤ the one held is ignored,
child-before-parent rows are parked until the parent arrives, adaptive slices (≤200 rows, ~8 ms). **Company and
Branch:** pulled rows update their detail columns only (name, code, VAT, address, phone, e-mail) — the portal may send
a shop's edited details; the till never inserts a Company/Branch from a pull. The §17.8 migration (`cloud/migrate`,
initial upload, `cloud/migrate/complete`) is built; its place is kept in branch settings `sync.upload_*`; the credential
is the portal key the shop enters (left in `sync.migrate_code`). Licence calls built: `licence/activate`,
`licence/validate`, `licence/redeem` (incl. local-key reports, §17.16), `devices/deactivate`.

Still open:
- **`baseVersion` is not sent on push** (§19.3): the till holds the portal's per-row version in memory only, so parked
  rows and versions are lost on a restart (the pull cursor still covers restarts). Needs a table
  (`SyncRowVersion(entity, entityId, portalVersion)` + parked pulls) — then `SyncChange.baseVersion` and new samples.
- **Rows that do not derive `Entity` never enter the ChangeLog and are not applied from a pull**: `Setting` and
  `RolePermission` (need a deny-list for secret settings and a settings-cache refresh).
- **Child rows carry no branch or till of their own.** `SaleLine`, `SalePayment`, `SaleVat` and
  `CustomerOrderPayment` derive `Entity`, not `BranchEntity`; the envelope's `branchId` / `registerId` are `""` for
  them. Use the `X-SSPOS-Branch-Id` header for the branch and the parent row for the till (`saleId` → `sale.registerId`).
- **Hard deletes are not logged** (the till soft-deletes synced data).
- **Branch price overrides are till-owned** (`BranchProduct.priceOverride`); per-branch pricing from the portal needs
  its own portal-owned row.
- **Web orders** (section 12) are a proposal with no till code yet.
- **The migration upload scans by `createdAt` without an index** — fine for a normal shop, slow for a very large one.

### 17.1 The idea in five lines

1. The portal is the **issuer**: it decides who may trade, for how long, with how many tills and which paid features.
2. It says so in a **signed licence token** that the till checks **offline**. The till never needs the portal to
   ring a sale; it needs a valid token and, for a cloud licence, a successful check at least every 14 days.
3. The branch's **main till** is the only caller (as for sync, section 2.2): it activates, validates daily
   (the heartbeat, listing every till of the branch), redeems keys and releases seats. Other tills join the main
   till over the shop LAN as today and never talk to the portal.
4. A **licence problem is never an HTTP error**: `licence/validate` answers 200 with a `status`, so the till always
   gets the portal's time, messages and (maybe) a fresh token.
5. Everything is **additive**: new fields, new features, new limits, new endpoints never break an older till (17.11).

| Endpoint | Auth | Called when |
|---|---|---|
| `POST /api/v1/licence/activate` | the licence key in the body | **any** till: the shop pastes the e-mailed key (17.15) |
| `POST /api/v1/devices/activate` | activation code in the body | first-run wizard "Link to your account"; a replacement PC with a transfer code |
| `GET /api/v1/sync/hello` | branch key | right after linking; the Test key (section 4.1) |

### 17.2 The licence token

#### Format (exactly `specs/licensing.md` section 1)

```
SSPOS1.<base64url(payload JSON)>.<base64url(Ed25519 signature over ASCII "SSPOS1." + payload part)>
```

- `base64url` = RFC 4648 section 5 alphabet (`-` and `_`), **no `=` padding**.
- The payload is UTF-8 JSON, camelCase. Write it compact; field order and spacing do not matter because the
  signature covers the **base64url text**, not a re-serialisation. **Never re-serialise to verify.**
- Ed25519 (RFC 8032, pure, no pre-hash). Signature = 64 bytes = 86 base64url characters.
- A token is **not secret** (signed, not encrypted): the till shows its fields. It is typically 700–900 characters.
  The till accepts it with line breaks or spaces pasted in (it strips whitespace).
- The till's reference implementation is `src/SSPOS.Infrastructure/Licensing/LicenceTokens.cs` (BouncyCastle);
  the payload type is `src/SSPOS.Domain/Licensing/LicenceClaims.cs`.

#### Payload fields (`licensing/schemas/licence-token-payload.schema.json`)

**The details only start the wizard.** The till pre-fills its first-run wizard from `businessName`, `branchName` and

are the truth, not your licence form; keep the form for new keys.

**Unknown fields are ignored** by every till, so you may add fields at any time. Absent, `null` and `""` mean the
same thing to the till; an older key without `company` or `limits.branches` still works. Samples:
`licence-token.payload.{trial,full,local}.json` (no company block), `licence-token.payload.per-till.json` (portal,
with the company block) and `licence-token.payload.local-open.json` (open local key, with the company block).

#### How a till (and your redeem/migrate code) verifies a token

1. Strip whitespace. It must start with `SSPOS1.` and have exactly three dot-separated parts.
2. base64url-decode part 2 and parse it as JSON (untrusted so far). `v` > 1 → `licence.unsupported_version`.
3. Look up `kid` in the trusted (built-in) keys. Not there → if the token has `signerCert`, check the certificate
   (17.17) and use the public key it carries; bad, from a non-approver, for another kid, or ended before the
   token's `issuedAt` → `licence.bad_signer_certificate`. No `signerCert` → `licence.unknown_key`.
4. Verify the Ed25519 signature (part 3) over the ASCII bytes of `"SSPOS1." + part 2` → fails: `licence.bad_signature`.
5. Only now trust the fields: `validFrom ≤ now ≤ expiresAt` (the till uses the later of its clock and its
   clock watermark / last portal time), then the binding (`local`: `installCode` = this install's, or — an open
   key — the install code the till bound it to when it first accepted it; `portal`: `installCode` = this install's
   for a per-till token (17.15), else `companyId`/`branchId` = this till's), then `maxRegisters`, `features`,
   `limits`, `onlineCheck`. For a local key **report** your `redeem` code checks steps 1–4 only (it records an
   expired key too); the binding is what the report itself establishes (17.16).

#### Keys: who holds what

- **You generate your own Ed25519 key pair.** The private key never leaves the portal's server side (a KMS/HSM or
  an encrypted secret store — never the database in plain text, never a repository, never an e-mail).
- **You send us the public key and its kid** (`licensing/samples/public-key-handover.json`: `kid`, `alg`,
  `publicKeyBase64Url` = raw 32 bytes, optional PEM). **We send back a signer certificate** (17.17) — we do NOT
  build your key into the till, so no till release is ever needed for it. You put the certificate in every token
  (`signerCert`). A till trusts a **list** of built-in kids (one per licence-generator installation) plus any key
  one of its **approvers** certified.
- **We send you every generator public key + kid**, so your `redeem` and `migrate` can verify local tokens. You
  verify with them; you never sign with them.
- **Rotation** (planned or after a leak): make a new pair → send us the public key → we send a certificate for it →
  sign with the new key and its certificate at once (no till release; every till already trusts the approver).
  Tokens are re-issued at the next daily check. A leaked key is withdrawn by kid (`RetiredAfter` cut-off) in the
  next release; tokens it made before the cut-off keep working. Every request that can receive a token carries
  `trustedKids` (built-in kids) and `approverKids` (built-in kids whose certificates the till accepts): **sign a
  returned token with a kid in `trustedKids`, or with your certified key when its certificate's `approvedBy` is in
  `approverKids`.**

#### Signing and verifying — code

The PHP and Node snippets below were run against the worked example and reproduce its token exactly.

**PHP / Laravel** (ext-sodium, bundled with PHP ≥ 7.2):

```php
function b64u(string $bin): string { return sodium_bin2base64($bin, SODIUM_BASE64_VARIANT_URLSAFE_NO_PADDING); }
function b64u_decode(string $s): string { return sodium_base642bin($s, SODIUM_BASE64_VARIANT_URLSAFE_NO_PADDING); }

// once: make the key pair, keep $secret server-side, send us $public + $kid
$pair   = sodium_crypto_sign_keypair();
$secret = sodium_crypto_sign_secretkey($pair);            // 64 bytes (seed + public) - SECRET
$public = sodium_crypto_sign_publickey($pair);            // 32 bytes - send b64u($public)
$kid    = 'k' . substr(hash('sha256', $public), 0, 8);

function sspos_sign(array $payload, string $secret64): string {
    $part  = b64u(json_encode($payload, JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE));
    $input = 'SSPOS1.' . $part;
    return $input . '.' . b64u(sodium_crypto_sign_detached($input, $secret64));
}
// from a stored 32-byte seed instead: sodium_crypto_sign_secretkey(sodium_crypto_sign_seed_keypair($seed32))

function sspos_verify(string $token, array $publicKeysByKid): ?array {   // for redeem / migrate
    $parts = explode('.', preg_replace('/\s+/', '', $token));
    if (count($parts) !== 3 || $parts[0] !== 'SSPOS1') return null;
    $payload = json_decode(b64u_decode($parts[1]), true);
    $key = $publicKeysByKid[$payload['kid'] ?? ''] ?? null;
    if (!is_array($payload) || $key === null) return null;
    return sodium_crypto_sign_verify_detached(b64u_decode($parts[2]), 'SSPOS1.' . $parts[1], $key) ? $payload : null;
}
```

**Node.js** (built-in `crypto`, Node ≥ 16):

```js
const crypto = require('crypto');

// once: make the key pair
const { publicKey, privateKey } = crypto.generateKeyPairSync('ed25519');
const rawPublic = Buffer.from(publicKey.export({ format: 'jwk' }).x, 'base64url');   // send rawPublic.toString('base64url')
const kid = 'k' + crypto.createHash('sha256').update(rawPublic).digest('hex').slice(0, 8);
// store privateKey.export({ format: 'pem', type: 'pkcs8' }) in your secret store

function ssposSign(payload, privateKey /* KeyObject */) {
  const part = Buffer.from(JSON.stringify(payload), 'utf8').toString('base64url');
  const input = 'SSPOS1.' + part;
  return input + '.' + crypto.sign(null, Buffer.from(input, 'ascii'), privateKey).toString('base64url');
}
// from a raw 32-byte seed: crypto.createPrivateKey({ key: Buffer.concat([Buffer.from('302e020100300506032b657004220420', 'hex'), seed]), format: 'der', type: 'pkcs8' })

function ssposVerify(token, publicKeysByKid /* kid -> raw 32-byte Buffer */) {
  const [pfx, part, sig] = token.replace(/\s+/g, '').split('.');
  if (pfx !== 'SSPOS1' || !part || !sig) return null;
  const payload = JSON.parse(Buffer.from(part, 'base64url').toString('utf8'));
  const raw = publicKeysByKid[payload.kid];
  if (!raw) return null;
  const key = crypto.createPublicKey({ key: { kty: 'OKP', crv: 'Ed25519', x: raw.toString('base64url') }, format: 'jwk' });
  return crypto.verify(null, Buffer.from('SSPOS1.' + part, 'ascii'), key, Buffer.from(sig, 'base64url')) ? payload : null;
}
```

**C# / .NET** (package `BouncyCastle.Cryptography`, as the till; or reuse `LicenceTokens.CreateKey` / `Sign`):

```csharp
using System.Buffers.Text;                       // Base64Url, .NET 9+
using System.Text;
using System.Text.Json;
using Org.BouncyCastle.Crypto.Parameters;
using Org.BouncyCastle.Crypto.Signers;

static string Sign(object payload, byte[] privateSeed32)
{
    byte[] json = JsonSerializer.SerializeToUtf8Bytes(payload, new JsonSerializerOptions(JsonSerializerDefaults.Web));
    string part = Base64Url.EncodeToString(json);
    byte[] input = Encoding.ASCII.GetBytes("SSPOS1." + part);
    var signer = new Ed25519Signer();
    signer.Init(true, new Ed25519PrivateKeyParameters(privateSeed32, 0));
    signer.BlockUpdate(input, 0, input.Length);
    return "SSPOS1." + part + "." + Base64Url.EncodeToString(signer.GenerateSignature());
}
// kid: "k" + Convert.ToHexStringLower(SHA256.HashData(publicKey32), 0, 4)
```

### 17.3 Onboarding, end to end

**Updated 2026-09-28 (owner): per-till keys, a key is required, one code for the shop.** The till does **not** call
`devices/activate` (17.4 is kept for reference only — do not build it). The shop types only a **licence key** per till,
plus a **sync key** only if it adds the dashboard later (`docs/web-portal-api/SIMPLE-SETUP.md`).

```
Owner              Portal                                   Main till                        Other tills
  | sign up -------> | Company + Branch + a TRIAL licence     |                                 |
  |                  | key per till (length per customer)     |                                 |
  | <-- e-mail: licence key(s) + installer link               |                                 |
  | install, wizard step 1 "Licence key" (required) --------->|                                 |
  |                  | <------ POST licence/activate ---------| existingIds = the till's OWN ids |
  |                  | ------- token (+ apiKey if dashboard)->| stores token; apiKey → Cloud     |
  |                  |                                        | sync ON (no second code)         |
  |                  | <------ GET sync/hello, push / pull -->| every 30 s                       |
  |                  |                                        | <-- LAN join ---- own key, own licence/activate
  |                  | <------ POST licence/validate daily, EVERY till for itself ---------------|
```

1. **Sign-up (portal).** Create the Company, its first Branch and **one trial licence key per till** (length per
   customer — there is no built-in trial on the till any more). E-mail the key(s) and the installer link.
2. **Wizard (till).** Step 1 "Licence key" — required; Skip is greyed.
3. **`licence/activate`** (17.15.1). **Ids (owner, 2026-09-28): the till always keeps its OWN ids** (ULIDs made at its
   first start) and sends them as `existingIds`; it never adopts yours. Every synced row carries the till's ids.
   - First activation of a new customer's first branch → **adopt**: create/re-key your Company and Branch rows to the
     till's `existingIds.companyId` / `branchId` (your sign-up rows have no data yet), or keep a mapping table.
   - A **second branch** of an existing company → its main till made its own `companyId` → **alias** it to your
     company (store `till companyId → your companyId`, translate rows at your edge, 17.8 rule). Its `branchId` is
     adopted as the new branch.
   - **Bind every key to the branch you issued it for** (you know that from your own records), not by
     `existingIds`; identify a till by `installId` (stable per PC) and record its `registerId`.
   - The **token's** `companyId` / `branchId` are **your** customer ids, the same in every key of the branch — the
     till only compares key to key (two tills of one shop must name the same company/branch).
   - **One code for the dashboard:** when the licence includes the dashboard (`cloud_sync`), put **`apiKey`** (the
     branch's sync key) at the top level of the `licence/activate` / `licence/validate` reply — and `hubUrl` only if
     sync runs on another host than the built-in address. The till stores it and turns Cloud sync on. If you also send
     `companyId` / `branchId` next to it they must be **the till's own ids or blank** (a link naming other ids is
     ignored). `settingsBootstrap` is not read from this reply — settings reach the till by `pull` (v1.4).
4. **More tills.** Each further till of the branch has its **own licence key**, calls `licence/activate` itself and
   joins the main till over the LAN; only the main till syncs. A second **branch** is a new main till with its own keys.
5. **Daily check** (17.5 / 17.15.2) from **every** till for itself. The token's `onlineCheck` sets the rhythm and the 14-day grace.
6. **Lock rules** (17.9): trial over, expired, revoked, suspended, 14 days without a successful check, clock
   tampering, seats exceeded → the till finishes the sale in progress, then shows the lock screen (enter a key /
   Check again; backup and export; the support number — nothing else).

**Local-only path (no portal):** since 2026-09-28 a new install needs a key in the first-run wizard (Skip is
greyed) — a dealer's trial key or a portal key; the built-in 7-day trial only runs out on installs that already
started it. For a bound key the owner reads the **install code** off the licence screen (`XXXX-XXXX`, derived from the install id —
`src/SSPOS.Domain/Licensing/InstallCode.cs`) to the dealer, who makes a `local` token with the licence generator;
the owner pastes it. Since 2026-09-28 the dealer may also make an **open** key (no install code) that binds to the
first till that accepts it, and the key may carry the shop's details for the wizard (17.16). The till needs no
portal to trade; **when a licence server is set and reachable it reports the local key once** to
`licence/redeem` (17.6, 17.16). Later the shop can move to the cloud with `cloud/migrate` (17.8); days left on the
local token carry over.

### 17.4 `POST /api/v1/devices/activate`

| Field | Meaning |
|---|---|
| `activationCode` | From the e-mail (or a transfer code, 17.7). Trimmed and upper-cased by the till. |
| `installId` | ULID made once on this PC at first run (survives updates). Identifies the PC, not the register. |
| `installCode` | `InstallCode.From(installId)` — the code shown on the licence screen. |
| `deviceName`, `appVersion`, `os {name, version, architecture}` | For the portal's device list. |
| `tillClockUtc` | The till's clock, so you can record the skew. |
| `trustedKids` | Kids this till build trusts — sign the returned token with one of them. |
| `registerName` | Name typed in the wizard, or null (portal default "Till 1"). |
| `existingIds` | null on a fresh install. `{companyId, branchId, registerId}` when the till already holds data (a restored backup on a replacement PC). |
| `localLicenceToken` | null, or the local token in use (a local trial being upgraded before any trading). Verify it (17.2); you may honour its remaining days. |

**Portal logic:**
1. Look the code up (hash). Unknown → 404 `activation.code_not_found`; expired → 410 `activation.code_expired`;
   used by **another** `installId` → 409 `activation.code_used`. The **same** `installId` within 24 h → return the
   **same 200 reply** again (the till may have crashed after you committed).
2. Account suspended/revoked → 403 `licence.not_active`.
3. `existingIds` set: must be the code's branch → reuse those ids (the portal already has the data; push resumes from
   the till's own cursor, you dedupe). Different branch → 409 `activation.use_migrate`.
4. The branch already has an active main till (not deactivated) and this is not its transfer code → 409
   `device.branch_already_linked` (with `details.deviceName`, `lastSeenUtc`).
5. Registers in use for the branch ≥ `maxRegisters` → 403 `licence.seat_limit`.
6. Create the register (a new ULID, `isMain: true`) unless reusing one; issue a **new** branch API key (store only its
   hash; revoke older keys of the branch); sign the licence token; mark the code used.

**Reply 200** (`activate-reply.schema.json`, `activate-reply.json`): `companyId`, `branchId`, `registerId`, `isMain`,
`hubUrl` (base URL for every later call), `apiKey` (shown once — you cannot show it again), `licenceToken`,
`licence` (plain summary; the token wins), `settingsBootstrap` (open object: `company`, `branch`, `register`,
`settings` = till setting keys from `src/SSPOS.Domain/Common/SettingKeys.cs` → values; never a secret, never
`sync.hub_api_key`; the till applies what it knows and ignores the rest), `portalTimeUtc`,
`nextCheckAfterSeconds`, `messages`.

**Errors:** 400, 403 (`licence.seat_limit`, `licence.not_active`), 404, 409 (`activation.code_used`,
`device.branch_already_linked`, `activation.use_migrate`), 410, 422 (`licence.*` for a bad `localLicenceToken`),
426, 429 (`activation.too_many_attempts`), 500, 503.

### 17.5 `POST /api/v1/licence/validate` — the daily check and heartbeat

**Auth:** branch key + every section 3 header + `Idempotency-Key`. Sent by the **main till only**, once per
`onlineCheck.intervalHours` (plus up to 60 minutes of random jitter), at start-up when a check is overdue, and when
the owner presses **Check again**. Honour `nextCheckAfterSeconds` from the last reply (e.g. 3600 while revoked).
On a network failure the till retries after 5, 15 and 60 minutes, then hourly, and shows the daily alert
"Your licence has not been validated with the server — connect the internet".

**Request** (`validate-request.schema.json`, `validate-request.json`): `licenceId`, `tokenSha256` (of the token it
holds), `appVersion`, `trustedKids`, `tillClockUtc`, `clockWatermarkUtc` (the latest time it has ever seen),
`lastValidatedAtUtc`, `lastSyncAt`, `lock {locked, reason}` (reason: `trialOver`, `expired`, `revoked`,
`suspended`, `offlineTooLong`, `clockTampering`, `seatsExceeded` — open list), `registers[]` (**every** till of the
branch: `registerId`, `code`, `name`, `isMain`, `appVersion`, `installId`, `deviceName`, `lastSeenUtc`,
`isActive`), `diagnostics` (open object for support: `pendingSyncRows`, `lastSyncError`, `databaseSizeMb`, …).

**Portal logic:**
1. Record the check-in: time, till clock and skew, lock state, diagnostics, app versions. Upsert every register
   (first seen, last seen, version, device); a register you have never seen is a till that joined the main till —
   that is how you learn about secondary tills. The register named by `X-SSPOS-Register-Id` must be reported with
   `isMain: true`, else 403 `device.not_main_till` (a promoted main till reports itself as main — record the change).
2. Work out the **status** (first match wins): `revoked` → `suspended` → `expired` (portal time > `expiresAt`) →
   `seatLimit` (active registers > `maxRegisters`) → `expiring` (≤ 7 days to `expiresAt`) → `active`.
3. **Token:** if `tokenSha256` differs from your current token for this branch, or your current token's kid is not
   in `trustedKids`, or anything in it changed (renewal, extension, trial length, `maxRegisters`, `features`,
   `limits`, `onlineCheck`, names) → sign and return a new token (same `licenceId`). Otherwise `licenceToken: null`.
4. **Seats:** `registers[]` = one `{registerId, seat}` per reported register: `allowed`, `refused` (over the
   limit — keep the main till and the earliest-activated tills, refuse the newest; **never refuse the main till**),
   or `deactivated` (released on the portal — the till forgets its link and locks).
5. Add `messages` (17.9), optional `apiKey` (a replacement key — rotation; keep the old one valid 7 days) and
   `minimumAppVersion` (tills below it show "please update" but keep trading).

**Reply 200** (`validate-reply.schema.json`; samples `validate-reply.trial-expiring.json`, `.renewed.json`,
`.revoked.json`, `.seat-limit.json`): `status`, `licenceToken` (or null = keep yours), `licence`, `registers`,
`apiKey`, `minimumAppVersion`, `portalTimeUtc`, `nextCheckAfterSeconds`, `messages`.

**Errors:** only request/auth/transport problems — 400, 401 (`auth.*`: the day counts as **not validated**; the
14-day grace keeps running), 403 (`auth.wrong_branch`, `device.not_main_till`), 409, 422, 426, 429, 500, 503.

### 17.6 `POST /api/v1/licence/redeem`

Two callers:

- **(a) A linked till:** a key typed or pasted at it (Settings → Licence → Enter key, or the lock screen). Branch key.
- **(b) A till holding a local key — changed 2026-09-28 (owner), this reverses "an unlinked till never calls
  this".** A till with a local (licence generator) key verifies it offline and trades; when its **Licence server**
  (`licence.portal_url`) is set and reachable it **reports** that key here **once per token**, retrying with its
  daily check until a 200 or 409 comes back. It usually has no branch key: **no `Authorization`** — the signed token
  is the credential. Headers as 17.15.1 (`X-SSPOS-Contract`, `X-SSPOS-App-Version`, `X-SSPOS-Install-Id`, the till's
  own `X-SSPOS-Company-Id` / `-Branch-Id` / `-Register-Id`, `Idempotency-Key`). Rules in 17.16.

**Request** (`redeem-request.schema.json`; `redeem-request.portal-key.json`, `redeem-request.local-token.json`,
`redeem-request.local-report.json`): `key` (a portal key in any format you choose, e.g. `SSPK-4F7Q-XM2D-9KTR-B6WN`,
**or** a whole `SSPOS1.` token), `keyType` (`portalKey` | `token`; a courtesy — a report always sends `token`),
`licenceId` + `tokenSha256` (what the till holds; for a report, the reported token's own), `trustedKids`,
`installCode`, `installId` (new 2026-09-28; older tills omit it).

**Local key report (b), portal logic:**
1. Verify the token (17.2 steps 1–4 with our generator public keys; `licence.format`, `licence.bad_signature`,
   `licence.unknown_key`, `licence.unsupported_version` → 422). Do not refuse it for being expired, or for
   `companyId`/`branchId` — record it.
2. **First sighting of this `licenceId`** → record `licenceId → installCode` (+ `installId`, `kid`, `tokenSha256`,
   `issuer`, `companyId`, `branchId`, names, `company`, `maxRegisters`, `features`, `limits`, dates, time) and reply
   200 `result: "recorded"`, `licenceToken: null`, `licence` = the summary (`redeem-reply.local-report.json`).
3. **Same `licenceId`, same `installCode`** (a retry, a renewal token for that till, a reinstall keeping its install
   id) → 200 `recorded` again; store the new `tokenSha256`/dates if they changed.
4. **Same `licenceId`, another `installCode`** → **409 `key.used_on_another_install`**, `details {licenceId,
   installCode (the first one), firstSeenUtc}` (`error.key-used-on-another-install.409.json`). The till stores the
   key's hash as withdrawn and locks after the sale in progress ("This key is already used on another PC — contact
   your dealer"); only a new key unlocks it. The first PC keeps trading.
5. Only 200 and this 409 change anything on the till; anything else (no answer, 5xx, 429, 422) leaves its licence
   as it is and the report is tried again with the next daily check. Renewals for that till are made **for its `installCode`** (a normal bound key, same `licenceId`), so step 3
   applies to them.

**Linked till (a), portal logic:** a **portal key** → unknown 404 `key.not_found`; used by another branch 409 `key.already_redeemed`;
past its redeem-by date 410 `key.expired`; for another company 403 `key.not_for_this_branch`; else bind it to this
branch, apply it (extend / upgrade — your billing rules) and reply `result: "applied"` with the new token. A
**token** → verify (17.2; `licence.format`, `licence.unknown_key`, `licence.bad_signature`,
`licence.unsupported_version`, `licence.expired`, `licence.wrong_shop`, `licence.wrong_branch` → 422); a valid local
token is **recorded** for your records (`result: "recorded"`, `licenceToken: null` — the till keeps the token it
verified itself), or refused by policy (403 `key.not_allowed`), or turned into a portal token (`applied`). Which one
is an owner decision (17.14: recorded). The `licenceId → installCode` rule of (b) applies here too.

**Reply 200** (`redeem-reply.schema.json`; `redeem-reply.applied.json`, `redeem-reply.recorded.json`,
`redeem-reply.local-report.json`): `result`, `status`, `licenceToken`, `licence`, `portalTimeUtc`,
`nextCheckAfterSeconds`, `messages`.

**Errors:** as the 17.12 table for `redeem`, plus **409 `key.used_on_another_install`** (local key from a second
install).

### 17.7 `POST /api/v1/devices/deactivate` — free a seat, transfer a till

**Auth:** branch key, main till only. Idempotent by `registerId` (deactivating twice returns the same reply).

**Request** (`deactivate-request.schema.json`): `registerId`, `installId`, `reason` (`transfer`, `replaced`,
`removed`, `closed`, `other` — open list), `note`.

- **A second till** (`deactivate-request.json` → `deactivate-reply.json`): the seat is freed (`seat: "deactivated"`,
  `seatsInUse`, `maxRegisters`); the main till stops letting that till join.
- **The main till itself** (`deactivate-request.main-till.json` → `deactivate-reply.main-till.json`):
  `apiKeyRevoked: true` (the branch key stops working **now**) and a one-time `transferCode` (+ `transferCodeExpiresAt`,
  suggested 7 days; also show it on the portal and e-mail it). The old till forgets its key and token and locks
  (backup/export still work).

**Transfer to a new PC:** old PC → Backup → Deactivate → note the transfer code. New PC → install → restore the
backup → wizard "Link to your account" → transfer code → `activate` with `existingIds` (17.4 step 3) → same
`registerId`, new key, token; sync resumes from the till's own cursor. **Old PC dead?** The admin (or owner) presses
Deactivate on the portal → the same transfer code; a later `validate` from the dead PC, if it ever comes back,
gets `auth.key_revoked`.

**Errors:** 400, 401, 403 (`device.not_main_till`), 404 `device.not_found`, 409, 422, 426, 429, 500, 503.

### 17.8 `POST /api/v1/cloud/migrate` — a local shop moves to the cloud

The shop has traded on a local licence (or the built-in trial) with ids the till made itself. It signs up on the
portal, gets an activation code and chooses **"Move my shop to the cloud"**. Rule: **in v1 the till never re-keys
a row** (its sales are immutable — `specs/invariants.md` rule 5), so the portal adapts, not the till.

**Auth:** none (the activation code is the credential), like `activate`; same rate limits; idempotent per
`(activationCode, installId)` — a retry returns the same reply and the same `uploadId`, with `resumeFromSeq` = what
you already hold.

**Request** (`migrate-request.schema.json`, `migrate-request.json`): the `activate` device fields, plus
`localLicenceToken` (or null on the built-in trial) and `localTrialEndsAt` (built-in trial only, unsigned),
`company {id, name}`, `branch {id, name, code}`, `registers[]`, and `data {totalRows, rowCounts{entity→n},
firstSaleAtUtc, lastSaleAtUtc, snapshotChangeLogSeq}`.

**Portal logic:**
1. Code checks as `activate` (17.4 step 1–2). `company.id`/`branch.id` already belong to another account → 409
   `migrate.already_migrated`.
2. Verify `localLicenceToken` (17.2) with our generator public keys and compute `carriedOverDays` (the days left on
   it); the cloud licence's `expiresAt` = at least the local `expiresAt` (owner rule: days carry over).
3. **Ids:** the account's sign-up Branch is a placeholder with no data → **adopt**: re-key the placeholder to the
   till's `branch.id`. Company: a new account with no other branches → **adopt** the till's `company.id`; an
   existing company that already has branches under its own id → **alias**: keep your company id, record the till's
   as an alias for this branch, and translate at your edge (rows arriving with the alias are stored under your id;
   rows you send this branch carry the alias). Registers are always adopted. `idMapping` reports what you did;
   `companyId`/`branchId` in the reply are always the ids the till keeps (the ones it sent).
4. Issue the branch key and token (`source: "portal"`), open an **upload**.

**Reply 200** (`migrate-reply.schema.json`; `migrate-reply.adopted.json`, `migrate-reply.aliased.json`):
`companyId`, `branchId`, `idMapping {company, branch}` (each `{localId, portalId, action: adopted|aliased}`),
`registers[]` (seats), `hubUrl`, `apiKey`, `licenceToken`, `licence`, `carriedOverDays`,
`upload {uploadId, mode: "initial", maxRowsPerBatch, resumeFromSeq}`, `settingsBootstrap` (usually null — the till
already has its settings), `portalTimeUtc`, `nextCheckAfterSeconds`, `messages`.

**Then the initial upload — through the normal push endpoint:**

- `POST /api/v1/sync/push` with the normal headers plus `X-SSPOS-Sync-Mode: initial` and `X-SSPOS-Upload-Id:
  <uploadId>`. Body = the section 5 envelope, gzip, ≤ `maxRowsPerBatch` rows (≤ 5000), **no** 5-batches-per-run cap
  (the upload runs continuously in the background; the shop keeps trading). Sample: `licensing/samples/push-request.initial.json`.
- Each row is the row's **current state**: `op: "I"`, `version` = its `rowVersion`, the full payload. `seq` is the
  **upload's own sequence** 1…N, strictly increasing — not the ChangeLog seq; key initial rows by `(uploadId, seq)`
  (and, as always, `(entity, entityId, version)`). Reply `acknowledgedSeq` / `accepted` exactly as section 7.
- **Order:** tier 1 company-wide master data (`VatRate`, `Unit`, `Department`, `Category`, `Supplier`, `Product`,
  `ProductBarcode`, `ProductAlias`, `ProductUnit`, `ProductSupplier`, `PaymentType`, `Reason`, `Role`, `User`,
  `Customer`, `Promotion*`, `Account`, `TaxRule`, other hub-owned entities of section 10); tier 2 branch set-up
  (`Register`, `BranchProduct`, other branch rows); tier 3 documents (`Shift`, `Sale`, `SaleLine`, `SalePayment`,
  `SaleVat`, `StockMovement`, `CustomerOrder`, `ZReport`, `JournalEntry`/`Line`, `AuditLog`, everything else).
  Inside a tier: entity, then `createdAt`, then `id`. **Do not enforce foreign keys on ingest** — store first,
  resolve later (true for every push).
- Resume: after a crash the till re-plans the same order and resends after its last `acknowledgedSeq` (or after the
  migrate reply's `resumeFromSeq`). Rows changed during the upload arrive with a higher `version`; keep the highest.
- While the upload is open the till does **not** run the normal delta push or pull. Changes made meanwhile wait in
  its ChangeLog.
- Finally `POST /api/v1/cloud/migrate/complete` (`migrate-complete-request.json`: `uploadId`, `totalRows`,
  `highestSeq`, `rowCounts`, `snapshotChangeLogSeq`). Compare counts; reply `status: "complete"` (set this branch's
  push cursor to `pushResumesAfterSeq` = `snapshotChangeLogSeq`) or `"incomplete"` with `missing[]` and
  `resumeFromSeq` (the till resends from there and calls complete again). After `complete` the till resumes
  normal push from `snapshotChangeLogSeq + 1` and pulls from `since = 0`; do not echo back rows you just received
  unchanged (if you do, the till skips them as already seen).
- Errors: 404 `migrate.upload_not_found` (the till calls `migrate` again), 409 `migrate.upload_closed` (the till
  stops uploading and resumes normal push).

### 17.9 What the till does with each answer

| `status` | Till |
|---|---|
| `active` | Trades. Stores the token if one came. |
| `expiring` | Trades; banner "Your licence ends on …" daily. (The till also warns by itself from 7 days before `expiresAt`.) |
| `expired`, `revoked`, `suspended` | Finishes the sale in progress, then the lock screen. It remembers the verdict against the token's hash, so a restart does not unlock; only a **new** token or a later `active`/`expiring` answer unlocks. |
| `seatLimit` | The main till trades; every register marked `refused` locks (the main till tells it over the LAN). |
| unknown value | Treated as **not active** (lock after the sale) — owner rule, `specs/licensing.md` section 4. So: **never send a status value to a till version that does not know it** (check `X-SSPOS-App-Version`; new values are announced in this document with the first till version that understands them). |

| `seat` | Till |
|---|---|
| `allowed` | Trades. |
| `refused` | Locks with "Too many tills for this licence". |
| `deactivated` | Forgets its link (key, token) and locks; backup/export still work. |
| unknown | As `refused`. |

**Other till rules the portal should know:** 14 days (`graceDays`) without a successful `validate` → lock, measured
on the portal's time from the last success; the clock guard locks when the PC clock goes back beyond tolerance
until corrected or a successful `validate` confirms the time; a paid feature not in the token shows **greyed**
("This is a paid feature — contact your dealer"), never hidden — adding a branch without `multi_branch`, or past
`limits.branches`, is greyed the same way; trial length can never be changed on the till — only a new signed token
changes it; a local key reported from a second PC (409 `key.used_on_another_install`) locks that PC (17.16).

**Messages** (`messages[]`, display only — never change what the till allows): `id` (the till shows each id at most
once a day and remembers dismissals), `level` (`info` | `warning` | `critical`; unknown = `info`), `title`, `text`
(en-GB, ≤ 500), `showFromUtc`, `showUntilUtc`, `dismissible`, `link {label, url}` (https; shown as text / QR — a
till has no browser).

### 17.10 Portal requirements checklist (what your admin and API must do)

**Accounts and sign-up**
- [ ] Sign-up creates Company + first Branch + trial licence (length: global default 7 days, overridable per customer).
- [ ] E-mail with activation code + installer link; resend / regenerate a code; codes single use, hashed, expiring (30 days suggested).
- [ ] Add a branch → its own activation code. Capture shop details for `settingsBootstrap`.
- [ ] **Customer form (2026-09-28, 17.16)** — everything a key carries: business name, branch name, the `company`
  block (business type from the `BusinessType` list, address, town, postcode, phone, e-mail, VAT number, owner's
  name, receipt footer), **tills** (`maxRegisters`), **branches** (`limits.branches`), **multi-branch** on/off
  (feature `multi_branch`), other **features** (catalogue), **length** in days / months / years (→ `validFrom`,
  `expiresAt`), **trial / full** (`kind`). Every till key of the customer's branch is signed from this form with the
  same `companyId`/`branchId`.

**Licences** (every change = a new token with the same `licenceId`, delivered at the next `validate`)
- [ ] Set / change trial length per customer; extend a trial; convert trial → full.
- [ ] Set / change `expiresAt`, `maxRegisters`, `features` (from a managed catalogue of names — open list), `limits`, `onlineCheck` (interval, grace) per customer.
- [ ] Suspend / reinstate; revoke (permanent). Free-text `notes`.
- [ ] Issue portal licence keys (duration, seats, features, redeem-by date, single use) and see who redeemed them.
- [ ] Token history per licence: every token issued (kid, hash, issued at, fields) — support looks tokens up by hash.
- [ ] Record local tokens reported by `redeem` / `migrate` (issuer, kid, install code, expiry).
- [ ] Local key register (17.16): `licenceId → installCode` (+ install id, first seen, last reported token hash,
  company/branch ids and names); every 409 `key.used_on_another_install` sent (which install code tried, when) for
  support; local tills counted per `branchId` against the key's `maxRegisters` (shown, not refused).
- [ ] Tills per branch ≤ `maxRegisters`, branches per company ≤ `limits.branches` (and > 1 only with `multi_branch`)
  — enforced when issuing keys and adding branches, shown as "in use / allowed".

**Devices**
- [ ] Tills per branch: register id, name, code, main or not, device name, install id / install code, app version, first activated, last seen, **last successful check-in**, clock skew, lock state and reason, pending sync rows, last sync.
- [ ] Seats in use vs `maxRegisters`; deactivate a till (frees the seat; for the main till: revoke the key and issue a transfer code).
- [ ] Activation / deactivation history.

**Monitoring and messages**
- [ ] Alerts: a branch with no check-in for 2 days (well before the 14-day lock), licences expiring within 7 days, tills below `minimumAppVersion`, clock skew > 5 minutes, sync errors, locked tills.
- [ ] Compose `messages` for one branch, one customer or everyone (level, text, link, show window).

**Keys and security**
- [ ] Generate the Ed25519 signing key in a secret store; hand us the public key + kid; support rotation (17.2).
- [ ] Hold our generator public keys (verify only). Sign returned tokens only with a kid in the till's `trustedKids`.
- [ ] Store API keys and activation codes **hashed**; show an API key once; rotate keys through `validate.apiKey`.
- [ ] Idempotency store (17.11), rate limits (17.12), HTTPS only, audit log of every admin action (who, when, before → after).

**Migration**
- [ ] Adopt / alias ids (17.8), accept the initial upload at full speed, compare counts on `complete`, show upload progress in the admin.

**Search** by business name, branch, install code, install id, licence id, token hash, activation code, licence key.

### 17.11 Extensibility rules (built to grow)

1. **Versioning.** The path's `/api/v1` is the contract **major**; the till sends it in `X-SSPOS-Contract: 1` and
   you echo `X-SSPOS-Contract` in every reply. Additive changes — a new endpoint, a new optional field, a new
   feature name or limit, a new error code, a new enum value introduced under rule 3 — **never** change the major.
   A breaking change is served as `/api/v2/...` **alongside** `/api/v1` until `validate` shows no till still on a
   v1-only version (and at least 12 months); a till moves to v2 in the release that speaks it. An unsupported major
   → 409 `contract.unsupported` with `details.supportedContracts`. This document's revision (1.2) and
   `openapi.yaml` `info.version` track additive edits.
2. **Unknown fields are ignored both ways.** Neither side rejects a request or reply because of a field it does not
   know; our schemas never say `additionalProperties: false`. Absent, `null` and (for strings) `""` mean the same.
   Send `null` or omit — both are fine.
3. **Enums are camelCase strings**, never numbers (section 6). Replies you send use only the values listed for this
   contract (the reply schemas carry `enum`). The till's handling of an unknown value is fixed and safe: state
   values → the **safe reading** (licence status → not active; seat → refused; `idMapping.action` → stop the
   migration and show the messages; `redeem.result` → keep the current licence; `complete.status` → incomplete);
   display values → neutral (`message.level` → info). Values the till **sends** (`lock.reason`, `deactivate.reason`,
   `keyType`) are open: store them as-is and treat an unknown one as "other".
4. **Open objects** carry new things without a contract change: token `features` and `limits`,
   `settingsBootstrap` (and its `settings` map), validate `diagnostics`, error `details`. Unknown keys are ignored.
5. **Idempotency.** Every POST in section 17 carries `Idempotency-Key` (a ULID or UUID, new per logical request,
   reused on a retry). Store `(key, endpoint, caller, body hash) → reply` for at least 24 hours: a repeat with the
   same body returns the **same status and body**; a different body → 422 `request.idempotency_mismatch`; the first
   still running → 409 `request.in_progress` + `Retry-After`. Endpoints are also idempotent by nature: activate and
   migrate per `(code, installId)`, deactivate per `registerId`, redeem per `(key, branch)`, complete per `uploadId`,
   push per `(entity, entityId, version)` (the key is optional on push).
6. **Paging.** Sync pull pages by `since` / `max` / `hasMore` (section 8); the initial upload by
   `maxRowsPerBatch`. Any future list endpoint uses `?cursor=&limit=` → `{ "items": [...], "nextCursor": "…" | null }`.
7. **Time** is UTC ISO-8601 with `Z` everywhere (section 6). Every licence reply carries `portalTimeUtc`; also send
   the HTTP `Date` header. The till trusts the portal's time over its own clock.
8. **Money** follows section 6 (pounds as JSON numbers, 2 dp, half away from zero, parse as decimal). No section 17
   endpoint carries money today; any future billing field follows section 6 and adds `"currency": "GBP"`.
9. **Ids** are ULIDs (section 6). Ids you make (`licenceId`, a new `registerId`, `uploadId`, message ids) must be
   ULIDs too; you never re-key a till's id (section 2.1).
10. **Error envelope** = section 9 + optional `details`; codes are `area.snake_case`; a new code may appear at any
    time — the till acts on the HTTP status (section 9 table) when it does not know the code.
11. **Rate limits** → 429 with `Retry-After` (seconds) and `retryAfterSeconds` (17.12). `RateLimit-*` headers are
    welcome; the till ignores them.
12. **Transport security.** HTTPS only (TLS 1.2+, 1.3 preferred) with a certificate from a public CA; HSTS on. The
    till refuses `http://` and invalid certificates. No certificate pinning in v1, so you can renew certificates
    freely. Never put a key, code or token in a URL or a query string.
13. **Compression.** Accept `Content-Encoding: gzip` on any POST (the till gzips push; others may be gzip later) and
    plain JSON too (test tools). Gzip replies when the till sends `Accept-Encoding: gzip`.

### 17.15 Per-till licensing — one e-mailed key per till (owner, 2026-09-26) — **supersedes the branch model for licences**

**Why:** the owner decided that **every till has its own licence**. A shop receives a **licence key by e-mail** (a
trial key at sign-up — since 2026-09-28 a new install cannot be set up without a key and there is **no built-in
trial**; installs that already started the old built-in trial keep it until it ends). The key is typed in the
first-run wizard (or Settings → Licence), checked **online**, and from then
on belongs to **that PC** (its `installId`, the "system id"). The same key typed on another PC is refused. The portal
admin can release a key and issue a new one at any time — the till never needs to know how.

**What changes against 17.1–17.9** (everything else in §17 stands — the token format, signing, kids, error envelope,
compatibility rules):

| Before (branch model) | Now (per-till) |
|---|---|
| One licence per branch, `maxRegisters` seats, counted by the main till | One licence **per till**; the portal counts the branch's activated keys. **Changed 2026-09-28:** `maxRegisters` in each till's token = the tills allowed in the **branch** (the same in every key of the branch — it was 1), and the portal refuses a till past it (17.16) |
| Only the main till calls the portal (`devices/activate`, `licence/validate`) | **Every** till with a portal licence calls `licence/activate` once and `licence/validate` daily, **for itself** |
| Portal token bound by `companyId`/`branchId` | Portal token bound by **`installCode`** (as local keys already are); the till no longer checks the branch for such a token |
| Seats: `registers[]` / `seat` / `seatLimit` | Not used for per-till licences (keep them for a branch-model customer if you ever need one) |
| Activation code = branch link + sync key | **No activation code (2026-09-28).** The licence key is the only code. Cloud sync comes either with the licence (`apiKey` in the `licence/activate` / `validate` reply, 17.3 step 3) or from a **sync key** the owner types on the main till (`cloud/migrate` + `sync/*`, `SIMPLE-SETUP.md`). `devices/activate` is not called by the till |

**Local (dealer) keys are unchanged:** the owner's key generator still makes offline keys bound to an install code
(no internet; for shops without internet). Such a shop can move to the cloud later: the owner gives it a portal key
and a cloud link; its history goes up with `cloud/migrate` (17.8).

#### 17.15.1 `POST /api/v1/licence/activate` — NEW

**Auth:** none — the **licence key is the credential** (store it hashed; ≥ 60 bits random; rate-limit wrong keys:
5 per install per 15 minutes → 429 `activation.too_many_attempts`). **Headers:** `X-SSPOS-Contract: 1`,
`X-SSPOS-App-Version`, `X-SSPOS-Install-Id`, `X-SSPOS-Company-Id`, `X-SSPOS-Branch-Id`, `X-SSPOS-Register-Id`
(the till's own ids), `Idempotency-Key`. A till that also has a branch API key sends `Authorization: Bearer …` —
optional here.

**Request** (`licence-activate-request.schema.json`, `licence-activate-request.json`): `licenceKey` (upper-cased,
spaces removed — any layout you choose, e.g. `SSPK-4F7Q-XM2D-9KTR-B6WN`), `installId`, `installCode`, `deviceName`,
`appVersion`, `os`, `tillClockUtc`, `trustedKids`, `approverKids`, `existingIds {companyId, branchId, registerId}`
(the till's own ids — it **never re-keys** its data; adopt or alias them as in 17.3 step 3).

**Portal logic:**
1. Look the key up (hash). Unknown → 404 `key.not_found`; past its activate-by date or withdrawn before use → 410
   `key.expired`; the account is suspended/revoked → 403 `licence.not_active`.
2. The key is **not yet bound** → bind it to this `installId` (+ `installCode`, `deviceName`, `existingIds`, time).
3. Bound to **the same `installId`** → answer 200 again with a valid token (a retry, or a reinstall that kept its data).
4. Bound to **another `installId`** → 409 `key.already_used`, `details {deviceName, installCode, activatedAtUtc}`,
   and a `message` naming the other PC. Only the admin can move it (17.15.3).
4a. Not yet bound, but the key's branch already has `maxRegisters` keys bound to other installs → 403
   `licence.seat_limit` (`details {maxRegisters, registersInUse}`, `error.seat-limit.403.json`). Normally unreachable: the admin cannot issue more
   till keys than the branch's tills (17.16).
5. Sign a token for this till. It **must** carry (2026-09-28):
   - `source: "portal"`, **`installCode` = the request's**, `kind` (`trial` / `full`);
   - the shop: `companyId`, `branchId` (the **same** in every till key of the branch — the customer's, not the
     till's `existingIds`), `businessName`, `branchName` and the **`company` block** (17.2) from the customer form;
   - **`maxRegisters` = tills allowed in the branch**, **`features`** as sold (with **`multi_branch`** when the
     company may run more than one branch), **`limits.branches`** (omit or 1 for a single-branch customer);
   - **`validFrom` / `expiresAt`** = the length the admin chose (days, months, years; trial or full);
   - `onlineCheck {required: true, intervalHours: 24, graceDays: 14}`.
   Sample payload: `licence-token.payload.per-till.json`.

**Reply 200** (`licence-activate-reply.schema.json`, `licence-activate-reply.json`): `status`, `licenceToken`,
`licence`, `portalTimeUtc`, `nextCheckAfterSeconds`, `messages`. **`licence`** (the plain summary) lists the same
fields: `licenceId`, `kind`, `source`, `companyId`, `branchId`, `businessName`, `branchName`, `installCode`,
`validFrom`, `expiresAt`, `maxRegisters`, `features`, `limits` (with `branches`) and `company` (the schema still
requires only `licenceId`, `kind`, `expiresAt`, `maxRegisters`, so an older reply stays valid); the signed token
always wins. **Optional (2026-09-28):** `apiKey` (the branch's sync key, when the licence includes the dashboard) and
`hubUrl` (only if sync is on another host) — the till stores them and turns Cloud sync on (17.3 step 3). The sample
token is signed with the documentation key `k13799fa4` from `licence-token.worked-example.json` — your signer must
verify it.

**Errors:** 400 `request.invalid`, 403 `licence.not_active` / `licence.seat_limit`, 404 `key.not_found`, 409 `key.already_used`,
410 `key.expired`, 426 `app.update_required`, 429 `activation.too_many_attempts` (a wrong-key limit — the till shows
it), 500/503/other 429 (the till says "could not reach the licence server" and changes nothing).

**What the till does:** verifies the token (signature, trusted `kid`, `installCode` = its own, dates), stores it,
records the check-in with `portalTimeUtc`, writes an audit row. A refused key changes nothing on the till.

#### 17.15.2 `POST /api/v1/licence/validate` — per till

Same endpoint and reply as 17.5, but **each till sends it for itself**, once per `onlineCheck.intervalHours`
(the till's timer runs every 15 minutes and sends when due), at start-up when due, and on **Check again**.
**No branch key is required** — identify the licence by `licenceId` + `tokenSha256` + `installId` (only answer
for a licence bound to that `installId`; anything else → 404 `key.not_found`).

**Request** (`validate-request.schema.json`, sample `validate-request.per-till.json`): `installId`,
`installCode`, `licenceId`, `tokenSha256`, `deviceName`, `appVersion`, `os`, `trustedKids`, `tillClockUtc`,
`clockWatermarkUtc`, `lastValidatedAtUtc`, `lock {locked, reason}`. `registers[]` and `lastSyncAt` are absent.

**Reply 200** (samples `validate-reply.per-till.json`, `validate-reply.released.json`): `status`,
`licenceToken` (a new token when anything changed — renewal, extension, features — else null), `licence`,
`portalTimeUtc`, `nextCheckAfterSeconds`, `messages`.

**Status → till** (17.9 rules, per till): `active`, `expiring` → trades (and a later `active` lifts an earlier
withdrawal); `expired`, `revoked`, `suspended`, **`released`** (new: the key was released from this PC on the
portal) and **any value the till does not know** → the till withdraws the token it holds (remembered across
restarts) and locks after the sale in progress; only a new key or a later `active` unlocks. No reply / 5xx / 429 →
nothing changes; after **14 days** without a successful check the till locks ("connect the internet").
The till takes `portalTimeUtc` as the true time on every successful call (clears its clock guard).

### 17.17 Signer certificates — your key needs no till release (owner, 2026-09-28)

Your signing key is **approved** by the owner's key generator instead of being compiled into the till, so a new
key, a rotation or a second server never waits for a till update.

**Format** (like a token, a different prefix):

```
SSPOSCERT1.<base64url(payload JSON)>.<base64url(Ed25519 signature by the APPROVER over ASCII "SSPOSCERT1." + payload part)>
```

| Payload field | Rule |
|---|---|
| `v` | `1`. |
| `kid` | Your key id = `"k"` + first 8 hex of SHA-256(your raw 32-byte public key). Must equal the `kid` of every token it rides in. |
| `publicKey` | Your raw 32-byte Ed25519 public key, base64url (43 characters). |
| `name` | Who the key belongs to, e.g. `SSPOS Portal`. |
| `issuedAt` | When it was approved (UTC). |
| `expiresAt` | Optional (UTC). A token whose `issuedAt` is after it is refused; tokens made before it keep working. Absent = no end date. |
| `approvedBy` | The approver's kid — one of the till's `approverKids`. |

**Hand-over, once:**
1. Generate your pair on the server (17.2). Send us `public-key-handover.json` (public key only).
2. The owner pastes it into the key generator → **Approve a signer** → sends you the certificate string (~300 characters).
3. Store it next to your key (it is **not secret**) and put it, unchanged, in the `signerCert` field of **every**
   token you sign. Nothing else changes in the token or its signature.

**What the till checks** (`src/SSPOS.Infrastructure/Licensing/SignerCertificates.cs`, `LicenceTokens.Read`): the
token's `kid` is not built in → `signerCert` starts with `SSPOSCERT1.` → `approvedBy` is in the till's approver list
**and** built in → the approver's signature verifies → SHA-256 kid of `publicKey` equals the certificate's `kid`
equals the token's `kid` → token `issuedAt` ≤ `expiresAt` (if set) → the token's own signature verifies with
`publicKey`. Any failure → `licence.bad_signer_certificate` (the till says "made by a licence server SSPOS has not
approved"). One level only: a certified key cannot approve another key. If an approver is withdrawn
(`RetiredAfter`), the keys it approved stop at the same cut-off.

**Requests tell you what the till accepts:** `activate`, `validate`, `redeem` and `migrate` carry
`approverKids` (string[]) beside `trustedKids`. Today every till has one approver (the owner's generator).

**Worked example** (byte for byte, documentation keys): `licensing/samples/signer-certificate.worked-example.json`
— the certificate, each intermediate string, and a portal token carrying it that a till trusting only the
approver accepts. Your signer can be tested against it.

## 18. The portal product — panels, roles, screens (owner's brief, 2026-09-26)

This section says **what the portal must let people do**; sections 1–17 say how it talks to the till.
Build it so that the owner can run every shop from one screen and a shop owner can run their own
business from theirs — and so that anything changed on the portal reaches the tills by itself.

### 18.1 Words — portal ↔ till

| Portal says | Till entity | Notes |
|---|---|---|
| **Business** | `Company` | One customer account. Owns its products, prices, users, customers, promotions (company-wide, §2.4). |
| **Shop** | `Branch` | A business has **one or many** shops. Each shop has its own licence, activation code, API key, stock and sales. |
| **Till** | `Register` | A shop has **one or many** tills. The first to activate is the shop's **main till**; the rest join it on the shop LAN (§2.2, §17.3). |

Ids: the portal creates the business, shop and first till ids (returned by `activate`, §17.4) as ULIDs;
rows made on the till keep the till's ids. Never re-key (§2.1).

### 18.2 Two panels, four roles

| Role | Panel | Sees | Can change |
|---|---|---|---|
| **Super admin** (SSPOS owner) | Admin panel | Every business, shop, till | Everything below, plus dealers and plans |
| **Dealer** (optional) | Admin panel | Only the businesses they sold | Same as super admin for those businesses; cannot create dealers |
| **Business owner** | Business panel (own login) | Only their business: all its shops and tills | Their master data (products, prices, promotions, customers, staff, settings); cannot change the licence |
| **Shop manager** (optional) | Business panel | One shop | That shop's data only (stock, shop prices, shop settings) |

Every query is filtered by `companyId` (and `branchId` for a shop manager) on the server — a business
owner must never see another business, whatever the URL.

### 18.3 Admin panel — what it must do

**Per-till model (updated 2026-09-28).** One licence key per till; no activation codes; no seats.

1. **Businesses:** list with search; add (name, owner name, **owner e-mail**, phone, VAT number,
   address); suspend / reactivate.
2. **Shops under a business:** add any number (name, address, shop code e.g. `LDS` — shown on
   receipts); per shop: **tills allowed** (`maxRegisters`, e.g. 2), licence length (trial / months / years,
   start/end), paid features (17.2 list), dashboard on/off (`cloud_sync`).
3. **Licence keys:** per shop, **issue one key per till** up to tills allowed (a trial key at sign-up). "Send
   setup e-mail" → the owner receives the key(s), the installer link and two steps (install → type the key).
   If the shop has the dashboard, its **sync key** is shown in the Business panel ("Connect the dashboard") —
   or simply returned with the licence (17.3 step 3), so the owner types nothing else. Template in 18.7.
4. **Tills under a shop** (one row per issued key): key (masked), status (not activated / active / released /
   revoked), bound PC (`deviceName`, `installCode`, `installId`), `registerId`, app version, **last check-in**,
   online/offline. Actions: **release the key** (the PC locks at its next check; the key can then be activated on
   another PC — §17.15.3), re-issue a new key (the old one stops), revoke.
5. **Licence changes take effect by themselves:** raise tills allowed 2 → 3 (issue one more key), extend a
   trial 7 → 30 days, add a feature, renew, suspend — the portal signs a new token for **each till** and every
   till picks it up at its own next `licence/validate` (daily, or at once on "Check again").
6. **Dashboard** (18.5) across all businesses, and per business / per shop.
7. **Audit:** who changed which licence or record, when (keep your own log).

### 18.4 Business panel — the shop owner's own login

1. **Dashboard** for their business: today / this week / this month, per shop and in total (18.5).
2. **Products and prices:** add / edit products, barcodes, departments, categories, VAT, prices, promotions,
   coupons. A **price for one shop only** is planned: today `BranchProduct.priceOverride` is till-owned (§16),
   so it needs its own portal-owned row first — build the screen, we add the row on the till side.
3. **Customers, staff (users, roles, PINs), suppliers, payment types, reasons.**
4. **Shops and tills:** read the licence (tills allowed, end date, features), see each till's status;
   "Ask for more tills" sends a request to the admin (they cannot raise it themselves).
5. **Reports:** sales, refunds, VAT, stock, Z reports — read-only (they come from the tills).
6. **Settings** for a shop (receipt text, opening hours…) — see 18.6 for what reaches the till today.

### 18.5 Dashboards — where the numbers come from

Everything a till sells arrives by `push` within about **30 seconds** while the shop is online (and
catches up by itself after an outage). Build your own reporting tables as rows arrive; do not query the
raw change log for every screen.

| Figure | Built from |
|---|---|
| Sales total, count, average basket — per business / shop / till / day | `Sale` (status `completed`; refunds are their own `Sale` rows with type `refund` — subtract them), or the ready daily totals `SalesDaily` |
| Takings by payment type (cash, card…) | `SalePayment`, or `TenderDaily` |
| Top products, department sales | `SaleLine` |
| VAT | `SaleVat` |
| End-of-day / shift figures | `ZReport`, `Shift` |
| Stock on hand, low stock | `BranchProduct`, `StockMovement` |
| Tills online / offline, versions | the daily `licence/validate` call (§17.5) and the last `push` time per shop |

Rules: the shop's **trading day** is the local day in the shop's time zone (UK: Europe/London), not the UTC
date; money is decimal pounds (§6); a sale belongs to the till in its `registerId` and the shop in its
`branchId`. Show "last updated N minutes ago" per shop so an offline shop is obvious.

### 18.6 What a portal change does on the till, and how fast

| Changed on the portal | Reaches the tills | How |
|---|---|---|
| Products, barcodes, prices, departments, categories, VAT rates, promotions, coupons, customers, users/roles, suppliers, payment types, units, reasons (§10 "Portal") | ≈ 30 seconds, online | `pull` by the shop's main till, which serves its other tills over the LAN |
| A price for one shop only | **not yet** — planned | needs a portal-owned per-branch price row; today `BranchProduct.priceOverride` is till-owned (§16) |
| Licence: tills allowed, dates, features, suspend | next daily check, or at once on "Check now" | new token in the `licence/validate` reply (§17.5) |
| Shop settings (receipt text, hours…) | **not yet** — see 18.10 | `Setting` rows are portal-owned, but the till does not yet apply them from `pull` (§16) |
| Sales, refunds, shifts, Z reports, stock movements | never — read-only on the portal | till-owned (§10); correct a sale on the till, never on the portal |

While a shop is offline, portal changes wait and arrive the moment it reconnects. If the shop edited the
same record before it synced, the till shows a conflict for a person to settle (§8).

### 18.7 E-mails the portal sends

- **Setup (per shop):** business and shop name; the **activation code** (large, copyable); the installer
  link; three steps; valid for 30 days; the support number.
- **Trial ending** (3 days and 1 day before), **licence renewed / extended**, **till limit changed**,
  **licence suspended**, **a till has not checked in for 3 days** (to the owner, and to the admin).

### 18.8 Make it easy to plug in (and to extend later)

- Store the till's `id` as your primary key; upsert by `(entity, id)` and keep the highest `version`.
- Keep the full `payload` JSON beside your typed columns: a field the till adds tomorrow is then already
  in your database, and you add a column when you need it — no data lost meanwhile.
- Ignore fields and entity names you do not know (§17.11); never fail a whole batch for one row
  (reply per row, §7).
- Put company/shop filters in one place in your API layer (18.2), not in every screen.
- New feature later = a new entity or field on the till side, a new sample/schema in this package, and
  your screen — the transport, auth and licence flow do not change.

### 18.9 Never slow a shop down

Syncing must never make a till slower at the counter. The till keeps its own rules for this
(`specs/performance.md`, "Cloud sync never slows the till": background only, thin write slices, no
catalogue reloads, throttled big jobs). The portal's part:

- **Answer fast.** `push` and `pull` should reply within 2 seconds; do heavy work (reports, e-mails,
  re-indexing) after you reply, in your own background jobs.
- **Page, don't flood.** Honour `max` on pull; never send more rows than asked. A bulk change on the
  portal (e.g. 5,000 new prices) is fine — it simply goes down in pages and the till applies it in
  slices.
- **Only send what changed.** Bump `version` only for rows that really changed; re-sending the whole
  catalogue on every edit costs every shop time and data.
- **No big blobs in sync.** Product images and files are URLs the till fetches on demand, never inline
  base64 in a sync row.
- **Say when you are busy.** Under load reply 429/503 with `Retry-After`; the till backs off
  (1 → 2 → 5 → 15 min) instead of retrying in a loop.
- **Big history uploads** (a shop moving to the cloud, or catching up after a long outage) arrive in
  batches over time; accept them in order and don't time the shop out.

### 18.10 Till side — what is ready and what is still being built

Ready in the till (2026-09-28): the contract, the change log, the HTTPS client (hello / push / pull), applying
pulled rows, `licence/activate`, the daily `licence/validate`, `licence/redeem`, `devices/deactivate`,
`cloud/migrate`, the offline licence check and signer certificates (17.17). **Still being built:** applying pulled
settings and role permissions, and the items in section 16 "Still open" and `UPCOMING-CHANGES.md`. Test against the
samples and a Postman mock server first; we will run end-to-end together once your server is up.

## 19. Synced once, never twice, never backwards (owner, 2026-09-26)

Three promises, kept by **both** sides. Section 7 (push) and section 8 (pull) already carry the
mechanics; this section is the rulebook and the test list. Nothing here is decided by clock time (`at`) —
only by `seq` and `version`.

### 19.1 Never twice — no duplicates

- **Push:** a row's identity is `(entity, entityId, version)`; a batch's is `(branchId, seq)`. A retried
  batch (timeout, crash, lost reply) is stored once and answered with **the same reply** (section 7).
- **Pull:** the till skips any row with `version ≤ since` and any `(entity, entityId, version)` it has
  already applied (section 8).
- **POSTs in section 17** carry `Idempotency-Key`; the same key returns the same answer (17.11).
- **Upserts, not inserts:** both sides store by `entityId`; the same row arriving twice updates one row,
  never creates a second.

### 19.2 Never echoed — what came from the other side does not go back

- **Till:** rows applied from `pull` are written **without a ChangeLog entry** (they are marked as coming
  from the portal), so the next `push` never contains them. Only an edit made in the shop creates a
  ChangeLog row. Applying a row whose content is identical to what the till already holds does nothing at
  all — no ChangeLog, no screen refresh.
- **Portal:** rows received by `push` are stored with their **origin branch**. When such a row also has to
  reach other shops (a company-wide row, e.g. a price changed at shop A), send it in `pull` to the **other**
  branches only — not back to the branch it came from. If you do send it back, the till treats identical
  content as already applied (above), but do not rely on that.

### 19.3 Never backwards — old data never overwrites new

- **Till-owned rows** (sales, shifts, stock movements… section 10): the till is the authority. Keep the row
  with the highest `version`; a late, lower `version` is acknowledged and ignored (section 7).
- **Portal-owned rows** (products, prices, promotions, users… section 10): the portal is the authority, and
  its pull `version` — one counter per company, bumped on every change (section 8) — is also each row's
  **revision**.
  - The till never applies a pulled row whose `version` is not higher than the one it last applied for that
    row.
  - When the shop edits a portal-owned row, the till pushes it with **`baseVersion`** = the portal `version`
    it last applied for that row (a new envelope field, push only, portal-owned rows only — added in the
    till's integration task; `schemas/sync-change.schema.json` is regenerated then).
  - Portal: `baseVersion` equal to your current version for the row → accept, bump the version, send the new
    row to the other branches. `baseVersion` lower (the row changed on the portal meanwhile) → **conflict**:
    your current row wins by default, record the conflict, and send your row down to that branch too; the
    till shows it on its Sync status screen for a person to settle (section 8).
- **Deletes are soft** (`deletedAt`, section 5) and follow the same version rules, so a late update can
  never bring a deleted row back.

### 19.4 Test list the portal must pass before we connect a real shop

1. Push the same batch twice → one set of rows, identical replies.
2. Reply is lost, the till retries a batch that overlaps the previous one → no duplicates, `acknowledgedSeq`
   still correct.
3. Create a product on the portal → it reaches the till (`pull`) → the till's next `push` does **not**
   contain it.
4. Change a product's price at shop A → the portal gets it once → shop B receives it → shop A does not get it
   back.
5. Change the same product on the portal and at the till before either syncs → one conflict, the portal's
   row wins, both sides end up identical.
6. A delayed, older version of a row arrives after a newer one (either direction) → the newer stays.
7. Delete a product on the portal, then a late till update of that product arrives → it stays deleted.
8. Two tills of one shop both sell offline for an hour, then reconnect → every sale arrives exactly once,
   numbered per till (section 2.4).
9. Kill the connection mid-push and mid-pull a dozen times → the final data on both sides is identical to
   a clean run.

## 20. Everything reaches you; the till never needs you to trade; how future changes arrive (owner, 2026-09-26)

### 20.1 Everything the shop does comes up

Every till-owned table is pushed — 113 of the till's 142 entities (`samples/ownership.json`), not just
sales. So the portal can build **every report the till has**, per business, shop, till and person:

| Report area | Entities that arrive by push |
|---|---|
| Sales, refunds, voids, discounts, VAT | `Sale`, `SaleLine`, `SalePayment`, `SaleVat`, `SalesDaily`, `TenderDaily` |
| Cash-up, shifts, Z reports | `Shift`, `ShiftTender`, `ZReport`, cash movements |
| **Staff: who clocked in and out, when** | `ClockEvent` (each clock in/out with user, till and time), `RotaShift`, `TimesheetApproval`, `WageRate` |
| Stock | `BranchProduct`, `StockMovement` |
| Who did what (voids, refunds, price changes, drawer opens…) | `AuditLog` |
| Customer orders, purchasing, finance | `CustomerOrder…`, purchasing documents, `JournalEntry`/`JournalLine`, `VatReturn`… |

Not yet: `Setting` and `RolePermission` rows (they do not enter the ChangeLog, §16), and child rows carry
their branch through the parent (§16). Both are fixed in the till's integration task.

### 20.2 Offline first — the till never waits for the portal

Written as a rule for both sides (`specs/architecture.md`: "Internet down → full trade, sync later";
`specs/performance.md`: "Cloud sync never slows the till"):

- **Net on:** changes go up and down about every 30 seconds in the background.
- **Net off (minutes or weeks):** the till trades exactly as normal — sales, refunds, cash-up, reports,
  labels, clock-in, everything. Its changes wait in the ChangeLog; the portal's changes wait on the portal.
- **Net back:** both queues drain by themselves, in order, without duplicates (§19), throttled so the till
  stays fast (§18.9). Nobody presses anything.
- **Portal down or slow:** same as net off. A failing portal never shows an error to a cashier — only a
  quiet "last synced …" on the Sync status screen.
- **The one exception is the licence:** a cloud licence that cannot check in for **14 days** locks the till
  (§17.9), with a daily warning before that. Nothing else about the portal can stop a shop from trading.

### 20.3 How future changes reach you

The till will keep growing (new features, new fields, new tables). The contract grows with it, the same
way every time:

1. **Additive only** within `/api/v1` (§17.11): new endpoints, new optional fields, new entities, new enum
   values that older code treats safely. Nothing is renamed or removed without a `/v2`.
2. **The till cannot add a table without deciding who owns it** — a guard test fails otherwise (§10), and
   the schemas and samples are regenerated from the till's code, so this package can never silently fall
   behind.
3. **Every change ships as a new package** named with its date, containing the whole contract plus a
   "What changed" list at the top of `START-HERE.md`: new/changed entities and fields, new endpoints, and
   anything the portal must do.
4. **Your side stays safe in the meantime:** because you keep the full `payload` JSON (§18.8) and ignore
   unknown fields, a new field the till starts sending is already stored before you build a screen for it.
