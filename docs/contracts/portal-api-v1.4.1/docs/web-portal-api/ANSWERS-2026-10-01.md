## 1. Staff PIN (`User.pinHash`) — ASP.NET Identity v3 **nahi**

Till Identity v3 ka hash **nahi** padhta. `AQAAAA…` wala blob till par refuse hota hai — staff ka PIN kabhi nahi
chalega. Till ka apna text format hai (`src/SSPOS.Infrastructure/Security/Pbkdf2PinHasher.cs`):

```
pbkdf2$<iterations>$<base64 salt>$<base64 subkey>
```

| Cheez | Value |
|---|---|
| Algorithm | PBKDF2-HMAC-**SHA256** |
| Input | PIN ke UTF-8 bytes (pepper/secret koi nahi) |
| Iterations | **100000** (till likhta hai; padhte waqt string wala number use hota hai) |
| Salt | 16 random bytes |
| Subkey | 32 bytes (padhte waqt string wali length use hoti hai) |
| Encoding | standard Base64 (`+` `/` aur `=` padding ke saath), base64url nahi |
| Layout | 4 hisse, `$` se alag: `pbkdf2` (exact, chhote huroof) · iterations (decimal) · salt · subkey |
| Lambai | ≤ 200 characters |

**Test ke liye sample** (salt = bytes `00 01 02 … 0F`, sirf test ke liye — asal mein har PIN ka naya random salt):

| PIN | `pinHash` |
|---|---|
| `1234` | `pbkdf2$100000$AAECAwQFBgcICQoLDA0ODw==$hp5sg1DFvrCsw5n7qsO2DSIEM4lrJqZHc00NjxWG4fo=` |
| `0000` | `pbkdf2$100000$AAECAwQFBgcICQoLDA0ODw==$aS55LrsMVg+Dlele5It7ctBUzXJV2B2/FMilt+7ObRM=` |

Yeh dono till ke test mein pinned hain (`Pbkdf2PinHasherTests.Verify_ThePortalSample_IsTrue`) — jo hash aap ka
code banaye ga woh till par chalega, agar yahi format ho.

C# mein portal ki taraf (`System.Security.Cryptography`):

```csharp
static string HashPin(string pin)
{
    byte[] salt = RandomNumberGenerator.GetBytes(16);
    byte[] key = Rfc2898DeriveBytes.Pbkdf2(pin, salt, 100_000, HashAlgorithmName.SHA256, 32);
    return $"pbkdf2$100000${Convert.ToBase64String(salt)}${Convert.ToBase64String(key)}";
}
```

Yaad rahe (§10.7): `pinHash` sirf PIN set/badalne ke liye bhejein. Khaali, `null` ya na ho to till apna PIN
rakhta hai. Portal ki Identity login (owner/admin) alag cheez hai — woh Identity v3 mein hi rahe; sirf `User.pinHash`
(till staff ka PIN) is format mein ho.

## 2. `PromotionRule` — offers portal se

Dono tables portal-owned hain: `PromotionRule` + `PromotionItem` (products/categories ki list). Enums **camelCase
string** mein (number kabhi nahi), paisa **pounds decimal** (2.00, pence nahi), tareekh `"yyyy-MM-dd"`, waqt
`"HH:mm:ss"`. Schema: `schemas/entities/PromotionRule.schema.json`, `PromotionItem.schema.json`.

### 2a. Quantity-price ("3 for £2", "2 for £5")

**Aik tier — `multiBuy`:**

```json
{ "name": "3 for £2", "type": "multiBuy", "scope": "product", "targetId": "<productId>",
  "buyQuantity": 3, "dealPrice": 2.00, "priceTiers": null }
```

`dealPrice` = poori deal ki qeemat (3 ka £2). "2 for £5" = `buyQuantity: 2`, `dealPrice: 5.00`. Bache hue pieces
shelf price par.

**Kai tiers aik product par — `quantityPrice` + `priceTiers`:**

```json
{ "name": "2 for £5, 3 for £7", "type": "quantityPrice", "scope": "product", "targetId": "<productId>",
  "priceTiers": "2=5.00;3=7.00", "memberValue": 0 }
```

`priceTiers` aik **string** hai (JSON array nahi): `quantity=total price` VAT samait, `;` se alag, quantity
chhoti se bari, har quantity ≥ 2 aur dobara na aaye, price > 0 aur pence tak (`.` decimal). Till woh blocks chunta
hai jo customer ko sab se zyada bachat dein (`src/SSPOS.Domain/Promotions/PromotionPriceTiers.cs`).
`quantityPrice` mein `memberValue` ignore hota hai — 0 bhejein.

**Kai products mila kar ("any 3 for £2") — `mixMatch`:** rule par `scope: "itemGroup"`, `targetId: ""`,
`buyQuantity: 3`, `dealPrice: 2.00`, aur har product/category ke liye aik `PromotionItem`:

```json
{ "promotionRuleId": "<ruleId>", "scope": "product", "targetId": "<productId>",
  "groupNo": 0, "quantity": 1, "isExcluded": false, "attributeFilter": null }
```

`PromotionItem.scope` = `product`, `category`, `department` ya `style`. `isExcluded: true` = is ko deal se bahar
rakho (e.g. poori category magar aik product nahi). Meal deal = `mealDeal`, items `groupNo` 1, 2, 3 mein (har group
se aik). Rule ki koi `PromotionItem` na ho to till rule ka apna `scope` + `targetId` use karta hai.

### 2b. Din aur waqt (happy hour)

| Field | Format |
|---|---|
| `days` | flags enum, **camelCase naam comma + space se**: `"monday, tuesday, wednesday, thursday, friday"`, `"saturday, sunday"`, `"all"`. `"none"` bhi = har din. |
| `timeFrom`, `timeTo` | `"HH:mm:ss"` ya `null` — **shop ka local waqt (UK)**, UTC nahi. Dono end shamil. Dono `null` = poora din. |
| `effectiveFrom`, `effectiveTo` | `"yyyy-MM-dd"` local trading date, dono shamil; `effectiveTo: null` = koi end nahi. |

**Raat 12 ke paar:** `timeTo` < `timeFrom` ho to window midnight cross karti hai (`"22:00:00"` → `"02:00:00"`).
Din ka check us waqt ki **calendar date** par hota hai — "Fri 22:00–02:00" ke liye `days` mein `friday` **aur**
`saturday` dono dein, warna Saturday 01:00 par offer nahi lagega.

Poora example — weekdays 17:00–19:00, any 3 for £2, har shop:

```json
{ "id": "<ulid>", "companyId": "<co>", "name": "Any 3 for £2", "type": "mixMatch", "scope": "itemGroup",
  "targetId": "", "percent": 0, "amountOff": 0, "dealPrice": 2.00, "memberValue": 0, "buyQuantity": 3,
  "getQuantity": 0, "priceTiers": null, "minQuantity": 0, "priority": 0, "allowStack": false,
  "isExclusive": false, "maxRedemptionsPerSale": null, "maxRedemptionsTotal": null, "redemptionCount": 0,
  "couponCode": "", "branchId": null, "customerGroupId": null, "isHfssSafe": false,
  "effectiveFrom": "2026-10-01", "effectiveTo": null, "seasonalEventId": "",
  "days": "monday, tuesday, wednesday, thursday, friday", "timeFrom": "17:00:00", "timeTo": "19:00:00",
  "isActive": true }
```

(+ base fields: `createdAt`, `updatedAt`, `rowVersion`, `deletedAt`, `isDeleted`.) `branchId: null` = har shop;
aik shop ke liye us ka branch id (`SHOP-OR-EVERY-SHOP.md`). `isGroupOffer` aur `requiresCoupon` till khud nikalta
hai — bhejein to ignore. `redemptionCount` till barhata hai — portal naya rule 0 se banaye.

## 3. `shop.trading_hours` — free text, aap ka format theek hai

Setting `Text` hai (JSON nahi), company scope, max **200** characters, default `"08:00-22:00"`. Till abhi ise
**parse nahi karta** — sirf customer second screen par jaisa likha hai waisa dikhata hai. Is liye
`"Mon 07:00-22:00, Tue 07:00-22:00, … Sun Closed"` bilkul theek hai — bas 200 characters se kam rakhein (saat din
poore likhne se ~110 banta hai). Agar kabhi till ko ise samajhna pada (reports/ordering) to hum isi format ko parse
karenge, aur pehle UPCOMING-CHANGES mein batayenge.

## 4. Staff time — kya hai, kya nahi

| Cheez | Till mein | Portal ko |
|---|---|---|
| Clock in/out, breaks | `ClockEvent` (`type`: `in`/`out`/`breakStart`/`breakEnd`, `at` UTC, `registerId`) | push, read-only |
| Rota | `RotaShift` (`shiftDate`, `startTime`/`endTime` UK local, `breakMinutes`, `isPublished`) | push, read-only |
| Approved hafta | `TimesheetApproval` (`weekStart`, `totalHours`, **`overtimeHours`**, kis ne approve kiya) | push, read-only |
| Staff ka hourly rate | **`User.ratePerHour`** (decimal £) + `User.maxShiftHours` (warning) | `User` portal-owned — aap set kar sakte hain |
| Minimum wage table | `WageRate` (umar ke hisaab se NMW/NLW) | push, read-only |
| **Overtime rules** | **koi setting/entity nahi** — till mein fixed: din mein 8 ghante se upar = overtime. Weekly rule ya rate multiplier nahi. | sirf `TimesheetApproval.overtimeHours` ka natija |
| **Holiday / absence** | **nahi bana.** Holiday sirf calculate hoti hai (12.07% kaam ke ghanton ka, timesheet screen par) — save ya sync nahi. Absence/leave/holiday booking ki koi table nahi. | kuch nahi |

To portal par: overtime **dikha** sakte hain (`TimesheetApproval.overtimeHours`), rate **set** kar sakte hain
(`User.ratePerHour`), lekin overtime rules aur holiday/absence abhi till nahi bhejta. Agar owner chahte hain ke
yeh portal par banen to bata dein — pehle till mein entity banegi aur UPCOMING-CHANGES mein schema aayega.
Tab tak inhein portal par apni tables mein rakh sakte hain, till ko nahi bhejein (till anjaan fields/tables
ignore karta hai).

## 5. Newspapers — kya hai, kya nahi

Till mein newspapers sirf **shop counter + supplier sale-or-return** ke liye hain:

| Entity | Kya | Malik |
|---|---|---|
| `NewsTitle` | `name`, `publisher`, `frequency`, `supplierId`, `coverPrice`, `linkedProductId`, `linkedBarcode`, `isActive` | portal-owned |
| `NewsDelivery` + `NewsDeliveryLine` | supplier ki delivery note: `qtyIn`, `unitCost`, `qtyReturned` (sale-or-return credit) | branch, read-only |
| `NewsVoucherRedemption` | newspaper vouchers jo counter par liye gaye | branch, read-only |

- **Delivery rounds — nahi bane.** Ghar ghar delivery ke rounds ki koi table nahi.
- **Customer news accounts — nahi bane.** Customer ki subscription / paper bill ki koi table nahi.
- **Title par VAT — field nahi.** VAT `linkedProductId` wale `Product.vatRateId` se aata hai (scan par till
  product ki normal price/VAT path use karta hai). UK mein newspapers zero-rated hain: linked product ka
  `vatRateId` zero-rate wala `VatRate` ho (`percentage: 0`, seed mein naam "Zero", receipt letter `code: "C"`). Title ka linked product na ho to till par us ki koi
  VAT line nahi banti.

Agar portal par rounds aur news accounts chahiye to yeh naya feature hai — owner se poochh kar till mein banega;
abhi in ke liye till ko kuch na bhejein.

## 6. Stock transfer — variance ka sign (dono ulte hain)

| Field | Formula | Matlab |
|---|---|---|
| `StockTransferReceiptLine.qtyVariance` | **received − sent** (`qtyReceived − qtyDispatched`) | minus = kam aaya, plus = zyada aaya |
| `StockTransferReceipt.varianceCost` | **sent − received** (`dispatchedCost − receivedCost`) | plus = raste mein maal/qeemat gum |

Misaal: 10 bheje, 8 pahunche, £1.50 each → line par `qtyVariance: -2`, receipt par `varianceCost: 3.00`.
Jaise aaye waise dikhayein, dobara calculate na karein. Ab spec §10.2 mein bhi likha hai.
