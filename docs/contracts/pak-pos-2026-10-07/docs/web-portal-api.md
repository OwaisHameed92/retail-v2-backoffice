## 1. What the shop enters — nothing leaves the shop until a key is entered

**Simple set-up (owner, 2026-09-28; `docs/web-portal-api/SIMPLE-SETUP.md` has the whole chain).** Whoever installs
SSPOS types a **licence key** on every till (section 17.15). A shop that wants the online dashboard also types a
**sync key** once, on its main till (Settings → System → Network → Cloud sync → **Connect**) — or gets it without
typing when your `licence/activate` / `licence/validate` reply carries `apiKey` (17.3 step 3). The portal's
address is **built into the till** at release (`build/portal.json`); the fixed `/api/v1/…` paths are added to it.
Send the owner your production base URL (HTTPS) before the release that should use it.

Licence calls (section 17) need only the licence key. Sync (sections 4–9) runs only on the branch's main till and
only when **both** of the first two settings below are set — Connect, or your reply's `apiKey`, sets them:

| Setting (Settings → Network → Cloud sync; group 20) | Key | Default | Meaning |
|---|---|---|---|
| Portal API key | `sync.hub_api_key` | blank | The branch's **sync key** — the bearer of every sync call (one per branch). Set by Connect or by your reply's `apiKey`. Masked on screen, never logged, never printed, never in a support bundle, never synced (§10.3, §10.7). |
| Cloud sync | `sync.hub_enabled` | **off** | The master switch; Connect (or your `apiKey`) turns it on. While off, the till opens no connection to the sync endpoints at all. |
| Hub address | `sync.hub_url` | blank = the built-in address | An advanced override (Advanced), or the `hubUrl` your reply sent. HTTPS only. |
| Sync every | `sync.interval_seconds` | 30 | Seconds between runs (10–3600). |
| Rows per batch | `sync.batch_size` | 5000 | Rows per push (100–5000; 5,000 is a hard ceiling). |
| Licence server (Settings → Licence) | `licence.portal_url` | blank = the built-in address | An advanced override for the licence and migration calls (dealers, test portals). |

Which address a call uses (the first one filled in): `licence/*`, `devices/deactivate`, `cloud/migrate*` →
Licence server, then Hub address, then built-in; `sync/*` → Hub address, then Licence server, then built-in.

## 2. Company → Branch → Till (how the till is structured — build the portal the same way)

1. **Hierarchy.** Company → Branch (a shop) → Register (a till). Every row carries `companyId`; every
   branch-scoped row also carries `branchId`; every till-scoped row also carries `registerId`
   (`src/SSPOS.Domain/Common/Entity.cs`, `BranchEntity.cs`, `RegisterEntity.cs`). Every row has an
   `id` that is a **ULID made on the till** (`Entity.Id = Shared.Ulid.NewId()`), globally unique.
   **The portal must never re-key a row**; store the till's id as your primary key.
2. **Who talks to the portal: one sender per branch.** Inside a branch, the main till owns the branch
   database and hosts the embedded store server (`src/SSPOS.Server`); the other tills sell against
   that database over the shop LAN and keep only a cache and an emergency queue
   (`src/SSPOS.Client`, `src/SSPOS.Domain/Common/TillRole.cs`: `SingleTill`, `MainTill`,
   `SecondaryTill`). So **only the main till (or the only till) of each branch pushes and pulls**.
   The till enforces this (`src/SSPOS.Application/Sync/SyncSenderGate.cs`: a `SecondaryTill` is
   refused with `sync.wrong_till`). One branch = one connection = one cursor.

   **How a second till's work reaches you (store protocols 2 and 3, 2026-09-28 — replaces the old wording that
   only sales were affected).** A secondary till keeps no trading data of its own. Everything it trades is
   run **on the main till, as the secondary till**, and written into the branch database, so it reaches you
   in the main till's ordinary pushes like any other row (`src/SSPOS.Application/MultiTill/SecondaryTillPolicy.cs`
   is the one list; `src/SSPOS.Server/Services/StoreTradingService.cs` runs it):
   - **What comes up from a second till:** sales; refunds (with and without a receipt), exchanges, voids,
     sale corrections, held sales; opening, closing and swapping a shift, the float, paid in, paid out, safe
     drops, spot counts, counterfeit notes, expenses paid from the drawer, X/Z reports; clock in / clock out;
     vouchers, customer accounts and loyalty, customer orders and stock reservations, parcels, pharmacy
     dispensing, age refusals and alcohol-hours / max-quantity overrides, diary checks, temperature readings,
     incidents, training records, news vouchers, "Add & sell" quick-add products — **and the `AuditLog` rows
     each of these writes**.
   - **Every such row names the till that did it.** `registerId` = the secondary till's own register (never
     the main till's), `shiftId` = the shift open on that till's register, `userId` = the person signed in at
     that till (the main till checks that person's role permissions in the branch database). **Staff are the
     main till's** (store protocol 3): the main till's `User` and `Role` rows are copied to every secondary
     till with the same ids, so `userId` is always a `User` row you hold, and the main till refuses work —
     sales included — by someone it does not know ("sign in with a user set up on the main till"). One
     exception: a sale by someone switched off on the main till after they signed in is still recorded under
     them (the customer has paid). Rows pushed before store protocol 3 may carry a second PC's own user id
     that matches no `User` row you hold, or `""` on a sale queued by an older version — show them as
     "unknown staff". **The till itself always has a
     `Register` row:** the first time a new secondary PC joins, the main till adds it to the branch's till list
     under the register id that PC made for itself (`isMainTill: false`, `code` the first free `T02`, `T03`…,
     `name` the PC's name) and pushes that `Register` row like any other, before or in the same push as the
     till's first sale (`src/SSPOS.Server/Services/StoreJoinService.cs`). A till switched off or removed there
     cannot join. Sales and refunds are numbered per till (`LDS-02-000017`; `(registerId, number)` is unique). Use the **row's**
     `registerId` for per-till reports — the `X-SSPOS-Register-Id` header is always the main till, because
     it is the sender.
   - **Sales a second till took while it could not reach the main till** (its emergency queue) arrive when
     the shop's network comes back. Their `completedAt` — and their `StockMovement.at`, till cash and ledger
     dates — is **when the customer paid**, never later than the moment the main till wrote it and never
     earlier than the opening of that till's shift; their `createdAt` / `updatedAt` and `seq` are when the main
     till wrote them. So a push can bring a sale whose `completedAt` is earlier than rows you already hold:
     bucket sales by `completedAt`, order processing by `seq`. While the main till is unreachable a second
     till only sells; every other trading key says "nothing was saved — do this again once the main till is
     back", so there is nothing else to catch up.
   - **Back office is done on the main till only** (products, prices, stock, purchasing, promotions, users
     and roles, finance, the cash office, day lock). On a secondary till those keys are greyed with "Do this
     on the main till", and the main till refuses them from another till. Master data therefore always comes
     from the main till (or from you).
   - **What never leaves a second till:** its card-terminal attempt log (`PaymentAttempt`; the payment itself
     is on the sale's `SalePayment`), its cart-event journal, its own device and printer settings, print and
     label queues, sign-in lockouts and practice (training-mode) sales — see section 16.
   - **Before store protocol 2** (till versions before this one), a second till's sale was booked under the
     **main till's** `registerId`, shift and user while keeping the second till's receipt number, and its
     refunds, shifts, cash and clock-ins were never pushed. Rows already on the portal from that time keep
     that shape. A till of an older store protocol cannot join a main till of a newer one (it trades in
     emergency mode — sales only — until it is updated), so the shapes are never mixed after the update.
   - **LAN-only feeds — nothing reaches the portal (store protocol 3).** The main till copies three things to
     every secondary till over the shop LAN, when it joins and at every heartbeat (about every 20 seconds): the
     **staff list** (its `User` and `Role` rows, same ids — `PullStaffAsync`, the reason for protocol 3), the
     **shop-wide settings** (its value of every Company- or Branch-scope catalogue setting, minus the §10.3
     deny-list and minus one PC's own screen, keyboard, sound, scale, drawer, CCTV and retention settings;
     Register-scope settings never travel; read-only on the secondary till — `PullShopSettingsAsync`) and the
     **shop's prices** (§10.5, `PullBranchPricesAsync`). The last two are optional calls added within protocol 3
     (an older till never asks; an older main till answers "unimplemented"), so the number did not move. A
     secondary till never talks to the portal and never pushes these copies: the branch's staff, settings and
     prices are the main till's, exactly as its pushes show them. Nothing in the JSON you receive changes.
3. **Identification.** Every sync request carries the headers in section 3 (licence and device calls carry the
   shorter list there): the API key, company id, branch id, the sending register id, the contract version and the
   store protocol version
   (`src/SSPOS.Server/Contracts/StoreProtocol.cs`, `Version = 3` since 2026-09-28 — 2 for the forwarded
   trading of Wave 1, 3 for the staff list copied to secondary tills; informational — nothing in the JSON you
   receive changed with it). The API key is **per branch**
   (`sync.hub_api_key` is a branch-scoped setting); issue one key per branch and reject a request
   whose `X-SSPOS-Branch-Id` is not the key's branch.
4. **Company-wide vs per branch.**
   - Company-wide (no `branchId` on the row): the master data in section 10 — products, barcodes,
     aliases, departments, categories, units, VAT rates, promotions, customers, users, roles,
     suppliers, payment types, reasons, accounts, price history.
   - Per branch (`BranchEntity`): `BranchProduct` (the branch's stock on hand; its `priceOverride` is only a
     stock-valuation figure, never a selling price — `src/SSPOS.Domain/Catalogue/BranchProduct.cs`),
     `BranchPrice` (a shop's own shelf price, **set on the portal**, §10.5), `ZReport`, `CustomerOrder`,
     `Register`, `SyncConflict` and other branch rows.
   - Per till (`RegisterEntity`): `Sale`, `Shift`, `StockMovement`. Sales are numbered **per till**
     (`Register.NextSaleNo` / `NextRefundNo`, `src/SSPOS.Domain/Common/Register.cs`); receipt numbers
     look like `LDS-01-000482` = branch code, till code, sale number (`Register.ReceiptPrefix`).
     Two tills may both have a sale number 17; `(registerId, number)` and `id` are unique, `number`
     alone is not.
   - Down to **all branches**: rows with `branchId: ""` (company-wide master data). Down to **one
     branch**: rows with that branch's id (e.g. a web order for that shop).
5. **Cursors are per branch.** The push cursor (`seq`) is the branch database's own ChangeLog
   sequence; Leeds and Bradford both have a `seq` 5120 and they are different rows. Key everything
   by `(branchId, seq)`. The pull cursor (`since`) is per branch too
   (`src/SSPOS.Domain/Sync/SyncState.cs`, one row per branch). **A pull must never return another
   branch's till-owned rows**, only company-wide rows and rows addressed to the caller's branch.
6. **Samples.** `samples/push-request.json` (Leeds, sent by Leeds till 1),
   `push-request.second-till.json` (Leeds till 2's morning — still sent by Leeds till 1, same `branchId`,
   `seq` carries on: till 2's shift opened by its own cashier, a sale rung on till 2 while the network was
   up, a paid-out from till 2's drawer, and a sale till 2 took while the main till was unreachable, whose
   `completedAt` is 14 minutes before its `createdAt`; every till-owned row carries till 2's `registerId`,
   till 2's `shiftId` and till 2's cashier as `userId`) and `push-request.second-branch.json` (Bradford:
   other `branchId`, its own `seq` numbers).

## 3. Transport

| | |
|---|---|
| Protocol | HTTPS only (TLS 1.2+). The till refuses `http://` and invalid certificates (no pinning). |
| Auth | `Authorization: Bearer <sync.hub_api_key>` (the branch's sync key) on every `sync/*` call and on `cloud/migrate/complete` (with the key the migrate reply issued); **none** on `cloud/migrate` (the sync key is the `activationCode` in the body); on `licence/*` and `devices/deactivate` only when the till holds a branch key (optional — 17.15). |
| Identity headers | Sync and migration calls (`sync/*`, `cloud/migrate*`): `X-SSPOS-Company-Id`, `X-SSPOS-Branch-Id`, `X-SSPOS-Register-Id` (the sending till — the branch's main till), `X-SSPOS-Contract: 1`, `X-SSPOS-Store-Protocol: 3` (`1` before 2026-09-28, then `2`, now `3`; informational — accept any number), `X-SSPOS-App-Version: 0.1.x` (the build's semver); the migration calls add `X-SSPOS-Install-Id`. Licence and device calls (`licence/*`, `devices/deactivate`): the same without `X-SSPOS-Store-Protocol`, plus `X-SSPOS-Install-Id`. |
| Idempotency | `Idempotency-Key` on every POST except a normal (delta) push — one key per logical request, repeated with the same body on every retry (§17.11 rule 5). |
| Content type | `application/json; charset=utf-8` both ways |
| Compression | Push body is **gzip** (`Content-Encoding: gzip`) — `SyncBatch.Pack` gzips it. The sync and migration calls send `Accept-Encoding: gzip`, so their replies may be gzip; licence calls do not — answer those uncompressed. |
| Push size | ≤ 5,000 rows per request (`SyncBatcher.MaxRowsPerBatch`, or less: your hello `maxBatchRows`, halved after a 413), at most 5 batches per run. Allow request bodies up to 50 MB uncompressed. |
| Timeouts | Till waits 30 s for a reply, then treats it as a network failure and retries later. |
| Frequency | Every `sync.interval_seconds` (30 s) on the branch's main till (`src/SSPOS.Server/Hosting/SyncTimerHost.cs`; a tick does nothing while Cloud sync is off; after a failed run the next ones back off 1 → 2 → 5 → 15 minutes, a longer `Retry-After` wins), at Close Shop, and on "Sync now" (Sync status screen, never held back). Order in a run: push, then pull — the pull runs **even when the push failed**, unless the failure ends the run (§9) (`src/SSPOS.Application/Sync/RunSync/RunSyncHandler.cs`). Up to 10 pull pages per run while you say `hasMore`. |

### 4.1 `GET /api/v1/sync/hello` — defined

The first sync call after the till starts or the key or address changes (then answered from memory until one of
them changes: every push and pull says hello first), the call **Connect** makes with a sync key when the branch
has synced before (route B of `SIMPLE-SETUP.md`), and the first call after the §17.8 migration. It proves the
address, the TLS certificate, the key and the key's branch in one round trip.

- **Request:** no body; `Authorization: Bearer <key>` and every section 3 header.
- **Reply 200** (`schemas/hello-reply.schema.json`, `samples/hello-reply.json`): `contractVersion` (1),
  `companyId` and `branchId` (the key's — the till checks they equal its own and shows a mismatch as "this key
  is for another install"), `branchName` (shown so the owner sees he pasted the right key), `serverTimeUtc` (the
  till warns when its clock is more than 5 minutes out), `maxBatchRows` (the most rows one push may carry,
  ≤ 5000; the till uses the smaller of this and `sync.batch_size`). New fields may be added.
- **Errors:** 401 `auth.invalid_key` / `auth.key_revoked`, 403 `auth.wrong_branch`, 409 `contract.unsupported`,
  426 `app.update_required`, 429 / 503 with `Retry-After`, 500. Body = section 9. A 200 naming another company or
  branch is refused by the till itself (`sync.key_other_install`: it stops until the key is changed).
- **Idempotency:** a GET with no side effects — answer it the same way every time.

## 5. The envelope — one changed row (`SyncChange`, both directions)

`src/SSPOS.Application/Sync/SyncChange.cs`. Schema: `schemas/sync-change.schema.json`.

| Field | JSON type | Push (till → portal) | Pull (portal → till) |
|---|---|---|---|
| `seq` | integer | Branch ChangeLog sequence, strictly increasing per branch | Always `0` |
| `entity` | string | Entity type name, e.g. `"Sale"` (PascalCase, as in section 10) | Same; plus `"WebOrder"` (section 12) |
| `entityId` | string (ULID) | The row's `id`. For `Setting` / `RolePermission` (no ULID of their own): an id derived from their key, the same for every change to that row (§10.3) | The row's `id` (a new row: a ULID you make). For `Setting` / `RolePermission` any id: the till keys them by the payload |
| `op` | `"I"` / `"U"` / `"D"` | Inserted / updated / soft-deleted. When one row has several entries in a push they all carry the op of the row's latest state: `D` if the last change deleted it, `I` if the row is new since the last push, otherwise `U` (§7) | Same meaning |
| `version` | integer | The version of the row state in `payload`: the row's `rowVersion` when the till built the batch (never below the ChangeLog version that queued it; `payload.rowVersion` equals it — §7). For `Setting` / `RolePermission` the row's `seq` (§10.3) | **Your** change counter (see 8) |
| `companyId` | string (ULID) | Always set | Always set |
| `branchId` | string (ULID or `""`) | The row's branch; `""` on a company-wide row and on a child row (e.g. `SaleLine`). The sender is always the `X-SSPOS-Branch-Id` header. | `""` = every branch, else the one branch it is for. A relayed row (§10.2) is addressed to the receiving branch here, while its payload keeps the owning branch's `branchId` |
| `registerId` | string (ULID or `""`) | The till, for till-scoped rows; `""` otherwise | `""` |
| `at` | string (date-time, UTC, `Z`) | When this version was written on the till (its ChangeLog time; section 6.1) | When it changed on the portal |
| `payload` | object or null | **The whole row** as `samples/entities/<Entity>.json` | The whole row, same shape |
| `key` | string | Derived `entity:entityId:version`; ignore it | Optional; the till ignores it |

**Upsert, not diff.** Every `I`/`U` row carries the complete row. Treat `I` and `U` as upserts by
`entityId` and keep the row with the highest `version`. `D` is a soft delete: the payload still
comes, with `deletedAt` set; keep the row and mark it deleted. The till never hard-deletes a synced
row.

## 6. JSON conventions (exactly what `SyncJson.Options` writes)

- **Names:** camelCase (`receiptNumber`, `vatTotal`). Reading is case-insensitive on the till.
- **Money:** a JSON **number in pounds sterling**, not pence: `5.15` = £5.15. Prices and totals have
  at most 2 decimal places, rounded half away from zero (`Domain/Common/Money.cs`). Cost prices
  (`costPrice`, `costAtSale`, `unitCost`) and quantities (`qty`, `qtyDelta`) may carry up to 4 dp.
  Parse them as decimal, never float. The till may write `1.45` or `1.4500` — same value.
- **Numbers:** the till always writes JSON numbers. It also reads a number sent as a string
  (`"5.15"`), which is why the schemas allow both; send numbers.
- **Percentages:** numbers, `20` = 20 % (`vatPercentage`, `percentage`).
- **Dates and times:** ISO-8601 UTC with `Z`, e.g. `2026-09-23T09:41:12Z` (UK time is shown only
  on screen). A date with no time is `"2026-09-26"`. Treat a date-time with no offset as UTC. Which
  time means what, and the portal's own `receivedAt`: section 6.1.
- **Ids:** 26-character ULID strings (`01K5VB000000000SR001000482`), Crockford base32. A missing
  optional id is `null`; a missing envelope id is `""`.
- **Enums:** written as camelCase names, never numbers (`"completed"`, `"over18"`, `"pcs"`).
  Every allowed value is in `samples/enums.json`; section 11 lists them.
- **Nulls:** written, not omitted. Every property in a sample is always present.
- **Embedded JSON strings:** a few columns hold a JSON document as a string (`receiptJson`,
  `linesJson`, `licensedHoursJson`). Store them as-is.
- **Derived members:** anything the till computes rather than stores (e.g. `key`, `isDeleted`,
  `balanceDue`) may appear; the till ignores them when reading.

### 6.1 Times — which time means what (revision 1.3, 2026-09-28)

The owner wants every sale, order and product — every synced row — to show **"made in the shop at X,
reached the portal at Y"**. These are the times that make that possible.

**Every time on the wire is UTC, ISO-8601, ending in `Z`**, in both directions: `2026-09-23T09:41:12Z`, or
with a fraction, `2026-09-23T09:41:12.2074531Z` (up to 7 digits; parse with a real ISO-8601 parser, never by
fixed length). UK time is for screens only. A date with no time (`"2026-09-26"`) is a calendar date and has no
zone.

| Time | Where it is | Whose clock | What it means |
|---|---|---|---|
| `createdAt` | every payload | the till's (for a second till's work: the main till's, §2 point 2) | When the row was first written in the shop's database. It never changes after that. |
| `updatedAt` | every payload | the till's | When the row last changed in the shop. The payload is the row as it is when the till pushes it, so if one row changed twice before a push, both envelopes carry the newer row and its `updatedAt`. |
| `at` | the envelope (section 5) | the till's | When **this** `version` was written to the till's change log. It is the same save that set `updatedAt` for that version, so for the newest version the two are normally equal (a few milliseconds apart at most). For `op` `"D"` it is the delete (`deletedAt`). |
| Business times — `Sale.completedAt`, `Shift.openedAt` / `closedAt`, `StockMovement.at`, `CashMovement.at`, `ClockEvent.at`, `AuditLog.at`, `ZReport.periodStart` / `periodEnd` / `generatedAt`, `CustomerOrder.readyAt` / `collectedAt` / `cancelledAt` | the payload | the till's | **When it happened in the shop.** Use these for every report: trading day, hour of day, "sales today". A sale a second till queued while the main till was down has `completedAt` **earlier** than its `createdAt` (§2 point 2). |
| `receivedAt` | **your** push reply (section 7), and **your** database, one per row | **the portal's** | When your API durably stored the row. You set it, never the till. |
| `serverTimeUtc` | your `hello` reply (4.1) | the portal's | Your clock. The till warns the owner when its own clock is more than 5 minutes out. |

- **Store `receivedAt` on every row** you store from a push, beside `created_at` / `updated_at`. Keep two
  columns, as `DASHBOARD.md` §4.1 does: `first_received_at` (set once, when the row's first version reached
  you — this is the *"reached the portal"* time you show) and `last_received_at` (set each time a **newer**
  `version` of the row is stored). A retried copy of a version you already hold changes neither. Also record
  it on your push log keyed by `(branchId, seq)` — that is where a retried batch's reply time comes from
  (section 7).
- **Show both times** wherever a row is shown — a sale, an order, a product, a Z report: *"Made at the till
  10:41:12 (Leeds, till 1) · reached the portal 10:42:13"* — both in UK time on screen (the samples' sale
  `completedAt` `2026-09-23T09:41:12Z` and push reply `receivedAt` `2026-09-23T09:42:13.207Z`, in BST). Use the till's time
  (the business time, else `createdAt`) for everything about the business; use `receivedAt` only for sync
  health: *data up to* = the newest `received_at` per shop, *lag* = `received_at − created_at` (a long lag =
  the shop was offline or queued; a **negative** lag = the till's clock is fast — show a warning).
- **Trading day** = the calendar date of the business time **in Europe/London** (the shop's time zone), not
  the UTC date: a sale at `2026-06-30T23:30:00Z` belongs to trading day **2026-07-01** (BST). Per-shift figures
  follow the shift (`Shift`, `ZReport` periods), which can cross midnight. `DASHBOARD.md` §1.3 has the SQL.
- **Calendar dates stored as a date-time.** A few older columns hold a date the operator picked, sent as
  midnight: `CustomerOrder.dueDate`, `ScaleCalibrationLog.calibratedOn` / `expiresOn` (e.g.
  `2026-09-26T00:00:00Z`). Use only the date part.
- **Rows you send down (pull) keep your times.** When the till writes a row it pulled, it keeps the
  `createdAt` and `updatedAt` you sent (converted to UTC if you sent an offset — send `Z`). If you leave one
  out, or send one it cannot read, it uses the moment it applied the row instead; it never refuses a row over
  a time. `rowVersion` is always the till's own counter. A pulled row whose content equals the till's copy
  and differs only in its times changes nothing (§19.2). `Company` and `Branch` (the till's rows, whose
  details you edit, §18.3) keep the till's `createdAt` and take your `updatedAt` only when it is later than the
  till's. The till never pushes a pulled row back (§19.2); if the shop later edits it, the push carries your
  `createdAt` and the shop's edit time as `updatedAt`.
- **What the till records.** For every change-log row you acknowledge the till keeps `SentAt` (when it sent
  the batch), `AckedAt` (when it read your reply, by its clock) and `PortalReceivedAt` (your `receivedAt`);
  all rows of one batch share one `receivedAt`. Its Sync status screen shows *Last sent*, *Last acknowledged*
  and *Reached the portal*. Rows the history upload covered (17.8) have no `SentAt` / `PortalReceivedAt` of
  their own on the till — your upload stored them, so give them the `received_at` of the upload batch.
- **Older tills.** Before revision 1.3 (till builds before 2026-09-28) the till sent times it read back from
  its database **without the `Z`** — the values were UTC, only the letter was missing — and gave a pulled row
  the moment it applied it as its `createdAt` / `updatedAt`. Keep treating a date-time with no offset as UTC
  (section 6); nothing needs re-importing. A till that finds no `receivedAt` in your reply still works — it
  simply has no portal time to show — but your API must send it.

## 7. Push — idempotent, ordered, acknowledged

- The till sends its oldest unsent rows first, `seq` ascending, one branch per request.
- Store rows **in `seq` order**, then reply with `acknowledgedSeq` = the highest `seq` you have safely
  stored with every lower `seq` of this batch also stored, `accepted` = rows stored (a row you
  already had counts as accepted), and **`receivedAt`** = when you durably stored them (UTC with `Z`, your
  clock, taken after your commit — section 6.1). Schema `schemas/push-reply.schema.json`, sample
  `samples/push-reply.json`.
- The till marks everything up to `acknowledgedSeq` as sent and resends the rest next run. Replying
  with less than the batch's highest `seq` is fine; the rest comes again.
- **Retries are normal.** A timeout or crash means the till sends the same batch again. The
  idempotency key of a row is `(entity, entityId, version)`; storing the same triple twice must
  change nothing and must give **the same reply** — including the same `receivedAt`: answer a retried batch
  with the time its rows were first stored (the latest `received_at` your push log holds for its
  `(branchId, seq)` values), never "now". Also dedupe by
  `(branchId, seq)`.
- A row whose `version` is lower than one you already hold is stale: accept it (count it) and keep
  the newer one.
- **An entry is the row's latest state (revision 1.4).** `payload` is the row as it is when the till builds the
  batch, and `version` is the version of *that* state (the row's `rowVersion` now — never below the ChangeLog
  version that queued it; `payload.rowVersion` equals `version`). A row edited several times before a push appears
  once per ChangeLog row (each with its own `seq`, so `acknowledgedSeq` works as above), and every one of those
  entries carries **the same triple, the same payload and the same op** (`D` if the last change deleted it, `I` if
  the row is new since the last push, otherwise `U`). Store the triple once; count the rest as already had
  (accepted). `Setting` / `RolePermission` rows (§10.3) differ: one version (their `seq`) per entry, each its own
  content.
- **A resend may carry a newer state than the first send of that `seq`.** After a lost reply the till re-reads the
  rows: if a row changed meanwhile, the resent entries carry the newer state under the newer `version` (a new
  triple). A triple you already hold is always a duplicate, whatever arrives with it — never a 422 or an
  "idempotency mismatch"; a lower `version` than the one you hold is stale (above).
- **No `Idempotency-Key` on a normal push** — the rows are the idempotency. Each batch of the §17.8 history upload
  (`X-SSPOS-Sync-Mode: initial`) does carry one: the same key for the same batch bytes on every retry, until you
  answer (§17.11 rule 5).
- **Secrets never come up** (§10.7): no `User.remoteApprovalSecret`, no deny-listed `Setting`.
- **What comes up is every change the shop made** — its own rows (§10 "Till"), and portal-owned rows the shop
  edited (§8, §19.3). Rows the till *pulled* never come back (§19.2).

## 8. Pull — versions and paging

- `version` on the pull side is **your** number: one counter per company (or per branch), strictly
  increasing, bumped on every change you want tills to see. It is not the row's `rowVersion`.
- Reply with rows whose `version > since` visible to the caller's branch (company-wide + that
  branch), **oldest first**, at most `max` rows; `highestVersion` = the largest `version` in
  `changes`; `hasMore` = true if more are waiting (the till pulls again straight away).
- The till skips any row with `version ≤ since`, and any `(entity, entityId, version)` it has seen, so
  resending is safe. An empty reply is `samples/pull-reply.empty.json`.
- If the shop changed a portal-owned row it has not yet pushed, the till records a **conflict**
  (Sync status screen): by default the owner of the entity wins (section 10) and a person confirms. **The till
  keeps the row you sent with the clash** (revision 1.4) — your cursor has moved past it: "Head office wins" writes
  that row (as a pulled row: no ChangeLog entry, never pushed back) and drops the shop's unsent edits of it, so
  they are not pushed over yours; "This shop wins" keeps the till's row, which pushes as usual. A newer row from
  you for a row still in clash replaces the kept one (one open clash per row); a newer row that applies normally
  settles the old clash as "head office wins". Details in §19.3. Each clash is a branch-owned `SyncConflict` row
  that comes up in push like any other (`entity`, `entityId`, `hubVersion`, `branchVersion`, `detail`,
  `resolution` `pending` / `hubWins` / `branchWins` / `ignored`, `resolvedAt`, `resolvedByUserId`, and — new in
  1.4 — `hubChange`: your pulled envelope, as JSON text, `null` on older clashes), so you can show a shop's open
  clashes; the shop settles them, never you.
- **Child before parent is safe, across restarts.** A pulled row whose parent the till does not hold yet (a
  barcode before its product, a transfer line before its transfer, a `BranchPrice` before its product, an order
  line before its order) is **parked on disk** and applied the moment the parent arrives — retried at the start of
  every pull, so nothing is lost when the till restarts after your cursor moved past it. A row still waiting after
  **7 days** is dropped with a warning in the till's log — resend it with its parent if that happens. Sending
  parents first is still the right thing to do.
- **The till pulls even when its push was turned down** (422, 413, 400, 5xx, no answer), so your changes still
  reach it while the shop's rows wait; expect a pull right after a rejected push. It does not pull after 401/403,
  any `licence.*` code, 409 `contract.unsupported` or 426 (§9).
- Besides portal-owned rows (including `BranchPrice`, §10.5), a pull may carry **another branch's relayed rows** —
  a dispatched stock transfer and its lines, a transfer receipt, other branches' customer ledger rows (§10.2) —
  **settings and role permissions** (§10.3), and **head-office purchase orders** you drafted for this branch
  (§10.6). Nothing else that a branch owns may be sent.
- **Idempotency:** a GET with no side effects; the till's cursor and its `(entity, entityId, version)` check make a
  repeated page harmless.
- **A field you leave out keeps the till's value** (`HubRowMap.TryRead`; already so in 0.1.51). A field
  the till does not know is ignored (§17.11). `null` on a required text column reads as `""`; `null` (or a wrong
  type) on any other required column turns the whole row down. So to change only some columns of a row, send only
  those columns (plus `id`) — the safe way to edit a row the till also edits (e.g. `ProductRecall` text fields).

## 9. Errors and status codes

Every non-2xx reply has the body in `samples/error-reply.401.json` / `error-reply.422.json`
(`schemas/error-reply.schema.json`, defined): `code`, `message` (en-GB, shown to the shop
owner), `traceId`, `retryAfterSeconds`, `rejectedKey`, and optionally `details` (an open object of
machine-readable extras — `licensing/schemas/error-reply.schema.json`). Every code, on every endpoint, is
listed in section 17.12 and in `licensing/samples/error-codes.json`. 429 and 503 also carry a `Retry-After`
header. A code the till does not know is handled by its HTTP status as below.

| Status | Meaning | Till does |
|---|---|---|
| 200 | OK | Moves its cursor. |
| 400 | Malformed request | Shows `message`; the pull still runs; the push is retried next run. Rows are never dropped. |
| 401 / 403 | Bad or revoked key, or key not for this branch | Stops syncing and shows "API key rejected" until the key is changed — no pull, no retry storm. |
| 409 `contract.unsupported` (or a 409 with no code) | Contract version not supported | Stops syncing until the till is restarted (updated), shows `message`. |
| 409 `request.in_progress` | The same `Idempotency-Key` is still being worked on | Waits `Retry-After` (5 s when none), then repeats with the same key and body. |
| 413 | Batch too large | Halves the batch for the next push; the pull still runs. |
| 422 | A row cannot be stored; `rejectedKey` names it | Acknowledge the rows before it (reply 200 with the lower `acknowledgedSeq`) where you can; otherwise the till shows the row on the Sync status screen and retries next run. The pull still runs. |
| 426 | Update required | Stops syncing until the till is restarted (updated); keeps trading. |
| 429 / 503 | Busy | Sends nothing before `Retry-After` / `retryAfterSeconds` (60 s when neither is given), then carries on. |
| 5xx, timeout, no network | Portal down | The pull is still tried; later runs back off 1 → 2 → 5 → 15 minutes (then every 15 minutes; a longer `Retry-After` wins; "Sync now" is never held back). The shop keeps trading; rows wait in the ChangeLog. |

A failure that **ends the run** (no pull afterwards): 401/403, any `licence.*` code, 409 `contract.unsupported`,
426, sync switched off or not set up, or a history upload still open (§17.8). Anything else lets the pull run
(`src/SSPOS.Application/Sync/SyncStops.cs`).

### 10.1 Customer balance and points — the ledger is the truth (revision 1.4, 2026-09-28)

**Why this changed.** A `Customer` is one company-wide row that every shop moves: an account sale at Leeds, a
payment at Bradford, points everywhere. Until revision 1.4 each till pushed the customer's `balance` and
`points` as absolute numbers, so the last push overwrote the other shop's effect (a lost update).

**The rule now (built on the till):**

1. **The truth is the customer ledger, `CustomerTransaction`** (branch-owned, append-only, one row per
   movement; `samples/entities/CustomerTransaction.json`). A customer's **balance = the sum of `amount`** over
   their rows, **points = the sum of `points`**, leaving out rows with `deletedAt` set. `amount` is in pounds:
   positive increases what the customer owes, negative reduces it. `points` is positive when credited,
   negative when used or taken back. `type` is `charge`, `payment`, `refund`, `pointsEarn`, `pointsBurn`,
   `pointsAdjust`, `pointsExpire` or **`opening`** (new in 1.4, `samples/enums.json` → `CustomerTransactionType`).
   A correction is a new row; a row is never edited.
2. **`Customer.balance` and `Customer.points` are a cache** (`derivedColumns` in `samples/ownership.json`). In a
   push they are the sending till's own sum at that moment — **do not store them as the truth**; use your own
   sum over the ledger. In a pull the till **never writes them**, whatever you send (you may send your sum; it is
   ignored). **`Customer.pendingPoints`** (points a till held back on its own Not Paid sales until they are paid)
   is in the same list from till 0.1.52: the till keeps its own figure and never writes one from a pull. Every
   other `Customer` column is portal-owned as before. **`owed`, `creditHeld` and `isAnonymised`** are not
   columns: the till works them out (from `balance` / `anonymisedAt`) each time it pushes and never reads them from
   a pull — send them or not, they are ignored.
3. A change that only moves a customer's balance or points **no longer pushes the `Customer` row** — the
   `CustomerTransaction` row carries it. A `Customer` row is pushed when its details change (name, phone, card,
   credit limit, tier, notes, active, anonymised…). So a shop's account sales never cause a false "changed here
   and at head office" clash on a customer you edited.
4. **Relay every branch's ledger rows to every other branch of the business** (§10.2). Each till's cached
   balance and points = the sum of its own rows plus the rows you relayed to it, so every till and the portal
   add up the same rows. The till adds a relayed row's effect **once** — it is keyed by its `id`: the same row
   again changes nothing, and a changed copy moves only the difference. A new shop gets the whole history.
5. **Opening rows.** A customer import's opening balance or points now writes an `opening` row. On upgrade,
   **once per database**, the till writes one `opening` row for every customer whose stored figures differ from
   the sum of their ledger rows (note `"Opening balance brought into the ledger (upgrade)"`, booked to the main
   till's shop) and pushes it — so the ledger explains every figure the till showed before.
6. `balanceAfter` / `pointsAfter` on a row are the writing till's running figure at that moment, for its
   receipts and statements. Across shops they can differ from yours; never add them up.
7. The portal does not change balances or points in v1: adjustments and payments are made at a till
   (Customers → Adjust points / Take payment) and reach you as ledger rows.
8. A till checks a customer's credit limit against its own cached balance, which can lag another shop by one
   sync cycle (about 30 seconds while both are online).

Before revision 1.4 no shop has synced customers across branches (the portal is not live yet), so there is
nothing to reconcile. If you already stored `Customer.balance` from test pushes, recompute it from the ledger.

**`ProductRecall` works the same way from till 0.1.52.** The recall is company-wide (you may create it and edit
`reason`, `source`, `batchCode`, `expiryFrom`, `expiryTo`), but `returnedQty`, `status`, `closedAt`, `closedByUserId`
and `note` are `derivedColumns`: never written from a pull, never pushed on their own. Each shop's own close / reopen
is a branch-owned `ProductRecallBranchState` row (no row = open in that shop); a shop's returned quantity is
−Σ `StockMovement.qtyDelta` (type supplierReturn, refType "Recall", refId = the recall id) for that branch.

### 10.2 Relayed rows — stock transfers and the customer ledger (revision 1.4, 2026-09-28)

A few branch-owned rows are needed by **one other branch**. You copy ("relay") them, unchanged, in that
branch's pull. **The owner does not change:** the row keeps the sending branch's `branchId` in its payload,
only that branch ever changes it, and the receiving till holds it **read-only** — it never edits it and never
pushes it back. `samples/pull-reply.relay.json` is a real example (Bradford receiving a Leeds transfer with its
two lines, and a Leeds ledger row).

| Entity | Relay to | When |
|---|---|---|
| `StockTransfer` | its `toBranchId` | once its `status` is `dispatched` (never while `requested`, never `cancelled`). A dispatched header does not change again. |
| `StockTransferLine` | the `toBranchId` of its transfer | with its transfer: every line, in the same pull page as the header or straight after it |
| `StockTransferReceipt` | the `fromBranchId` of its transfer | when you store it, and again when it changes (`received` → `closed`) |
| `StockTransferReceiptLine` | the `fromBranchId` of its transfer | with its receipt |
| `CustomerTransaction` | every other branch of the same business | always; a new branch gets the whole history |

**Envelope.** `branchId` = the branch the row is **for** (the receiving branch; `""` is also accepted for a
`CustomerTransaction`, meaning every branch). The payload's `branchId` stays the **owning** branch. `version` is
your pull counter, as for every pulled row; `op` is `"I"`, or `"U"` for a receipt that moved on. Never relay a
row to the branch that owns it.

**What the till does with a relayed row:**
- It accepts a `StockTransfer` only when `toBranchId` is its own branch and `status` is `dispatched`; a
  `StockTransferLine` only for such a transfer (a line that arrives before its transfer waits for it); a
  `StockTransferReceipt` only for a transfer **it sent**; a `StockTransferReceiptLine` once its receipt is
  there; a `CustomerTransaction` once its customer is there (it waits for the `Customer` row otherwise).
- It refuses (skips and logs) a relayed row whose payload `branchId` is its own branch, or whose `id` is one of
  its own rows — a relay never overwrites the till's own data.
- **Idempotent:** keyed by `id`. The same relay twice is one row; a resend with a higher version but the same
  content changes nothing; a version at or below the one held is ignored.
- It never writes a ChangeLog row for a relayed row, so the next push never carries it back (§19.2).

**Receiving a transfer that came through the portal.** The receiving shop can press Receive only when it holds
every line: `StockTransfer.lineCount` (new column in 1.4, set when the transfer is raised and at dispatch) must
equal the number of `StockTransferLine` rows it holds for that transfer; until then the till says the transfer
is "still arriving". `lineCount: 0` is a transfer from a till older than 1.4: the lines held are taken as all
of them. Receiving writes the receiving branch's own `StockTransferReceipt` + lines, `StockMovement`s and
journal rows, pushed as ordinary branch rows; relay the receipt back to the sender and its screen shows
Received, then Closed. A transfer can be received only once (the till's `StockTransferReceipt.transferId` is
unique), so a relay applied twice can never book the goods twice.

**Variance signs (2026-10-01) — the two fields run opposite ways.** `StockTransferReceiptLine.qtyVariance` =
`qtyReceived − qtyDispatched` (negative = short, positive = over-delivered). `StockTransferReceipt.varianceCost`
= `StockTransfer.dispatchedCost − receivedCost` (positive = value lost in transit). So a shortage of 2 × £1.50 is
`qtyVariance: -2` on the line and `varianceCost: 3.00` on the receipt. Show them as they come; do not recompute.

### 10.3 Settings and role permissions (revision 1.4, 2026-09-28)

`Setting` and `RolePermission` are portal-owned (`"hub"`) and now travel both ways (until 1.4 they never left
the till). Neither has a ULID or a row version — a setting is keyed by (scope, scope id, key), a permission by
(role, permission) — so their envelope differs in three places:

| Field | `Setting` | `RolePermission` |
|---|---|---|
| `entityId` | a stable 26-character id the till derives from the key: the first 130 bits of SHA-256 of `Setting|{scope}|{scopeId}|{key}`, in Crockford base32 (`src/SSPOS.Domain/Sync/SyncRowIds.cs`). Every change to that setting carries the same id. | the same, from `RolePermission|{roleId}|{permissionKey}` |
| `op` | `I` / `U` / `D` | `I` = granted, `D` = taken away (there is no `U`) |
| `version` (push) | the row's `seq` — strictly increasing per branch | the row's `seq` |
| `branchId` | the `scopeId` of a branch setting; `""` for a company setting | `""` |
| `registerId` | `""` | `""` |
| `payload` | `{ scope, scopeId, key, value, updatedAt }` — `schemas/entities/Setting.schema.json`, `samples/entities/Setting.json` | `{ roleId, permissionKey }` — `schemas/entities/RolePermission.schema.json`, `samples/entities/RolePermission.json` |

`samples/push-request.settings.json` is a real push (a changed receipt footer, a permission granted, one taken
away). **Key these rows by their payload**: a setting by (`scope`, `scopeId`, `key`), a permission by
(`roleId`, `permissionKey`). You may store the `entityId` we send; in a pull you may send it or any id — the
till works the id out from the payload itself. `value` is text exactly as the till stores it (`"true"`,
`"20"`, `"Thank you for shopping!"`), at most 4000 characters. `scope` is `company` (`scopeId` = the company id)
or `branch` (`scopeId` = the branch id); the till reads a setting register → branch → company → built-in default.

**Deny-list — these never leave the till and are never applied from a pull** (`src/SSPOS.Domain/Sync/SettingSyncPolicy.cs`;
`samples/settings-local-only.json` lists every catalogue key on each side):
- every `register`-scope row (one PC's own set-up: its printers, ports, scanner, drawer, screens, queues);
- every setting whose catalogue type is secret;
- every key starting `licence.`, `install.`, `sync.`, `server.`, `update.`, `backup.`, `devices.`, `printers.`,
  `payments.terminal_`, `payments.dna_`, `payments.dojo_`, `messaging.smtp_` or `messaging.whatsapp_gateway_`;
- every key starting `grid.layout.` or `help.tour_dismissed.` — one user's own screen preferences, stored under
  the **user's** id (new 2026-10-02: up to 0.1.31 they went up as `company` rows whose `scopeId` and envelope
  `companyId` were that user id — refuse those, they are not a second company);
- every key containing `secret`, `passphrase`, `thumbprint`, `api_key`, `private_key` or `signing_key`, or
  ending in `password`, `_key`, `.key`, `_hash` or `token`;
- every key ending in `_utc` — one PC's own bookkeeping time (when it last vacuumed its database, its clock
  watermark).
If you send one, the till skips it and logs it; it never overwrites the till's own value.

**Pull rules.** A company setting is applied only for the till's own company, a branch setting only for its own
branch (a blank `scopeId` means the till's own). `I`/`U` write the value; the same value again changes nothing;
`D` removes the row, so the wider scope or the built-in default applies again. A pulled setting is used by the
next action that reads it; a few till screens (layout, tile sizes) pick it up when they are next opened. A
`RolePermission` `I` grants the permission (if the role is not on the till yet, it waits for the `Role` row);
`D` takes it away. The till's system **Owner** role always keeps every permission: a `D` for it is refused, and
the till re-adds any missing Owner permission on every start.

**Push rules.** A row goes up whenever the shop changes a shared setting (only when the value actually changes)
or a role's permissions — saving a role's permission list sends only the differences (`I` per new grant, `D` per
removal). Once on upgrade, and again right after the §17.8 history upload completes, the till queues every
shared setting and every role permission it holds as `I`, so you receive the full current set. Conflicts follow
the portal-owned rule (§8, §19.3).

**Keys new or changed in 1.4 (owner, 2026-09-28).** No shape changes; show them in your role and settings editors.
- **Permission `sale.view_all_orders`** (`src/SSPOS.Domain/People/Permissions.cs`): the holder sees every staff
  member's sales in the till's receipt, Order List and refund look-ups; everyone else sees only the sales they rang
  up (`Sale.userId`). The seeded Manager and Owner roles carry it — a shop's existing seeded roles at Manager level
  and above get it once, on the next start, and the grant syncs like any other; a shop may take it off. Customer
  orders and held sales stay visible to all staff. It needs no other handling on the portal.
- **Setting `till.refund_needs_manager`** (group `till`, Bool, Branch scope, default `false`), "Ask a manager for
  refunds": on, every refund needs a Manager/Admin PIN before it completes.
- **Two defaults changed:** `till.manager_pin_refund_over` `20.00` → `0.00` (0 = never) and
  `till.refund_without_receipt_pin` `true` → `false`. A default is not a row: a shop that saved a value keeps it
  (you hold it as a `Setting` row); a shop that never saved one now reads the new default, and no row is sent for
  it. `samples/settings-local-only.json` lists every shared key (`sharedKeys`).

### 10.4 Customer order references and keys (revision 1.4, 2026-09-28)

- **Key every row by its `id`** (the ULID), `CustomerOrder` included — never by `reference`, `token` or a
  receipt number.
- `CustomerOrder.reference` is for people: **`CO-{branch code}-{till code}-{number}`**, e.g. `CO-LDS-02-000017`.
  The number comes from that till's own counter (`Register.nextOrderNo`, new column), so a reference is unique
  within its shop across all its tills, and two orders in the same second no longer share one. The till backs
  this with a unique index on (`branchId`, `reference`).
- Orders made before revision 1.4 keep their old `CO-yyyyMMdd-HHmmss` text. Where two orders of one shop had the
  same text, the upgrade kept it on the earliest and renamed the later ones `…-2`, `…-3`, and pushed them as `U`
  with a higher `rowVersion` — update your copy by `id`.
- Two shops can hold the same reference text only for those old orders, so show a reference with its shop.
- `token` (the collection-ticket code, six digits: the local time HHmmss, or the next code up when that one is
  taken) is unique only among a shop's **open** orders (`status` `ordered` / `ready`, not deleted) — the till backs
  this with a filtered unique index on (`branchId`, `token`). A collected, cancelled or expired order frees its code,
  so the same code comes round again; never key by it. Where two open orders of one shop already shared a code, the
  upgrade (migration CustomerOrderTokenUnique, 2026-09-29) kept it on the earliest, renamed the later ones `…-2`,
  `…-3` and pushed them as `U` with a higher `rowVersion`.
- Web orders (§12) carry your own reference: use a prefix the till never makes, e.g. `WEB-`.

### 10.5 `BranchPrice` — a shop's own price, set on the portal (revision 1.4, 2026-09-29)

A price for **one shop**, made on the portal (Business panel "Shop prices"). Portal-owned (`"hub"`): you write it,
the till applies it, the till never edits or pushes it. Schema `schemas/entities/BranchPrice.schema.json`, sample
`samples/entities/BranchPrice.json`, a real pull `samples/pull-reply.head-office.json` (two Leeds prices for the
white loaf: £1.25 through October, then £1.39 from 1 November).

- **Envelope:** `entity: "BranchPrice"`, `branchId` = the shop (a row for another shop is skipped by that till),
  `op` `I`/`U`/`D`, `version` = your pull counter, as for every pulled row.
- **Fields** (camelCase, all present): `id` (your ULID), `companyId`, `branchId` (the shop — must equal the
  envelope's), `productId`, `productUnitId` (`null` = the product's base unit; else the `ProductUnit` row id — a
  case or pack price), `price` (inc VAT, £, **2 dp**; the till rounds half away from zero), `validFromUtc` (UTC,
  inclusive), `validToUtc` (UTC, exclusive; `null` = until changed), plus the standard `createdAt`, `updatedAt`,
  `rowVersion`, `deletedAt`. Derived members in the sample (`priceIncVat`, `isDeleted`) are ignored when read.
- **Whole row every time** (§5 upsert). To end a price early send it again with `validToUtc`; to remove it send
  `op: "D"` with the row (`deletedAt` set). Several rows for one product (or unit) may exist — e.g. an October
  offer and a new price from November: the **live** one (not deleted, `validFromUtc ≤ now < validToUtc`) with the
  **latest `validFromUtc`** wins, then the higher `id`. A row that arrives before its `Product` waits for it
  (parked, §8), so order does not matter — but send the product first.
- **Idempotent** by `id` + `version` like every pulled row: the same version twice, or the same content at a newer
  version, changes nothing on the till.
- **Precedence on the till** — one rule wherever a shelf price is chosen (scan, tile, price check): scale-label
  embedded price → price-marked pack (PMP, the law; the till's PMP rule still applies) → **live `BranchPrice`** →
  the product's (or unit's) own price. The till's own `BranchProduct.priceOverride` is not a selling price (no
  till screen sets it; only the stock list's valuation reads it) and never competes with `BranchPrice`. The
  product form shows the price read-only: *"This shop: £1.25 — Set on the portal"*.
- **Speed:** the shop's prices sit in memory beside the barcode index and are patched row by row as a pull saves
  them; a 5,000-row price book keeps scan → line inside 50 ms (p99 80 ms) — `specs/performance.md`.
- **Where it applies — every till and every label of the shop:** the main (or only) till applies your rows from
  the pull; the main till copies the shop's live and future prices to every **secondary till** over the shop LAN
  when it joins and at every heartbeat (about every 20 seconds; store protocol stays 3 — an optional call), and a
  secondary till keeps selling at them while the main till is unreachable. Shelf-edge labels, A4 label sheets, the
  Barcode List, electronic shelf labels and customer orders use the same price by the same rule; the **scale PLU
  export** sends the shop's live price, else the product's own (never a price-marked-pack price — a scale weighs
  loose goods). Secondary tills never talk to the portal, so nothing extra reaches you.

### 10.6 Head-office purchase orders — the portal drafts, the shop receives (revision 1.4, 2026-09-29)

`PurchaseOrder` and `PurchaseOrderLine` stay **branch-owned**: a shop's own orders come up in `push` and must never
be sent down. The one addition (`"hubDrafted"` in `samples/ownership.json`): you may also **draft an order for one
shop** and send it down in that shop's `pull`, exactly like a relayed transfer; the shop then owns everything that
happens next. Sample `samples/pull-reply.head-office.json` (the supplier, then order `HO-000123` for Leeds with two
lines), `samples/entities/{Supplier,PurchaseOrder,PurchaseOrderLine}.json`; enums `PurchaseOrderOrigin`
(`branch`, `headOffice`) and `PurchaseOrderStatus` in `samples/enums.json`.

- **Order row** (`entity: "PurchaseOrder"`, envelope `branchId` = the shop): the full row with
  **`origin: "headOffice"`** (anything else is refused), `branchId` = the shop, `supplierId` (send the `Supplier`
  first — it is portal-owned master data), `number` = **your** per-shop head-office order number (unique per shop
  among head-office orders: a second order with a number the shop already holds is refused by the till's database
  and logged; the till shows it as `HO-000123` and never gives it one of its own `PO-` numbers), `status` = `sent`
  (placed with the supplier — the shop can receive at once), `draft` (a heads-up; not receivable until you send it
  again as `sent`) or `cancelled` (withdrawn before any goods arrive), `expectedDate`, `sentAt`, `notes`,
  `netTotal` / `vatTotal` / `grossTotal` (ex VAT net + VAT = gross, 2 dp), `discountAmount`. `sentByUserId`,
  `cancelledByUserId` may be `null` (your users are not till users).
- **Line rows** (`entity: "PurchaseOrderLine"`, envelope `branchId` = the shop; the line itself has no
  `branchId`): the full row — `purchaseOrderId` = your order's id, `productId`, `position`, `orderedCases`,
  `caseQtySnapshot`, `orderedUnits` (= cases × case size + loose units), `unitCostSnapshot` (ex VAT), `vatRateId`,
  `vatPercentage`. **`receivedQty` is never read from a pull** — only the shop's goods-in writes it (send `0`). A
  line that arrives before its order waits for it (§8). A line never moves to another order. A line whose order is
  held for a different shop, or whose envelope `branchId` names a different shop from its order's, is refused
  (2026-09-29).
- **Show `reference`, not `orderNo` (2026-09-29):** `number` is unique per shop only, so two shops both have a
  `PO-000001`. Every `PurchaseOrder` row now carries **`branchCode`** (the shop's code, e.g. `LDS`, written by the
  till from its own `Branch` row — never read from a pull; send `""` or leave it out) and **`reference`**
  (read-only, `PO-{branchCode}-{number}` / `HO-{branchCode}-{number}`, e.g. `PO-LDS-000001`, `HO-LDS-000123`) — the
  same shape as a receipt number and a customer-order reference (§10.4). Show `reference` in the portal. Nothing was
  renumbered: `number` and `orderNo` (`PO-000001`, what the till prints) are unchanged; existing orders took their
  shop's code on the upgrade (migration PurchaseOrderBranchCode) and were pushed again as `U` with a higher
  `rowVersion`. An order with no shop code shows `reference` = `orderNo`. Key by `id` as always.
- **Receiving:** the shop sees the order in Purchasing marked "From head office" and books goods in against it
  with the normal goods-in (GRN). The `GoodsReceipt` / `GoodsReceiptLine` rows (stamped with the shop's
  `branchId`), the order's new `status` (`partReceived` / `received`, later `invoiced` / `paid`) and the lines'
  `receivedQty` come up in `push` as the shop's own rows. The shop cannot change a head-office order's lines,
  quantities, prices or discounts (those keys are greyed: "its lines, quantities and prices are changed on the portal").
- **Send and Cancel at the shop (owner, 2026-09-28):** the shop may Send or Cancel a head-office order; the status
  (`sent` / `cancelled`) comes back to you in `push` as the shop's own change. After the shop sent or cancelled it (or
  started goods-in), your edits to it are refused and raised as a conflict — draft a new order instead. A `status`
  that would re-open a cancelled order is refused the same way.
- **Idempotent:** the same order (or line) relayed twice — same version, or same content at a newer version — is a
  no-op: no second order, no change, no echo in `push`.
- **Changes after the shop sent, cancelled or started receiving it are refused and flagged.** Until then you may
  change or cancel the order freely (send the whole row again). Once the shop has sent or cancelled it, or opened or
  posted a goods-in against it (or it is `partReceived` or further on), any change you send to the order or its
  lines is **refused** — nothing is written
  over the received quantities — and **flagged** on the shop's Sync status screen as a clash (`SyncConflict`,
  entity `PurchaseOrder` / `PurchaseOrderLine`, detail naming `HO-…`), once per version. An id that is one of the
  shop's own orders is never touched.

### 10.7 Secrets never leave the till (revision 1.4, 2026-09-28)

- **`User.remoteApprovalSecret` and `User.remoteApprovalSecretSetAt` are gone from every JSON** — push, the §17.8
  history upload, `schemas/entities/User.schema.json`, the samples. The key a manager's own code-reading device
  holds never leaves the till; a pulled `User` row that carries either field is ignored for it. Drop both columns
  from your copy and delete any values already received from test pushes.
- **`pinHash` still travels** (PBKDF2, never the PIN) so the portal can create staff. A pulled `User` row whose
  `pinHash` is missing, `null` or empty **keeps the till's PIN** — send it only to set or change a PIN. The same
  for `rfid` (v1.4.1): missing, `null` or empty keeps the member of staff's fob; a fob is removed at the till.
  **Format (2026-10-01):** `pbkdf2$<iterations>$<base64 salt>$<base64 subkey>` — PBKDF2-HMAC-SHA256 over the PIN's
  UTF-8 bytes, write 100000 iterations, 16-byte random salt, 32-byte subkey, standard Base64 (with `=`), no pepper,
  ≤ 200 chars. The till reads the iteration count and subkey length from the string. **Not** ASP.NET Identity v3
  (`AQAAAA…` blobs are refused — the PIN would never work). Sample: PIN `1234` =
  `pbkdf2$100000$AAECAwQFBgcICQoLDA0ODw==$hp5sg1DFvrCsw5n7qsO2DSIEM4lrJqZHc00NjxWG4fo=`
  (`src/SSPOS.Infrastructure/Security/Pbkdf2PinHasher.cs`; the sample is pinned in `Pbkdf2PinHasherTests`).
- **Settings:** the §10.3 deny-list (secrets, keys, device and licence settings, `sync.*`) never leaves the till
  and is never applied from a pull.
- **Keys and codes on the wire** — the sync key, a licence key, an activation or sync code, a licence token — go
  only in the `Authorization` header or the JSON body of the call that needs them, never in a URL or a log line on
  either side (§17.11 rule 12).
- One home on the till: `src/SSPOS.Domain/Sync/SyncSecretColumns.cs` (a test fails the day a synced table gains
  a column that looks like a secret and is not listed).

## 11. What the portal must never do

1. Change or delete a completed sale, sale line, payment, refund, VAT row, journal row or audit row
   (`specs/invariants.md` rule 5: they are historically immutable; the till's database refuses such
   updates). Corrections are new rows made on the till (a refund, a void), never edits.
2. Send any till-owned entity down (section 10) — the only exception is relaying the tables of §10.2,
   unchanged, to the other branch they concern; never back to the branch that owns them.
3. Send a price or money value with more than 2 decimal places.
4. Send a row with no `companyId`, or a branch row with no `branchId`.
5. Re-key a row, reuse an id for a different row, or send a numeric enum.
6. Send one branch's rows to another branch (other than the §10.2 relays), or send any setting on the
   §10.3 deny-list (`sync.hub_api_key`, any secret, device, licence, install or sync key) in a `Setting` row —
   the till refuses it.
7. Write `Customer.balance` / `Customer.points` expecting the till to take them — they are worked out from the
   ledger on each side (§10.1).
8. Send down a shop's **own** purchase order, a `PurchaseOrder` with any `origin` but `headOffice`, a
   `receivedQty`, or a change to a head-office order after the shop sent, cancelled or started receiving it
   (§10.6) — the till refuses them (and flags the last one).
9. Ask for, store or send a secret the till keeps to itself (`remoteApprovalSecret`, a deny-listed setting —
   §10.7), or put a key, code or token in a URL.
10. Reuse an `Idempotency-Key` answer for a different body, or store a 408 / 409 `request.in_progress` / 429 /
    502 / 503 / 504 reply under a key — the till repeats those requests with the same key (§17.11 rule 5).

## 14. How to test against the till

The till side is built and speaks HTTPS to your server (§16 lists what is built). Test in this order:

1. **Before your server is up:** build against `samples/` and `schemas/` (JSON Schema draft 2020-12) and run the
   Postman collection against a **Postman mock server** made from it — every request has saved example replies.
   Validate every reply you produce against its schema.
2. **Point a test till at your server.** Send us your test base URL (HTTPS with a publicly trusted certificate —
   the till refuses `http://` and self-signed certificates) and we give you an installer with that address built
   in. On an installer with another address, set **Settings → Licence → Licence server** and **Settings → Network →
   Cloud sync → Advanced → Hub address** to your URL instead (advanced overrides, section 1).
3. **Licence:** in the first-run wizard (or Settings → Licence → Enter key) type a licence key your test portal
   issued → your `POST /api/v1/licence/activate` receives a body shaped like
   `licensing/samples/licence-activate-request.json`, with the till's own ids in `existingIds` and the headers.
   **Check again** on Settings → Licence sends `licence/validate` at once.
4. **Sync:** on the branch's main till, Settings → Network → Cloud sync → **Sync key** → **Connect** with the
   branch's sync key (a till that never synced goes `cloud/migrate` → `sync/hello` → history upload through
   `sync/push` in initial mode → `cloud/migrate/complete`; one that synced before says `sync/hello`) — or return
   `apiKey` in your `licence/activate` reply and the till connects by itself (17.3 step 3).
5. **Push:** ring a sale, then Sync status → **Sync now** (or wait 30 s). Your `POST /api/v1/sync/push`
   receives a gzip body shaped like `samples/push-request.json`.
6. **Pull:** return `samples/pull-reply.json`, `pull-reply.relay.json` or `pull-reply.head-office.json` from
   `GET /api/v1/sync/pull` **with the test till's own `companyId` and branch ids in place of the samples'** (the
   till skips rows for another business or shop — they are named in its log); return
   `samples/pull-reply.empty.json` when nothing is new. The Sync status screen shows the rows as applied (or as
   conflicts).
7. **What the till shows and logs:** the Sync status screen shows pending rows, last sent / acknowledged / reached
   the portal (your `receivedAt`), last error (your `message`) and conflicts. The log is
   `%ProgramData%\SSPOS\logs\*.log`: one line per call (path, status or code, rows, acknowledged seq or highest
   version) and one per pulled row skipped, parked or refused, with the reason. Keys, codes and tokens are never
   written to the log.
8. Run the **guarantees checklist** (§21) before a real shop is connected.

>
> **Changed 2026-09-28 (owner): a key carries the shop — read 17.16 and `docs/web-portal-api/KEY-CARRIES-SHOP.md`.**

> **reports** it to `licence/redeem`, and the same key seen from a second PC gets 409 `key.used_on_another_install`.

Owner decisions: `specs/licensing.md` (2026-09-26). This section turns them into endpoints. Schemas are in

### 17.1 The idea in five lines

1. The portal is the **issuer**: it decides who may trade, for how long, with how many tills and which paid features.
2. It says so in a **signed licence token** that the till checks **offline**. The till never needs the portal to
   ring a sale; it needs a valid token and, for a cloud licence, a successful check at least every 14 days.
3. **Every till licenses itself** (17.15, which replaced the branch model): each till activates its own key and
   validates daily for itself; any till may redeem a key or release itself. **Sync** stays the branch's main
   till's alone (section 2.2): the other tills join it over the shop LAN and never push or pull.
4. A **licence problem is never an HTTP error**: `licence/validate` answers 200 with a `status`, so the till always
   gets the portal's time, messages and (maybe) a fresh token.
5. Everything is **additive**: new fields, new features, new limits, new endpoints never break an older till (17.11).

| Endpoint | Auth | Called when |
|---|---|---|
| `POST /api/v1/licence/activate` | the licence key in the body | **any** till: the shop pastes the e-mailed key (17.15) |
| `GET /api/v1/sync/hello` | branch key | before the first push/pull; Connect with a sync key that synced before (section 4.1) |
| `POST /api/v1/licence/validate` | none needed (the held token + `installId` identify the till; the branch key is sent when held) | **every** till for itself: daily, at start-up when overdue, "Check again" (17.15.2) |
| `POST /api/v1/licence/redeem` | branch key; **none** for a local key report | a licence key typed or pasted at a linked till; a till holding a local key reports it once (17.6, 17.16) |
| `POST /api/v1/devices/deactivate` | branch key when held | "Deactivate this till" on Settings → Licence: a till removed; the main till moving to a new PC |
| `POST /api/v1/cloud/migrate` | the sync key (`activationCode`) in the body | Connect with a sync key on a branch that never synced (route A of `SIMPLE-SETUP.md`); a local-licence shop moving to the cloud |
| `POST /api/v1/sync/push` (initial mode) | branch key | the history upload after `migrate` |
| `POST /api/v1/cloud/migrate/complete` | branch key | after the last upload batch |
| `POST /api/v1/devices/activate` | activation code in the body | **Not called by the till** (17.4 — reference only) |

### 17.2 The licence token

#### Format (exactly `specs/licensing.md` section 1)

```
SSPOS1.<base64url(payload JSON)>.<base64url(Ed25519 signature over ASCII "SSPOS1." + payload part)>
```

- `base64url` = RFC 4648 section 5 alphabet (`-` and `_`), **no `=` padding**.
- The payload is UTF-8 JSON, camelCase. Write it compact; field order and spacing do not matter because the
  signature covers the **base64url text**, not a re-serialisation. **Never re-serialise to verify.**
- Ed25519 (RFC 8032, pure, no pre-hash). Signature = 64 bytes = 86 base64url characters.
- A token is **not secret** (signed, not encrypted): the till shows its fields. It is typically 700–900 characters.
  The till accepts it with line breaks or spaces pasted in (it strips whitespace).
- The till's reference implementation is `src/SSPOS.Infrastructure/Licensing/LicenceTokens.cs` (BouncyCastle);
  the payload type is `src/SSPOS.Domain/Licensing/LicenceClaims.cs`.

#### Payload fields (`licensing/schemas/licence-token-payload.schema.json`)

| `v` | integer | `1`. A till refuses a higher `v` (`licence.unsupported_version`). |
| `kid` | string | Signing key id. Convention: `"k"` + first 8 lower-case hex digits of SHA-256(raw 32-byte public key), e.g. `k13799fa4` (`LicenceTokens.KidFor`). |
| `licenceId` | ULID | The licence. A renewal, extension or change is a **new token with the same `licenceId`**. |
| `kind` | `trial` \| `full` | |
| `source` | `portal` \| `local` | `portal` = you; `local` = our licence generator (`tools/licence-generator`). |
| `issuer` | string | Shown on the licence screen, e.g. `SSPOS Portal`. |
| `companyId`, `branchId` | ULID | **Required for `portal`** — the till refuses a portal token for another company/branch. A local key may leave them blank. Since 2026-09-28 **every till key of one shop carries the same `companyId` and `branchId`** (portal and local alike, 17.16). |
| `businessName`, `branchName` | string | Shown on the licence screen; the first-run wizard starts from them (shop name, branch name). |
| `installCode` | `XXXX-XXXX` | `portal` (per till, 17.15): the activating till's code. `local`: the install it was made for; **absent/empty = an open local key** (17.16) — the first till that accepts it binds it to itself. |
| `maxRegisters` | integer ≥ 1 | Tills allowed in this branch, **main till included**. The same value in every till key of the branch. |
| `features` | string[] | Open list of paid feature names (`^[a-z0-9]+([._-][a-z0-9]+)*$`; **the till knows exactly these 11** (`src/SSPOS.Application/Ports/Feature.cs`, 2026-09-28): `loyalty`, `promotions`, `purchasing`, `accounts`, `multi_branch`, `second_screen`, `label_printing`, `assist`, `cloud_sync`, `assist_invoice_scan`, `assist_questions` — an unknown name is ignored; compared exactly, so `multi-branch` is **not** `multi_branch`). `multi_branch` = the company may add branches. `full`: exactly these (absent/`[]` = none). `trial`: absent/`[]` = **every feature on**; a non-empty list = only those. |

Tills are not a limit — they are `maxRegisters`. |

|---|---|

**The details only start the wizard.** The till pre-fills its first-run wizard from `businessName`, `branchName` and
`company`; the shop may change any of them there or later on the till, and the result syncs up like any other
**Company / Branch** change (section 10). **A later token never overwrites them** — a renewal carrying different
details changes nothing on a till that has finished its first run. So after first run the synced Company/Branch rows
are the truth, not your licence form; keep the form for new keys.

**Unknown fields are ignored** by every till, so you may add fields at any time. Absent, `null` and `""` mean the
same thing to the till; an older key without `company` or `limits.branches` still works. Samples:
`licence-token.payload.{trial,full,local}.json` (no company block), `licence-token.payload.per-till.json` (portal,
with the company block) and `licence-token.payload.local-open.json` (open local key, with the company block).

#### How a till (and your redeem/migrate code) verifies a token

1. Strip whitespace. It must start with `SSPOS1.` and have exactly three dot-separated parts.
2. base64url-decode part 2 and parse it as JSON (untrusted so far). `v` > 1 → `licence.unsupported_version`.
3. Look up `kid` in the trusted (built-in) keys. Not there → if the token has `signerCert`, check the certificate
   (17.17) and use the public key it carries; bad, from a non-approver, for another kid, or ended before the
   token's `issuedAt` → `licence.bad_signer_certificate`. No `signerCert` → `licence.unknown_key`.
4. Verify the Ed25519 signature (part 3) over the ASCII bytes of `"SSPOS1." + part 2` → fails: `licence.bad_signature`.
5. Only now trust the fields: `validFrom ≤ now ≤ expiresAt` (the till uses the later of its clock and its
   clock watermark / last portal time), then the binding (`local`: `installCode` = this install's, or — an open
   key — the install code the till bound it to when it first accepted it; `portal`: `installCode` = this install's
   for a per-till token (17.15), else `companyId`/`branchId` = this till's), then `maxRegisters`, `features`,
   `limits`, `onlineCheck`. For a local key **report** your `redeem` code checks steps 1–4 only (it records an
   expired key too); the binding is what the report itself establishes (17.16).

#### Keys: who holds what

- **You generate your own Ed25519 key pair.** The private key never leaves the portal's server side (a KMS/HSM or
  an encrypted secret store — never the database in plain text, never a repository, never an e-mail).
- **You send us the public key and its kid** (`licensing/samples/public-key-handover.json`: `kid`, `alg`,
  `publicKeyBase64Url` = raw 32 bytes, optional PEM). **We send back a signer certificate** (17.17) — we do NOT
  build your key into the till, so no till release is ever needed for it. You put the certificate in every token
  (`signerCert`). A till trusts a **list** of built-in kids (one per licence-generator installation) plus any key
  one of its **approvers** certified.
- **We send you every generator public key + kid**, so your `redeem` and `migrate` can verify local tokens. You
  verify with them; you never sign with them.
- **Rotation** (planned or after a leak): make a new pair → send us the public key → we send a certificate for it →
  sign with the new key and its certificate at once (no till release; every till already trusts the approver).
  Tokens are re-issued at the next daily check. A leaked key is withdrawn by kid (`RetiredAfter` cut-off) in the
  next release; tokens it made before the cut-off keep working. Every request that can receive a token carries
  `trustedKids` (built-in kids) and `approverKids` (built-in kids whose certificates the till accepts): **sign a
  returned token with a kid in `trustedKids`, or with your certified key when its certificate's `approvedBy` is in
  `approverKids`.**

#### Signing and verifying — code

The PHP and Node snippets below were run against the worked example and reproduce its token exactly.

**PHP / Laravel** (ext-sodium, bundled with PHP ≥ 7.2):

```php
function b64u(string $bin): string { return sodium_bin2base64($bin, SODIUM_BASE64_VARIANT_URLSAFE_NO_PADDING); }
function b64u_decode(string $s): string { return sodium_base642bin($s, SODIUM_BASE64_VARIANT_URLSAFE_NO_PADDING); }

// once: make the key pair, keep $secret server-side, send us $public + $kid
$pair   = sodium_crypto_sign_keypair();
$secret = sodium_crypto_sign_secretkey($pair);            // 64 bytes (seed + public) - SECRET
$public = sodium_crypto_sign_publickey($pair);            // 32 bytes - send b64u($public)
$kid    = 'k' . substr(hash('sha256', $public), 0, 8);

function sspos_sign(array $payload, string $secret64): string {
    $part  = b64u(json_encode($payload, JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE));
    $input = 'SSPOS1.' . $part;
    return $input . '.' . b64u(sodium_crypto_sign_detached($input, $secret64));
}
// from a stored 32-byte seed instead: sodium_crypto_sign_secretkey(sodium_crypto_sign_seed_keypair($seed32))

function sspos_verify(string $token, array $publicKeysByKid): ?array {   // for redeem / migrate
    $parts = explode('.', preg_replace('/\s+/', '', $token));
    if (count($parts) !== 3 || $parts[0] !== 'SSPOS1') return null;
    $payload = json_decode(b64u_decode($parts[1]), true);
    $key = $publicKeysByKid[$payload['kid'] ?? ''] ?? null;
    if (!is_array($payload) || $key === null) return null;
    return sodium_crypto_sign_verify_detached(b64u_decode($parts[2]), 'SSPOS1.' . $parts[1], $key) ? $payload : null;
}
```

**Node.js** (built-in `crypto`, Node ≥ 16):

```js
const crypto = require('crypto');

// once: make the key pair
const { publicKey, privateKey } = crypto.generateKeyPairSync('ed25519');
const rawPublic = Buffer.from(publicKey.export({ format: 'jwk' }).x, 'base64url');   // send rawPublic.toString('base64url')
const kid = 'k' + crypto.createHash('sha256').update(rawPublic).digest('hex').slice(0, 8);
// store privateKey.export({ format: 'pem', type: 'pkcs8' }) in your secret store

function ssposSign(payload, privateKey /* KeyObject */) {
  const part = Buffer.from(JSON.stringify(payload), 'utf8').toString('base64url');
  const input = 'SSPOS1.' + part;
  return input + '.' + crypto.sign(null, Buffer.from(input, 'ascii'), privateKey).toString('base64url');
}
// from a raw 32-byte seed: crypto.createPrivateKey({ key: Buffer.concat([Buffer.from('302e020100300506032b657004220420', 'hex'), seed]), format: 'der', type: 'pkcs8' })

function ssposVerify(token, publicKeysByKid /* kid -> raw 32-byte Buffer */) {
  const [pfx, part, sig] = token.replace(/\s+/g, '').split('.');
  if (pfx !== 'SSPOS1' || !part || !sig) return null;
  const payload = JSON.parse(Buffer.from(part, 'base64url').toString('utf8'));
  const raw = publicKeysByKid[payload.kid];
  if (!raw) return null;
  const key = crypto.createPublicKey({ key: { kty: 'OKP', crv: 'Ed25519', x: raw.toString('base64url') }, format: 'jwk' });
  return crypto.verify(null, Buffer.from('SSPOS1.' + part, 'ascii'), key, Buffer.from(sig, 'base64url')) ? payload : null;
}
```

**C# / .NET** (package `BouncyCastle.Cryptography`, as the till; or reuse `LicenceTokens.CreateKey` / `Sign`):

```csharp
using System.Buffers.Text;                       // Base64Url, .NET 9+
using System.Text;
using System.Text.Json;
using Org.BouncyCastle.Crypto.Parameters;
using Org.BouncyCastle.Crypto.Signers;

static string Sign(object payload, byte[] privateSeed32)
{
    byte[] json = JsonSerializer.SerializeToUtf8Bytes(payload, new JsonSerializerOptions(JsonSerializerDefaults.Web));
    string part = Base64Url.EncodeToString(json);
    byte[] input = Encoding.ASCII.GetBytes("SSPOS1." + part);
    var signer = new Ed25519Signer();
    signer.Init(true, new Ed25519PrivateKeyParameters(privateSeed32, 0));
    signer.BlockUpdate(input, 0, input.Length);
    return "SSPOS1." + part + "." + Base64Url.EncodeToString(signer.GenerateSignature());
}
// kid: "k" + Convert.ToHexStringLower(SHA256.HashData(publicKey32), 0, 4)
```

### 17.3 Onboarding, end to end

**Updated 2026-09-28 (owner): per-till keys, a key is required, one code for the shop.** The till does **not** call
`devices/activate` (17.4 is kept for reference only — do not build it). The shop types only a **licence key** per till,
plus a **sync key** only if it adds the dashboard later (`docs/web-portal-api/SIMPLE-SETUP.md`).

```
Owner              Portal                                   Main till                        Other tills
  | sign up -------> | Company + Branch + a TRIAL licence     |                                 |
  |                  | key per till (length per customer)     |                                 |
  | <-- e-mail: licence key(s) + installer link               |                                 |
  | install, wizard step 1 "Licence key" (required) --------->|                                 |
  |                  | <------ POST licence/activate ---------| existingIds = the till's OWN ids |
  |                  | ------- token (+ apiKey if dashboard)->| stores token; apiKey → Cloud     |
  |                  |                                        | sync ON (no second code)         |
  |                  | <------ GET sync/hello, push / pull -->| every 30 s                       |
  |                  |                                        | <-- LAN join ---- own key, own licence/activate
  |                  | <------ POST licence/validate daily, EVERY till for itself ---------------|
```

1. **Sign-up (portal).** Create the Company, its first Branch and **one trial licence key per till** (length per
   customer — there is no built-in trial on the till any more). E-mail the key(s) and the installer link.
2. **Wizard (till).** Step 1 "Licence key" — required; Skip is greyed.
3. **`licence/activate`** (17.15.1). **Ids (owner, 2026-09-28): the till always keeps its OWN ids** (ULIDs made at its
   first start) and sends them as `existingIds`; it never adopts yours. Every synced row carries the till's ids.
   - First activation of a new customer's first branch → **adopt**: create/re-key your Company and Branch rows to the
     till's `existingIds.companyId` / `branchId` (your sign-up rows have no data yet), or keep a mapping table.
   - A **second branch** of an existing company → its main till made its own `companyId` → **alias** it to your
     company (store `till companyId → your companyId`, translate rows at your edge, 17.8 rule). Its `branchId` is
     adopted as the new branch.
   - **Bind every key to the branch you issued it for** (you know that from your own records), not by
     `existingIds`; identify a till by `installId` (stable per PC) and record its `registerId`.
   - The **token's** `companyId` / `branchId` are **your** customer ids, the same in every key of the branch — the
     till only compares key to key (two tills of one shop must name the same company/branch).
   - **One code for the dashboard:** when the licence includes the dashboard (`cloud_sync`), put **`apiKey`** (the
     branch's sync key) at the top level of the `licence/activate` / `licence/validate` reply — and `hubUrl` only if
     sync runs on another host than the built-in address. The till stores it and turns Cloud sync on. If you also send
     `companyId` / `branchId` next to it they must be **the till's own ids or blank** (a link naming other ids is
     ignored). `settingsBootstrap` is not read from this reply — settings reach the till by `pull` (v1.4).
4. **More tills.** Each further till of the branch has its **own licence key**, calls `licence/activate` itself and
   joins the main till over the LAN; only the main till syncs. A second **branch** is a new main till with its own keys.
5. **Daily check** (17.5 / 17.15.2) from **every** till for itself. The token's `onlineCheck` sets the rhythm and the 14-day grace.
6. **Lock rules** (17.9): trial over, expired, revoked, suspended, 14 days without a successful check, clock
   tampering, seats exceeded → the till finishes the sale in progress, then shows the lock screen (enter a key /
   Check again; backup and export; the support number — nothing else).

**Local-only path (no portal):** since 2026-09-28 a new install needs a key in the first-run wizard (Skip is
greyed) — a dealer's trial key or a portal key; the built-in 7-day trial only runs out on installs that already
started it. For a bound key the owner reads the **install code** off the licence screen (`XXXX-XXXX`, derived from the install id —
`src/SSPOS.Domain/Licensing/InstallCode.cs`) to the dealer, who makes a `local` token with the licence generator;
the owner pastes it. Since 2026-09-28 the dealer may also make an **open** key (no install code) that binds to the
first till that accepts it, and the key may carry the shop's details for the wizard (17.16). The till needs no
portal to trade; **when a licence server is set and reachable it reports the local key once** to
`licence/redeem` (17.6, 17.16). Later the shop can move to the cloud with `cloud/migrate` (17.8); days left on the
local token carry over.

### 17.4 `POST /api/v1/devices/activate`

> **Not called by the till (2026-09-28) — do not build it.** Kept for reference only; superseded by per-till
> `licence/activate` (17.15.1) plus the dashboard link in its reply or a sync key (17.3 step 3, `SIMPLE-SETUP.md`).

**Auth:** none. The **activation code is the credential** — treat it like a password: ≥ 60 bits random, stored
hashed, single use, expiring, rate-limited (17.12). **Headers:** `X-SSPOS-Contract`, `X-SSPOS-App-Version`,
`X-SSPOS-Install-Id`, `Idempotency-Key`. Only a branch's **main** till activates.

**Request** (`activate-request.schema.json`; samples `activate-request.json`, `activate-request.replacement-pc.json`):

| Field | Meaning |
|---|---|
| `activationCode` | From the e-mail (or a transfer code, 17.7). Trimmed and upper-cased by the till. |
| `installId` | ULID made once on this PC at first run (survives updates). Identifies the PC, not the register. |
| `installCode` | `InstallCode.From(installId)` on the till — the code shown on the licence screen. Store it as sent; never work it out or check it yourself (some sample pairs are illustrative, not derived). |
| `deviceName`, `appVersion`, `os {name, version, architecture}` | For the portal's device list. |
| `tillClockUtc` | The till's clock, so you can record the skew. |
| `trustedKids` | Kids this till build trusts — sign the returned token with one of them. |
| `registerName` | Name typed in the wizard, or null (portal default "Till 1"). |
| `existingIds` | null on a fresh install. `{companyId, branchId, registerId}` when the till already holds data (a restored backup on a replacement PC). |
| `localLicenceToken` | null, or the local token in use (a local trial being upgraded before any trading). Verify it (17.2); you may honour its remaining days. |

**Portal logic:**
1. Look the code up (hash). Unknown → 404 `activation.code_not_found`; expired → 410 `activation.code_expired`;
   used by **another** `installId` → 409 `activation.code_used`. The **same** `installId` within 24 h → return the
   **same 200 reply** again (the till may have crashed after you committed).
2. Account suspended/revoked → 403 `licence.not_active`.
3. `existingIds` set: must be the code's branch → reuse those ids (the portal already has the data; push resumes from
   the till's own cursor, you dedupe). Different branch → 409 `activation.use_migrate`.
4. The branch already has an active main till (not deactivated) and this is not its transfer code → 409
   `device.branch_already_linked` (with `details.deviceName`, `lastSeenUtc`).
5. Registers in use for the branch ≥ `maxRegisters` → 403 `licence.seat_limit`.
6. Create the register (a new ULID, `isMain: true`) unless reusing one; issue a **new** branch API key (store only its
   hash; revoke older keys of the branch); sign the licence token; mark the code used.

**Reply 200** (`activate-reply.schema.json`, `activate-reply.json`): `companyId`, `branchId`, `registerId`, `isMain`,
`hubUrl` (base URL for every later call), `apiKey` (shown once — you cannot show it again), `licenceToken`,
`licence` (plain summary; the token wins), `settingsBootstrap` (open object: `company`, `branch`, `register`,
`settings` = till setting keys from `src/SSPOS.Domain/Common/SettingKeys.cs` → values; never a secret, never
`sync.hub_api_key`; the till applies what it knows and ignores the rest), `portalTimeUtc`,
`nextCheckAfterSeconds`, `messages`.

**Errors:** 400, 403 (`licence.seat_limit`, `licence.not_active`), 404, 409 (`activation.code_used`,
`device.branch_already_linked`, `activation.use_migrate`), 410, 422 (`licence.*` for a bad `localLicenceToken`),
426, 429 (`activation.too_many_attempts`), 500, 503.

### 17.5 `POST /api/v1/licence/validate` — the daily check and heartbeat

> **What this till version sends is the per-till form of 17.15.2** — every till for itself, no branch key needed,
> no `registers[]` / `lastSyncAt` / `diagnostics`. It checks once `onlineCheck.intervalHours` have passed since its
> last successful check (a 15-minute timer; no jitter), at start-up when due and on **Check again**; an unanswered
> check is repeated at the next 15-minute tick with the **same** `Idempotency-Key` and body (17.11 rule 5), and the
> daily alert shows until one succeeds. Of the reply this till acts on `status`, `licenceToken`, `portalTimeUtc`,
> `messages` and the dashboard link (`apiKey`, `hubUrl`, 17.3 step 3); `licence` (a display summary — the token
> wins), `registers`, `minimumAppVersion` and `nextCheckAfterSeconds` are not acted on yet — send them anyway, they
> are safe to add. The branch-model text below (heartbeat for the whole branch, seats) is kept for reference.

**Auth:** branch key + every section 3 header + `Idempotency-Key`. Sent by the **main till only**, once per
`onlineCheck.intervalHours` (plus up to 60 minutes of random jitter), at start-up when a check is overdue, and when
the owner presses **Check again**. Honour `nextCheckAfterSeconds` from the last reply (e.g. 3600 while revoked).
On a network failure the till retries after 5, 15 and 60 minutes, then hourly, and shows the daily alert
"Your licence has not been validated with the server — connect the internet".

**Request** (`validate-request.schema.json`, `validate-request.json`): `licenceId`, `tokenSha256` (of the token it
holds), `appVersion`, `trustedKids`, `tillClockUtc`, `clockWatermarkUtc` (the latest time it has ever seen),
`lastValidatedAtUtc`, `lastSyncAt`, `lock {locked, reason}` (reason — an open list; this till sends `trialOver`,
`expired`, `revoked`, `offlineTooLong`, `clockTampering`, `seatsExceeded`, `wrongInstall`, `wrongBranch`,
`wrongCountry` (2026-10-07, 17.18) or `other`; `suspended` is reserved), `registers[]` (**every** till of the
branch: `registerId`, `code`, `name`, `isMain`, `appVersion`, `installId`, `deviceName`, `lastSeenUtc`,
`isActive`), `diagnostics` (open object for support: `pendingSyncRows`, `lastSyncError`, `databaseSizeMb`, …).

**Portal logic:**
1. Record the check-in: time, till clock and skew, lock state, diagnostics, app versions. Upsert every register
   (first seen, last seen, version, device); a register you have never seen is a till that joined the main till —
   that is how you learn about secondary tills. The register named by `X-SSPOS-Register-Id` must be reported with
   `isMain: true`, else 403 `device.not_main_till` (a promoted main till reports itself as main — record the change).
2. Work out the **status** (first match wins): `revoked` → `suspended` → `expired` (portal time > `expiresAt`) →
   `seatLimit` (active registers > `maxRegisters`) → `expiring` (≤ 7 days to `expiresAt`) → `active`.
3. **Token:** if `tokenSha256` differs from your current token for this branch, or your current token's kid is not
   in `trustedKids`, or anything in it changed (renewal, extension, trial length, `maxRegisters`, `features`,
   `limits`, `onlineCheck`, names) → sign and return a new token (same `licenceId`). Otherwise `licenceToken: null`.
4. **Seats:** `registers[]` = one `{registerId, seat}` per reported register: `allowed`, `refused` (over the
   limit — keep the main till and the earliest-activated tills, refuse the newest; **never refuse the main till**),
   or `deactivated` (released on the portal — the till forgets its link and locks).
5. Add `messages` (17.9), optional `apiKey` (a replacement key — rotation; keep the old one valid 7 days) and
   `minimumAppVersion` (tills below it show "please update" but keep trading).

**Reply 200** (`validate-reply.schema.json`; samples `validate-reply.trial-expiring.json`, `.renewed.json`,
`.revoked.json`, `.seat-limit.json`): `status`, `licenceToken` (or null = keep yours), `licence`, `registers`,
`apiKey`, `minimumAppVersion`, `portalTimeUtc`, `nextCheckAfterSeconds`, `messages`.

**Errors:** only request/auth/transport problems — 400, 401 (`auth.*`: the day counts as **not validated**; the
14-day grace keeps running), 403 (`auth.wrong_branch`, `device.not_main_till`), 409, 422, 426, 429, 500, 503.

### 17.6 `POST /api/v1/licence/redeem`

Two callers:

- **(a) A linked till:** a key typed or pasted at it (Settings → Licence → Enter key, or the lock screen). Branch key.
- **(b) A till holding a local key — changed 2026-09-28 (owner), this reverses "an unlinked till never calls
  this".** A till with a local (licence generator) key verifies it offline and trades; when its **Licence server**
  (`licence.portal_url`) is set and reachable it **reports** that key here **once per token**, retrying with its
  daily check until a 200 or 409 comes back. It usually has no branch key: **no `Authorization`** — the signed token
  is the credential. Headers as 17.15.1 (`X-SSPOS-Contract`, `X-SSPOS-App-Version`, `X-SSPOS-Install-Id`, the till's
  own `X-SSPOS-Company-Id` / `-Branch-Id` / `-Register-Id`, `Idempotency-Key`). Rules in 17.16.

**Request** (`redeem-request.schema.json`; `redeem-request.portal-key.json`, `redeem-request.local-token.json`,
`redeem-request.local-report.json`): `key` (a portal key in any format you choose, e.g. `SSPK-4F7Q-XM2D-9KTR-B6WN`,
**or** a whole `SSPOS1.` token), `keyType` (`portalKey` | `token`; a courtesy — a report always sends `token`),
`licenceId` + `tokenSha256` (what the till holds; for a report, the reported token's own), `trustedKids`,
`approverKids`, `installCode`, `installId` (new 2026-09-28; older tills omit it), and — sent by this till version,
optional in the schema — `deviceName`, `appVersion`, `os`, `tillClockUtc` (on a retried key the first attempt's
time, 17.11 rule 5).

**Local key report (b), portal logic:**
1. Verify the token (17.2 steps 1–4 with our generator public keys; `licence.format`, `licence.bad_signature`,
   `licence.unknown_key`, `licence.unsupported_version` → 422). Do not refuse it for being expired, or for
   `companyId`/`branchId` — record it.
2. **First sighting of this `licenceId`** → record `licenceId → installCode` (+ `installId`, `kid`, `tokenSha256`,
   `issuer`, `companyId`, `branchId`, names, `company`, `maxRegisters`, `features`, `limits`, dates, time) and reply
   200 `result: "recorded"`, `licenceToken: null`, `licence` = the summary (`redeem-reply.local-report.json`).
3. **Same `licenceId`, same `installCode`** (a retry, a renewal token for that till, a reinstall keeping its install
   id) → 200 `recorded` again; store the new `tokenSha256`/dates if they changed.
4. **Same `licenceId`, another `installCode`** → **409 `key.used_on_another_install`**, `details {licenceId,
   installCode (the first one), firstSeenUtc}` (`error.key-used-on-another-install.409.json`). The till stores the
   key's hash as withdrawn and locks after the sale in progress ("This key is already used on another PC — contact
   your dealer"); only a new key unlocks it. The first PC keeps trading.
5. Only 200 and this 409 change anything on the till; anything else (no answer, 5xx, 429, 422) leaves its licence
   as it is and the report is tried again with the next daily check. Renewals for that till are made **for its `installCode`** (a normal bound key, same `licenceId`), so step 3
   applies to them.

**Linked till (a), portal logic:** a **portal key** → unknown 404 `key.not_found`; used by another branch 409 `key.already_redeemed`;
past its redeem-by date 410 `key.expired`; for another company 403 `key.not_for_this_branch`; else bind it to this
branch, apply it (extend / upgrade — your billing rules) and reply `result: "applied"` with the new token. A
**token** → verify (17.2; `licence.format`, `licence.unknown_key`, `licence.bad_signature`,
`licence.unsupported_version`, `licence.expired`, `licence.wrong_shop`, `licence.wrong_branch` → 422); a valid local
token is **recorded** for your records (`result: "recorded"`, `licenceToken: null` — the till keeps the token it
verified itself), or refused by policy (403 `key.not_allowed`), or turned into a portal token (`applied`). Which one
is an owner decision (17.14: recorded). The `licenceId → installCode` rule of (b) applies here too.

**Reply 200** (`redeem-reply.schema.json`; `redeem-reply.applied.json`, `redeem-reply.recorded.json`,
`redeem-reply.local-report.json`): `result`, `status`, `licenceToken`, `licence`, `portalTimeUtc`,
`nextCheckAfterSeconds`, `messages`.

**Errors:** as the 17.12 table for `redeem`, plus **409 `key.used_on_another_install`** (local key from a second
install).

### 17.7 `POST /api/v1/devices/deactivate` — free a seat, transfer a till

**Auth:** the branch key when the till holds one (a per-till licence is identified by the body's `registerId` +
`installId`, which the till always sends). Sent by **the till being released** — "Deactivate this till" on
Settings → Licence — with `Idempotency-Key` (17.11 rule 5). Idempotent by `registerId` (deactivating twice returns
the same reply). On 200 the till forgets its cloud link and withdraws the licence it holds (backup and export still
work) and writes an `AuditLog` row `DeactivateTill`; any refusal or no answer changes nothing on the till.

**Request** (`deactivate-request.schema.json`): `registerId`, `installId`, `reason` (`transfer`, `replaced`,
`removed`, `closed`, `other` — open list), `note`; from till **0.1.53** also `tokenSha256` (SHA-256 hex of the licence
token this install holds, as in `validate`; null when it holds none) and `installCode` — both optional. A
`tokenSha256` that is not the token given to this install → 403 `device.token_mismatch`; without them, check as before.

- **A second till** (`deactivate-request.json` → `deactivate-reply.json`): the seat is freed (`seat: "deactivated"`,
  `seatsInUse`, `maxRegisters`); the main till stops letting that till join.
- **The main till itself** (`deactivate-request.main-till.json` → `deactivate-reply.main-till.json`):
  `apiKeyRevoked: true` (the branch key stops working **now**) and a one-time `transferCode` (+ `transferCodeExpiresAt`,
  suggested 7 days; also show it on the portal and e-mail it). The old till forgets its key and token and locks
  (backup/export still work).

**Transfer to a new PC:** old PC → Backup → Deactivate → note the transfer code. New PC → install → restore the
backup → wizard "Link to your account" → transfer code → `activate` with `existingIds` (17.4 step 3) → same
`registerId`, new key, token; sync resumes from the till's own cursor. **Old PC dead?** The admin (or owner) presses
Deactivate on the portal → the same transfer code; a later `validate` from the dead PC, if it ever comes back,
gets `auth.key_revoked`.

**Errors:** 400, 401, 403 (`device.not_main_till`, `device.token_mismatch`), 404 `device.not_found`, 409, 422, 426, 429, 500, 503.

### 17.8 `POST /api/v1/cloud/migrate` — a local shop moves to the cloud

A branch that has never sent anything to the portal links itself and uploads its history. **Since 2026-09-28 this
is what Connect does with a sync key** (route A of `SIMPLE-SETUP.md`) — on any licence, a local one, the built-in
trial or a portal licence (a branch you already know: answer 200 "adopted" with the same ids) — and what a
local-licence shop does when it enters a portal licence key (kept as the code in `sync.migrate_code`). Every till
has ids it made itself. Rule: **in v1 the till never re-keys a row** (its sales are immutable —
`specs/invariants.md` rule 5), so the portal adapts, not the till.

**Auth:** none — the code in `activationCode` (the branch's **sync key**, which must also work as the branch's sync
bearer, or a portal licence key) is the credential; same rate limits as `activate`. **Headers:** every section 3
header (company, branch, register, contract, store protocol, app version) plus `X-SSPOS-Install-Id` and
`Idempotency-Key`. **Idempotent** per `(activationCode, installId)` — a retry returns the same reply and the same
`uploadId`, with `resumeFromSeq` = what you already hold; the till repeats the key and the first attempt's body
(including `tillClockUtc` and `registers[].lastSeenUtc`) until you answer (17.11 rule 5).

**Request** (`migrate-request.schema.json`, `migrate-request.json`): the `activate` device fields, plus
`localLicenceToken` (or null on the built-in trial) and `localTrialEndsAt` (built-in trial only, unsigned),
`company {id, name}`, `branch {id, name, code}`, `registers[]`, and `data {totalRows, rowCounts{entity→n},
firstSaleAtUtc, lastSaleAtUtc, snapshotChangeLogSeq}`.

**Portal logic:**
1. Code checks as `activate` (17.4 step 1–2). `company.id`/`branch.id` already belong to another account → 409
   `migrate.already_migrated`.
2. Verify `localLicenceToken` (17.2) with our generator public keys and compute `carriedOverDays` (the days left on
   it); the cloud licence's `expiresAt` = at least the local `expiresAt` (owner rule: days carry over).
3. **Ids:** the account's sign-up Branch is a placeholder with no data → **adopt**: re-key the placeholder to the
   till's `branch.id`. Company: a new account with no other branches → **adopt** the till's `company.id`; an
   existing company that already has branches under its own id → **alias**: keep your company id, record the till's
   as an alias for this branch, and translate at your edge (rows arriving with the alias are stored under your id;
   rows you send this branch carry the alias). Registers are always adopted. `idMapping` reports what you did;
   `companyId`/`branchId` in the reply are always the ids the till keeps (the ones it sent).
4. Issue the branch key and token (`source: "portal"`), open an **upload**.

**Reply 200** (`migrate-reply.schema.json`; `migrate-reply.adopted.json`, `migrate-reply.aliased.json`):
`companyId`, `branchId`, `idMapping {company, branch}` (each `{localId, portalId, action: adopted|aliased}`),
`registers[]` (seats), `hubUrl`, `apiKey`, `licenceToken`, `licence`, `carriedOverDays`,
`upload {uploadId, mode: "initial", maxRowsPerBatch, resumeFromSeq}`, `settingsBootstrap` (usually null — the till
already has its settings), `portalTimeUtc`, `nextCheckAfterSeconds`, `messages`.

**Then the initial upload — through the normal push endpoint:**

- `POST /api/v1/sync/push` with the normal headers plus `X-SSPOS-Sync-Mode: initial` and `X-SSPOS-Upload-Id:
  <uploadId>`. Body = the section 5 envelope, gzip, ≤ `maxRowsPerBatch` rows (≤ 5000), **no** 5-batches-per-run cap
  (the upload runs continuously in the background; the shop keeps trading). Sample: `licensing/samples/push-request.initial.json`.
- Each row is the row's **current state**: `op: "I"`, `version` = its `rowVersion`, the full payload. `seq` is the
  **upload's own sequence** 1…N, strictly increasing — not the ChangeLog seq; key initial rows by `(uploadId, seq)`
  (and, as always, `(entity, entityId, version)`). Reply `acknowledgedSeq` / `accepted` / `receivedAt` exactly as section 7.
- **Order:** tier 1 company-wide master data (`VatRate`, `Unit`, `Department`, `Category`, `Supplier`, `Product`,
  `ProductBarcode`, `ProductAlias`, `ProductUnit`, `ProductSupplier`, `PaymentType`, `Reason`, `Role`, `User`,
  `Customer`, `Promotion*`, `Account`, `TaxRule`, other hub-owned entities of section 10); tier 2 branch set-up
  (`Register`, `BranchProduct`, other branch rows); tier 3 documents (`Shift`, `Sale`, `SaleLine`, `SalePayment`,
  `SaleVat`, `StockMovement`, `CustomerOrder`, `ZReport`, `JournalEntry`/`Line`, `AuditLog`, everything else).
  Inside a tier: entity, then `createdAt`, then `id`. **Do not enforce foreign keys on ingest** — store first,
  resolve later (true for every push).
- Resume: after a crash the till re-plans the same order and resends after its last `acknowledgedSeq` (or after the
  migrate reply's `resumeFromSeq`). Rows changed during the upload arrive with a higher `version`; keep the highest.
- While the upload is open the till does **not** run the normal delta push or pull. Changes made meanwhile wait in
  its ChangeLog.
- Each upload batch carries an `Idempotency-Key` — the same key for the same batch bytes until you answer it
  (17.11 rule 5); a normal delta push carries none.
- Finally `POST /api/v1/cloud/migrate/complete` (`Authorization: Bearer <apiKey from the migrate reply>`, every
  section 3 header, `X-SSPOS-Install-Id`, `Idempotency-Key` — kept until you answer; after `"incomplete"` the
  resent rows are followed by a new complete with a new key; body `migrate-complete-request.json`: `uploadId`,
  `totalRows`, `highestSeq`, `rowCounts`, `snapshotChangeLogSeq`). Compare counts; reply `status: "complete"` (set this branch's
  push cursor to `pushResumesAfterSeq` = `snapshotChangeLogSeq`) or `"incomplete"` with `missing[]` and
  `resumeFromSeq` (the till resends from there and calls complete again). After `complete` the till resumes
  normal push from `snapshotChangeLogSeq + 1` and pulls from `since = 0`; do not echo back rows you just received
  unchanged (if you do, the till skips them as already seen).
- Errors: 404 `migrate.upload_not_found` (the till calls `migrate` again), 409 `migrate.upload_closed` (the till
  stops uploading and resumes normal push).

### 17.9 What the till does with each answer

> **This till version (per-till licences, 17.15.2):** only `active` and `expiring` let it trade; every other
> `status` — `expired`, `revoked`, `suspended`, `released`, **`seatLimit`** and any value it does not know —
> withdraws the token it holds and locks after the sale in progress (`src/SSPOS.Application/Ports/LicencePortalReply.cs`).
> It does not read the validate reply's `registers` / `seat`. The `seatLimit` row and the `seat` table below are the branch model, kept
> for reference: a per-till portal refuses a till past `maxRegisters` at `licence/activate` (403
> `licence.seat_limit`, 17.15.1 step 4a) instead.

| `status` | Till |
|---|---|
| `active` | Trades. Stores the token if one came. |
| `expiring` | Trades; banner "Your licence ends on …" daily. (The till also warns by itself from 7 days before `expiresAt`.) |
| `expired`, `revoked`, `suspended` | Finishes the sale in progress, then the lock screen. It remembers the verdict against the token's hash, so a restart does not unlock; only a **new** token or a later `active`/`expiring` answer unlocks. |
| `seatLimit` | The main till trades; every register marked `refused` locks (the main till tells it over the LAN). |
| unknown value | Treated as **not active** (lock after the sale) — owner rule, `specs/licensing.md` section 4. So: **never send a status value to a till version that does not know it** (check `X-SSPOS-App-Version`; new values are announced in this document with the first till version that understands them). |

| `seat` | Till |
|---|---|
| `allowed` | Trades. |
| `refused` | Locks with "Too many tills for this licence". |
| `deactivated` | Forgets its link (key, token) and locks; backup/export still work. |
| unknown | As `refused`. |

**Other till rules the portal should know:** 14 days (`graceDays`) without a successful `validate` → lock, measured
on the portal's time from the last success; the clock guard locks when the PC clock goes back beyond tolerance
until corrected or a successful `validate` confirms the time; a paid feature not in the token shows **greyed**
("This is a paid feature — contact your dealer"), never hidden — adding a branch without `multi_branch`, or past
`limits.branches`, is greyed the same way; trial length can never be changed on the till — only a new signed token
changes it; a local key reported from a second PC (409 `key.used_on_another_install`) locks that PC (17.16).

**Messages** (`messages[]`, display only — never change what the till allows): `id` (the till shows each id at most
once a day and remembers dismissals), `level` (`info` | `warning` | `critical`; unknown = `info`), `title`, `text`
(en-GB, ≤ 500), `showFromUtc`, `showUntilUtc`, `dismissible`, `link {label, url}` (https; shown as text / QR — a
till has no browser).

### 17.11 Extensibility rules (built to grow)

1. **Versioning.** The path's `/api/v1` is the contract **major**; the till sends it in `X-SSPOS-Contract: 1` and
   you echo `X-SSPOS-Contract` in every reply. Additive changes — a new endpoint, a new optional field, a new
   feature name or limit, a new error code, a new enum value introduced under rule 3 — **never** change the major.
   A breaking change is served as `/api/v2/...` **alongside** `/api/v1` until `validate` shows no till still on a
   v1-only version (and at least 12 months); a till moves to v2 in the release that speaks it. An unsupported major
   → 409 `contract.unsupported` with `details.supportedContracts`. This document's revision (1.4) and
   `openapi.yaml` `info.version` (1.4.0) track additive edits.
2. **Unknown fields are ignored both ways.** Neither side rejects a request or reply because of a field it does not
   know; our schemas never say `additionalProperties: false`. Absent, `null` and (for strings) `""` mean the same.
   Send `null` or omit — both are fine.
3. **Enums are camelCase strings**, never numbers (section 6). Replies you send use only the values listed for this
   contract (the reply schemas carry `enum`). The till's handling of an unknown value is fixed and safe: state
   values → the **safe reading** (licence status → not active; seat → refused; `idMapping.action` → stop the
   migration and show the messages; `redeem.result` → keep the current licence; `complete.status` → incomplete);
   display values → neutral (`message.level` → info). Values the till **sends** (`lock.reason`, `deactivate.reason`,
   `keyType`) are open: store them as-is and treat an unknown one as "other".
4. **Open objects** carry new things without a contract change: token `features` and `limits`,
   `settingsBootstrap` (and its `settings` map), validate `diagnostics`, error `details`. Unknown keys are ignored.
5. **Idempotency — one key per logical request (revision 1.4).** Every POST the till sends carries
   `Idempotency-Key` (a ULID) — `licence/activate`, `licence/validate`, `licence/redeem`, `devices/deactivate`,
   `cloud/migrate`, `cloud/migrate/complete` and each history-upload batch (`sync/push` with
   `X-SSPOS-Sync-Mode: initial`); a normal delta push sends none (its rows are the idempotency, §7).
   - **What the till does.** A request keeps its key from its first attempt until you *answer* it. Every retry in
     between — "Enter key" pressed again, the next check-in, the migration's next step, a restart of the till —
     repeats the key **and the first attempt's body byte for byte**, including `tillClockUtc` (and
     `clockWatermarkUtc`, `registers[].lastSeenUtc`): on a retried key those are the time of the first attempt,
     not now. The till sends the same key again after **no reply** (network, timeout), **408**, **409
     `request.in_progress`**, **429**, **502**, **503** or **504**; any other reply (2xx, another 4xx, 500) ends the
     request and the next call has a new key. A key is never reused after 12 hours (half your 24-hour store). Keys
     survive a restart of the till (`src/SSPOS.Infrastructure/Sync/PortalRequestKeys.cs`).
   - **What you do.** Store `(key, endpoint, caller, body hash) → reply` for at least 24 hours: a repeat with the
     same body returns the **same status and body**; a different body → 422 `request.idempotency_mismatch` (the
     till never does this — it is a bug to report); the first still running → 409 `request.in_progress` +
     `Retry-After`. **Do not store** a 408, 409 `request.in_progress`, 429, 502, 503 or 504 under the key — the till
     will send the request again with it and must get a real answer.
   - Endpoints are also idempotent by nature: `licence/activate` per `(key, installId)`, `cloud/migrate` per
     `(code, installId)`, `devices/deactivate` per `registerId`, `licence/redeem` per `(key, branch)` (a local key
     report per `(licenceId, installCode)`), `complete` per `uploadId`, push per `(entity, entityId, version)` and
     `(branchId, seq)` / `(uploadId, seq)`.
6. **Paging.** Sync pull pages by `since` / `max` / `hasMore` (section 8); the initial upload by
   `maxRowsPerBatch`. Any future list endpoint uses `?cursor=&limit=` → `{ "items": [...], "nextCursor": "…" | null }`.
7. **Time** is UTC ISO-8601 with `Z` everywhere (section 6). Every licence reply carries `portalTimeUtc`; also send
   the HTTP `Date` header. The till trusts the portal's time over its own clock.
8. **Money** follows section 6 (pounds as JSON numbers, 2 dp, half away from zero, parse as decimal). No section 17
   endpoint carries money today; any future billing field follows section 6 and adds `"currency": "GBP"`.
9. **Ids** are ULIDs (section 6). Ids you make (`licenceId`, a new `registerId`, `uploadId`, message ids) must be
   ULIDs too; you never re-key a till's id (section 2.1).
10. **Error envelope** = section 9 + optional `details`; codes are `area.snake_case`; a new code may appear at any
    time — the till acts on the HTTP status (section 9 table) when it does not know the code.
11. **Rate limits** → 429 with `Retry-After` (seconds) and `retryAfterSeconds` (17.12). `RateLimit-*` headers are
    welcome; the till ignores them.
12. **Transport security.** HTTPS only (TLS 1.2+, 1.3 preferred) with a certificate from a public CA; HSTS on. The
    till refuses `http://` and invalid certificates. No certificate pinning in v1, so you can renew certificates
    freely. Never put a key, code or token in a URL or a query string.
13. **Compression.** Accept `Content-Encoding: gzip` on any POST (the till gzips push; others may be gzip later) and
    plain JSON too (test tools). Gzip replies only when the till sends `Accept-Encoding: gzip` (the sync and
    migration calls do; the licence and device calls do not).

### 17.15 Per-till licensing — one e-mailed key per till (owner, 2026-09-26) — **supersedes the branch model for licences**

**Why:** the owner decided that **every till has its own licence**. A shop receives a **licence key by e-mail** (a
trial key at sign-up — since 2026-09-28 a new install cannot be set up without a key and there is **no built-in
trial**; installs that already started the old built-in trial keep it until it ends). The key is typed in the
first-run wizard (or Settings → Licence), checked **online**, and from then
on belongs to **that PC** (its `installId`, the "system id"). The same key typed on another PC is refused. The portal
admin can release a key and issue a new one at any time — the till never needs to know how.

**What changes against 17.1–17.9** (everything else in §17 stands — the token format, signing, kids, error envelope,
compatibility rules):

| Before (branch model) | Now (per-till) |
|---|---|
| One licence per branch, `maxRegisters` seats, counted by the main till | One licence **per till**; the portal counts the branch's activated keys. **Changed 2026-09-28:** `maxRegisters` in each till's token = the tills allowed in the **branch** (the same in every key of the branch — it was 1), and the portal refuses a till past it (17.16) |
| Only the main till calls the portal (`devices/activate`, `licence/validate`) | **Every** till with a portal licence calls `licence/activate` once and `licence/validate` daily, **for itself** |
| Portal token bound by `companyId`/`branchId` | Portal token bound by **`installCode`** (as local keys already are); the till no longer checks the branch for such a token |
| Seats: `registers[]` / `seat` / `seatLimit` | Not used for per-till licences (keep them for a branch-model customer if you ever need one) |
| Activation code = branch link + sync key | **No activation code (2026-09-28).** The licence key is the only code. Cloud sync comes either with the licence (`apiKey` in the `licence/activate` / `validate` reply, 17.3 step 3) or from a **sync key** the owner types on the main till (`cloud/migrate` + `sync/*`, `SIMPLE-SETUP.md`). `devices/activate` is not called by the till |

**Local (dealer) keys are unchanged:** the owner's key generator still makes offline keys bound to an install code
(no internet; for shops without internet). Such a shop can move to the cloud later: the owner gives it a portal key
and a cloud link; its history goes up with `cloud/migrate` (17.8).

#### 17.15.1 `POST /api/v1/licence/activate` — NEW

**Auth:** none — the **licence key is the credential** (store it hashed; ≥ 60 bits random; rate-limit wrong keys:
5 per install per 15 minutes → 429 `activation.too_many_attempts`). **Headers:** `X-SSPOS-Contract: 1`,
`X-SSPOS-App-Version`, `X-SSPOS-Install-Id`, `X-SSPOS-Company-Id`, `X-SSPOS-Branch-Id`, `X-SSPOS-Register-Id`
(the till's own ids), `Idempotency-Key` (one per key entered: pressing Enter key again — even after a restart —
before you answer repeats the key and the first attempt's body, `tillClockUtc` included; 17.11 rule 5). A till
that also has a branch API key sends `Authorization: Bearer …` — optional here.

**Request** (`licence-activate-request.schema.json`, `licence-activate-request.json`): `licenceKey` (upper-cased,
spaces removed — any layout you choose, e.g. `SSPK-4F7Q-XM2D-9KTR-B6WN`), `installId`, `installCode`, `deviceName`,
`appVersion`, `os`, `tillClockUtc`, `trustedKids`, `approverKids`, `existingIds {companyId, branchId, registerId}`
(the till's own ids — it **never re-keys** its data; adopt or alias them as in 17.3 step 3).

**Portal logic:**
1. Look the key up (hash). Unknown → 404 `key.not_found`; past its activate-by date or withdrawn before use → 410
   `key.expired`; the account is suspended/revoked → 403 `licence.not_active`.
2. The key is **not yet bound** → bind it to this `installId` (+ `installCode`, `deviceName`, `existingIds`, time).
3. Bound to **the same `installId`** → answer 200 again with a valid token (a retry, or a reinstall that kept its data).
4. Bound to **another `installId`** → 409 `key.already_used`, `details {deviceName, installCode, activatedAtUtc}`,
   and a `message` naming the other PC. Only the admin can move it (17.15.3).
4a. Not yet bound, but the key's branch already has `maxRegisters` keys bound to other installs → 403
   `licence.seat_limit` (`details {maxRegisters, registersInUse}`, `error.seat-limit.403.json`). Normally unreachable: the admin cannot issue more
   till keys than the branch's tills (17.16).
5. Sign a token for this till. It **must** carry (2026-09-28):
   - `source: "portal"`, **`installCode` = the request's**, `kind` (`trial` / `full`);
   - the shop: `companyId`, `branchId` (the **same** in every till key of the branch — the customer's, not the
     till's `existingIds`), `businessName`, `branchName` and the **`company` block** (17.2) from the customer form;
   - **`maxRegisters` = tills allowed in the branch**, **`features`** as sold (with **`multi_branch`** when the
     company may run more than one branch), **`limits.branches`** (omit or 1 for a single-branch customer);
   - **`validFrom` / `expiresAt`** = the length the admin chose (days, months, years; trial or full);
   - `onlineCheck {required: true, intervalHours: 24, graceDays: 14}`.
   Sample payload: `licence-token.payload.per-till.json`.

**Reply 200** (`licence-activate-reply.schema.json`, `licence-activate-reply.json`): `status`, `licenceToken`,
`licence`, `portalTimeUtc`, `nextCheckAfterSeconds`, `messages`. **`licence`** (the plain summary) lists the same
fields: `licenceId`, `kind`, `source`, `companyId`, `branchId`, `businessName`, `branchName`, `installCode`,
`validFrom`, `expiresAt`, `maxRegisters`, `features`, `limits` (with `branches`) and `company` (the schema still
requires only `licenceId`, `kind`, `expiresAt`, `maxRegisters`, so an older reply stays valid); the signed token
always wins. **Optional (2026-09-28):** `apiKey` (the branch's sync key, when the licence includes the dashboard) and
`hubUrl` (only if sync is on another host) — the till stores them and turns Cloud sync on (17.3 step 3). The sample
token is signed with the documentation key `k13799fa4` from `licence-token.worked-example.json` — your signer must
verify it.

**Errors:** 400 `request.invalid`, 403 `licence.not_active` / `licence.seat_limit`, 404 `key.not_found`, 409 `key.already_used`,
410 `key.expired`, 426 `app.update_required`, 429 `activation.too_many_attempts` (a wrong-key limit — the till shows
it), 500/503/other 429 (the till says "could not reach the licence server" and changes nothing).

**What the till does:** verifies the token (signature, trusted `kid`, `installCode` = its own, dates), stores it,
records the check-in with `portalTimeUtc`, writes an audit row. A refused key changes nothing on the till.

#### 17.15.2 `POST /api/v1/licence/validate` — per till

Same endpoint and reply as 17.5, but **each till sends it for itself**, once per `onlineCheck.intervalHours`
(the till's timer runs every 15 minutes and sends when due), at start-up when due, and on **Check again**.
**No branch key is required** — identify the licence by `licenceId` + `tokenSha256` + `installId` (only answer
for a licence bound to that `installId`; anything else → 404 `key.not_found`).

**Headers:** `X-SSPOS-Contract`, `X-SSPOS-App-Version`, `X-SSPOS-Install-Id`, the till's own
`X-SSPOS-Company-Id` / `-Branch-Id` / `-Register-Id`, `Idempotency-Key` (one per due check-in: an unanswered
check is repeated at the next 15-minute tick, or on Check again, with the same key and the first attempt's body —
`tillClockUtc` and `clockWatermarkUtc` included; 17.11 rule 5), and `Authorization: Bearer` only when the till holds
a branch key.

**Request** (`validate-request.schema.json`, sample `validate-request.per-till.json`): `installId`,
`installCode`, `licenceId`, `tokenSha256`, `deviceName`, `appVersion`, `os`, `trustedKids`, `approverKids`,
`tillClockUtc`, `clockWatermarkUtc`, `lastValidatedAtUtc`, `lock {locked, reason}`. `registers[]`, `lastSyncAt`
and `diagnostics` are absent.

**Reply 200** (samples `validate-reply.per-till.json`, `validate-reply.released.json`): `status`,
`licenceToken` (a new token when anything changed — renewal, extension, features — else null), `licence`,
`portalTimeUtc`, `nextCheckAfterSeconds`, `messages`; optional `apiKey` (+ `hubUrl`) — the branch's sync key, which
the till stores and uses (a rotation replaces the held one; 17.3 step 3).

**Status → till** (17.9 rules, per till): `active`, `expiring` → trades (and a later `active` lifts an earlier
withdrawal); `expired`, `revoked`, `suspended`, **`released`** (new: the key was released from this PC on the
portal) and **any value the till does not know** → the till withdraws the token it holds (remembered across
restarts) and locks after the sale in progress; only a new key or a later `active` unlocks. No reply / 5xx / 429 →
nothing changes; after **14 days** without a successful check the till locks ("connect the internet").
The till takes `portalTimeUtc` as the true time on every successful call (clears its clock guard).

### 17.16 A key carries the shop; open local keys; local keys reported (owner, 2026-09-28)

| Owner's word | Token field |

that would take the live tills past its own key's `maxRegisters`. The till never re-keys its own database ids to

the first time either PC reaches the licence server.

### 17.17 Signer certificates — your key needs no till release (owner, 2026-09-28)

Your signing key is **approved** by the owner's key generator instead of being compiled into the till, so a new
key, a rotation or a second server never waits for a till update.

**Format** (like a token, a different prefix):

```
SSPOSCERT1.<base64url(payload JSON)>.<base64url(Ed25519 signature by the APPROVER over ASCII "SSPOSCERT1." + payload part)>
```

| Payload field | Rule |
|---|---|
| `v` | `1`. |
| `kid` | Your key id = `"k"` + first 8 hex of SHA-256(your raw 32-byte public key). Must equal the `kid` of every token it rides in. |
| `publicKey` | Your raw 32-byte Ed25519 public key, base64url (43 characters). |
| `name` | Who the key belongs to, e.g. `SSPOS Portal`. |
| `issuedAt` | When it was approved (UTC). |
| `expiresAt` | Optional (UTC). A token whose `issuedAt` is after it is refused; tokens made before it keep working. Absent = no end date. |
| `approvedBy` | The approver's kid — one of the till's `approverKids`. |

**Hand-over, once:**
1. Generate your pair on the server (17.2). Send us `public-key-handover.json` (public key only).
2. The owner pastes it into the key generator → **Approve a signer** → sends you the certificate string (~300 characters).
3. Store it next to your key (it is **not secret**) and put it, unchanged, in the `signerCert` field of **every**
   token you sign. Nothing else changes in the token or its signature.

**What the till checks** (`src/SSPOS.Infrastructure/Licensing/SignerCertificates.cs`, `LicenceTokens.Read`): the
token's `kid` is not built in → `signerCert` starts with `SSPOSCERT1.` → `approvedBy` is in the till's approver list
**and** built in → the approver's signature verifies → SHA-256 kid of `publicKey` equals the certificate's `kid`
equals the token's `kid` → token `issuedAt` ≤ `expiresAt` (if set) → the token's own signature verifies with
`publicKey`. Any failure → `licence.bad_signer_certificate` (the till says "made by a licence server SSPOS has not
approved"). One level only: a certified key cannot approve another key. If an approver is withdrawn
(`RetiredAfter`), the keys it approved stop at the same cut-off.

**Requests tell you what the till accepts:** `activate`, `validate`, `redeem` and `migrate` carry
`approverKids` (string[]) beside `trustedKids`. Today every till has one approver (the owner's generator).

**Worked example** (byte for byte, documentation keys): `licensing/samples/signer-certificate.worked-example.json`
— the certificate, each intermediate string, and a portal token carrying it that a till trusting only the
approver accepts. Your signer can be tested against it.

### 17.18 Country — one portal and one till build per country (owner, 2026-10-07; the Pakistan line)

Each country has its own portal, its own licence signing key (17.17) and **its own till build**: the United
Kingdom's (SSPOS 3) and Pakistan's are two installers (owner, 2026-10-07). A build is made for one country and
never changes country; the licence says which country it was sold in, so a key typed into the other country's
till is told so in plain words.

**What you send — additive and optional:**

| Where | Field | Value |
|---|---|---|
| Token payload (17.2) | `country` | ISO 3166-1 alpha-2 in capitals: `PK` on the Pakistan portal, `GB` on the UK portal. Signed with the rest, so it cannot be changed on the way. **This is the one the till trusts.** |
| `licence/activate` reply (17.15.1) | `country` | The same value, top level. |
| `licence/validate` reply (17.5, 17.15.2) | `country` | The same value, top level. The till does not read it there today; send it so the three always agree. |

**What the till does:**

1. A token whose `country` is not the till's own is refused. At *Enter key*: code `licence.other_country`,
   "This key is for the United Kingdom. This till is for Pakistan — ask your dealer for a key for Pakistan.",
   and nothing is saved. A token already stored locks the till with the same reason. This check comes before the
   install-code and branch checks, so the plainer reason is the one shown.
2. An activate reply whose top-level `country` is another country's is refused the same way, before its token is read.
3. **No `country` = the key works in any till.** Every key made before 2026-10-07, and every key from our own
   licence generator, has none — so you can deploy the field whenever you like and nothing breaks either way round.
4. `licence/validate` → `lock.reason` gains **`wrongCountry`** (an open list, 17.11 rule 3).
5. If you refuse a key yourselves because of its country, use the code **`licence.other_country`**; without a
   `message` of yours the till shows "This key is for another country. This till is for Pakistan — …".

**One thing the field cannot do.** An *e-mailed* key (not a token) typed into the other country's till is sent to
that till's own portal, which has never heard of it and answers `key.not_found` — the till then says "This key was
not found", not "wrong country". If you want the plain message there too, give each country's keys a form the till
can tell apart without asking (tell us the rule) — the two portals share no data, so nothing else can know.

**Which builds:** the Pakistan till has this from its first build. The UK till (SSPOS 3, 0.1.60) does not read
`country` yet — to it, an unknown field.

## 18. The portal product — panels, roles, screens (owner's brief, 2026-09-26)

This section says **what the portal must let people do**; sections 1–17 say how it talks to the till.
Build it so that the owner can run every shop from one screen and a shop owner can run their own
business from theirs — and so that anything changed on the portal reaches the tills by itself.

### 18.1 Words — portal ↔ till

| Portal says | Till entity | Notes |
|---|---|---|
| **Business** | `Company` | One customer account. Owns its products, prices, users, customers, promotions (company-wide, §2.4). |
| **Shop** | `Branch` | A business has **one or many** shops. Each shop has its tills' licence keys (one per till), one **sync key** (the branch API key, only with the dashboard), its own shop prices (`BranchPrice`), stock and sales. |
| **Till** | `Register` | A shop has **one or many** tills. One is the shop's **main till**: it holds the shop's database and is the only one that syncs; the rest join it on the shop LAN (§2.2, §17.3). |

Ids: **the till keeps its own ids** (ULIDs made at its first start) and sends them as `existingIds` in
`licence/activate`; you adopt or alias them (§17.3 step 3, §17.8). Rows made on the till keep the till's ids;
rows you make (products, prices, head-office orders…) keep yours. Never re-key (§2.1).

### 18.2 Two panels, four roles

| Role | Panel | Sees | Can change |
|---|---|---|---|
| **Super admin** (SSPOS owner) | Admin panel | Every business, shop, till | Everything below, plus dealers and plans |
| **Dealer** (optional) | Admin panel | Only the businesses they sold | Same as super admin for those businesses; cannot create dealers |
| **Business owner** | Business panel (own login) | Only their business: all its shops and tills | Their master data (products, prices, promotions, customers, staff, settings); cannot change the licence |
| **Shop manager** (optional) | Business panel | One shop | That shop's data only (stock, shop prices, shop settings) |

Every query is filtered by `companyId` (and `branchId` for a shop manager) on the server — a business
owner must never see another business, whatever the URL.

### 18.3 Admin panel — what it must do

**Per-till model (updated 2026-09-28).** One licence key per till; no activation codes; no seats.

1. **Businesses:** list with search; add (name, owner name, **owner e-mail**, phone, VAT number,
   address); suspend / reactivate.
2. **Shops under a business:** add any number (name, address, shop code e.g. `LDS` — shown on
   receipts); per shop: **tills allowed** (`maxRegisters`, e.g. 2), licence length (trial / months / years,
   start/end), paid features (17.2 list), dashboard on/off (`cloud_sync`).
3. **Licence keys:** per shop, **issue one key per till** up to tills allowed (a trial key at sign-up). "Send
   setup e-mail" → the owner receives the key(s), the installer link and two steps (install → type the key).
   If the shop has the dashboard, its **sync key** is shown in the Business panel ("Connect the dashboard") —
   or simply returned with the licence (17.3 step 3), so the owner types nothing else. Template in 18.7.
4. **Tills under a shop** (one row per issued key): key (masked), status (not activated / active / released /
   revoked), bound PC (`deviceName`, `installCode`, `installId`), `registerId`, app version, **last check-in**,
   online/offline. Actions: **release the key** (the PC locks at its next check; the key can then be activated on
   another PC — §17.15.3), re-issue a new key (the old one stops), revoke.
5. **Licence changes take effect by themselves:** raise tills allowed 2 → 3 (issue one more key), extend a
   trial 7 → 30 days, add a feature, renew, suspend — the portal signs a new token for **each till** and every
   till picks it up at its own next `licence/validate` (daily, or at once on "Check again").
6. **Dashboard** (18.5) across all businesses, and per business / per shop.
7. **Audit:** who changed which licence or record, when (keep your own log).

### 18.4 Business panel — the shop owner's own login

1. **Dashboard** for their business: today / this week / this month, per shop and in total (18.5).
2. **Products and prices:** add / edit products, barcodes, departments, categories, VAT, prices, promotions,
   coupons — and a **price for one shop only** (`BranchPrice`, §10.5: a shop, a product or a case, a price, from /
   until). Show the shop's price beside the product price, and the till's rule: a price-marked pack beats it.
3. **Customers, staff (users, roles, PINs), suppliers, payment types, reasons.** Customer balances and points are
   read-only sums of the ledger (§10.1).
4. **Purchasing (optional):** head-office purchase orders for a shop (§10.6) — draft, send, cancel until the shop
   acts on it; follow each one's status as the shop sends, cancels or receives it (its pushes are the truth).
5. **Shops and tills:** read the licence (tills allowed, end date, features), see each till's status;
   "Ask for more tills" sends a request to the admin (they cannot raise it themselves).
6. **Reports:** sales, refunds, VAT, stock, Z reports — read-only (they come from the tills).
7. **Settings** for a shop or the business (receipt text, opening hours…) — `Setting` rows both ways (§10.3),
   never a deny-listed one.

### 18.5 Dashboards — where the numbers come from

Everything a till sells arrives by `push` within about **30 seconds** while the shop is online (and
catches up by itself after an outage). Build your own reporting tables as rows arrive; do not query the
raw change log for every screen.

| Figure | Built from |
|---|---|
| Sales total, count, average basket — per business / shop / till / day | `Sale` (status `completed`; refunds are their own `Sale` rows with type `refund` — subtract them), or the ready daily totals `SalesDaily` |
| Takings by payment type (cash, card…) | `SalePayment`, or `TenderDaily` |
| Top products, department sales | `SaleLine` |
| VAT | `SaleVat` |
| End-of-day / shift figures | `ZReport`, `Shift` |
| Stock on hand, low stock | `BranchProduct`, `StockMovement` |
| Tills online / offline, versions | the daily `licence/validate` call (§17.5) and the last `push` time per shop |

Rules: the shop's **trading day** is the local day in the shop's time zone (UK: Europe/London), not the UTC
date; money is decimal pounds (§6); a sale belongs to the till in its `registerId` and the shop in its
`branchId`. Show "last updated N minutes ago" per shop so an offline shop is obvious — from the newest
`received_at` you stored for that shop (§6.1). On every row's detail screen show both times: made at the
till (its business time / `createdAt`) and reached the portal (`received_at`).

### 18.6 What a portal change does on the till, and how fast

| Changed on the portal | Reaches the tills | How |
|---|---|---|
| Products, barcodes, prices, departments, categories, VAT rates, promotions, coupons, customers, users/roles, suppliers, payment types, units, reasons (§10 "Portal") | ≈ 30 seconds, online | `pull` by the shop's main till, which serves its other tills over the LAN |
| A price for one shop only | ≈ 30 seconds, online (+ up to 20 s to reach a secondary till) | a `BranchPrice` row in that shop's `pull` (§10.5); the main till copies it to its secondary tills over the LAN; labels, electronic shelf labels and the scale PLU export use it too |
| Shop or business settings (receipt text, hours…) | ≈ 30 seconds, online | `Setting` rows in `pull` (§10.3); the next action that reads a setting uses it; secondary tills copy the main till's shop-wide settings over the LAN |
| Role permissions | ≈ 30 seconds, online | `RolePermission` rows in `pull` (§10.3) |
| A head-office purchase order for a shop | ≈ 30 seconds, online | `PurchaseOrder` + lines in that shop's `pull` (§10.6); a change is refused and flagged once the shop has sent, cancelled or started receiving it |
| Licence: tills allowed, dates, features, suspend | next daily check, or at once on "Check again" | new token in the `licence/validate` reply (§17.15.2) |
| Sales, refunds, shifts, Z reports, stock movements, receipts of goods | never — read-only on the portal | till-owned (§10); correct a sale on the till, never on the portal |
| Customer balance or points | never from the portal | adjustments are made at a till and reach you as ledger rows (§10.1) |

While a shop is offline, portal changes wait and arrive the moment it reconnects. If the shop edited the
same record before it synced, the till shows a conflict for a person to settle (§8).

### 18.7 E-mails the portal sends

- **Setup (per shop):** business and shop name; **one licence key per till** ("Till 1 of 3", large, copyable —
  a trial key at sign-up); the installer link; two steps (install → type the key; the installer's optional key
  page takes it too); with the dashboard, either nothing more (your `licence/activate` reply carries `apiKey`) or
  the **sync key** and where to type it (Settings → Network → Cloud sync → Connect, main till only —

### 18.8 Make it easy to plug in (and to extend later)

- Store the till's `id` as your primary key; upsert by `(entity, id)` and keep the highest `version`.
- Keep the full `payload` JSON beside your typed columns: a field the till adds tomorrow is then already
  in your database, and you add a column when you need it — no data lost meanwhile.
- Ignore fields and entity names you do not know (§17.11); never fail a whole batch for one row
  (reply per row, §7).
- Put company/shop filters in one place in your API layer (18.2), not in every screen.
- New feature later = a new entity or field on the till side, a new sample/schema in this package, and
  your screen — the transport, auth and licence flow do not change.

### 18.9 Never slow a shop down

Syncing must never make a till slower at the counter. The till keeps its own rules for this
(`specs/performance.md`, "Cloud sync never slows the till": background only, thin write slices, no
catalogue reloads, throttled big jobs). The portal's part:

- **Answer fast.** `push` and `pull` should reply within 2 seconds; do heavy work (reports, e-mails,
  re-indexing) after you reply, in your own background jobs.
- **Page, don't flood.** Honour `max` on pull; never send more rows than asked. A bulk change on the
  portal (e.g. 5,000 new prices) is fine — it simply goes down in pages and the till applies it in
  slices.
- **Only send what changed.** Bump `version` only for rows that really changed; re-sending the whole
  catalogue on every edit costs every shop time and data.
- **No big blobs in sync.** Product images and files are URLs the till fetches on demand, never inline
  base64 in a sync row.
- **Say when you are busy.** Under load reply 429/503 with `Retry-After`; the till backs off
  (1 → 2 → 5 → 15 min) instead of retrying in a loop.
- **Big history uploads** (a shop moving to the cloud, or catching up after a long outage) arrive in
  batches over time; accept them in order and don't time the shop out.

## 19. Synced once, never twice, never backwards (owner, 2026-09-26)

Three promises, kept by **both** sides. Section 7 (push) and section 8 (pull) already carry the
mechanics; this section is the rulebook and the test list. Nothing here is decided by clock time (`at`) —
only by `seq` and `version`.

### 19.1 Never twice — no duplicates

- **Push:** a row's identity is `(entity, entityId, version)`; a batch's is `(branchId, seq)`. A retried
  batch (timeout, crash, lost reply) is stored once and answered with **the same reply** (section 7). Several
  entries of one row in a push carry the same triple (revision 1.4): store it once, count the rest as accepted.
- **Pull:** the till skips any row with `version ≤ since` and any `(entity, entityId, version)` it has
  already applied (section 8).
- **POSTs** (`licence/*`, `devices/deactivate`, `cloud/migrate*`, each history-upload batch) carry
  `Idempotency-Key`; a retry repeats the key and the first attempt's body byte for byte, and the same key returns
  the same answer (17.11 rule 5).
- **Several tills, several branches:** only a branch's main till sends (§2.2), so one branch = one sender = one
  `seq` series; a second till's work arrives inside it, each row naming its own till (`registerId`). Branches
  have separate `seq` series and cursors — key by `(branchId, seq)`, rows by `id` (§2 point 5).
- **Upserts, not inserts:** both sides store by `entityId`; the same row arriving twice updates one row,
  never creates a second.
- **Human references are unique too, but they are not keys** (revision 1.4, §10.4): a customer order's
  `reference` is `CO-{branch}-{till}-{number}` from the till's own counter and unique in its shop; key by `id`.
- **Relays and ledger rows** (§10.1, §10.2): a relayed row is keyed by its `id` on the receiving till, so the
  same relay twice is one row and moves a customer's balance once; a transfer can be received only once.
- **Shop prices and head-office orders** (§10.5, §10.6) are keyed by their `id` too: the same row twice, or the
  same content at a newer version, changes nothing; a head-office order sent twice is still one order.

### 19.2 Never echoed — what came from the other side does not go back

- **Till:** rows applied from `pull` are written **without a ChangeLog entry** (they are marked as coming
  from the portal), so the next `push` never contains them. Only an edit made in the shop creates a
  ChangeLog row. Applying a row whose content is identical to what the till already holds does nothing at
  all — no ChangeLog, no screen refresh.
- **Portal:** rows received by `push` are stored with their **origin branch**. When such a row also has to
  reach other shops (a company-wide row, e.g. a price changed at shop A), send it in `pull` to the **other**
  branches only — not back to the branch it came from. If you do send it back, the till treats identical
  content as already applied (above), but do not rely on that. The same holds for relayed rows (§10.2): the
  till refuses a relayed row that is its own.
- **No lost updates on shared counters** (revision 1.4, §10.1): a customer's balance and points are never sent
  as the truth by either side — each adds up the same ledger rows — so two shops moving one customer at the same
  moment both count.

### 19.3 Never backwards — old data never overwrites new

- **Till-owned rows** (sales, shifts, stock movements… section 10): the till is the authority. Keep the row
  with the highest `version`; a late, lower `version` is acknowledged and ignored (section 7).
- **Portal-owned rows** (products, prices, promotions, users… section 10): the portal is the authority, and
  its pull `version` — one counter per company, bumped on every change (section 8) — is also each row's
  **revision**.
  - The till never applies a pulled row whose `version` is not higher than the one it last applied for that
    row.
  - **Clash on the till (built):** when a pulled portal-owned row meets the shop's own edit of it that has not
    been pushed yet, the till does not apply it; it records a clash with **your row kept on it** and shows it on
    the Sync status screen. "Head office wins" writes your row (as a pulled row — no ChangeLog, never pushed
    back) and drops the shop's unsent edits of it; "this shop wins" keeps the till's row, which then pushes as
    usual. A newer row from you for a row still in clash replaces the kept one; a newer row that applies normally
    settles the old clash as "head office wins" (§8).
  - **`baseVersion` — not sent yet (§16).** The plan: when the shop edits a portal-owned row, the till pushes it
    with `baseVersion` = the portal `version` it last applied for that row (a new optional envelope field, push
    only, portal-owned rows only; `schemas/sync-change.schema.json` and the samples are regenerated then). Build
    this rule now so it drops in: `baseVersion` equal to your current version for the row → accept, bump the
    version, send the new row to the other branches; `baseVersion` lower (the row changed on the portal
    meanwhile) → **conflict**: your current row wins by default, record the conflict, and send your row down to
    that branch too. **Until it is sent** (no `baseVersion` in the envelope) you cannot tell which of your
    versions the shop edited: decide on your side whether to accept or overwrite a pushed portal-owned row (§10)
    and send your winning version down either way — a row you send down while the shop's edit is still unsent
    becomes the till's clash above.
  - **The till learns the version of its own accepted edit without an echo (2026-09-29).** §19.2 still holds: do
    not send a branch its own row back. When `baseVersion` arrives, compare it with the version the row had
    **before this branch's last accepted edit of it** (keep `origin_branch` and `prev_version` per row): a push
    whose `baseVersion` is the current version, or whose row was last written by the same branch with
    `baseVersion` ≥ that `prev_version`, is not a conflict. (An identical row sent back would be a no-op on the
    till that also records your version — but if the shop edited it again meanwhile it becomes a false clash, so
    do not echo.)
- **Deletes are soft** (`deletedAt`, section 5) and follow the same version rules, so a late update can
  never bring a deleted row back.

### 19.4 Test list the portal must pass before we connect a real shop

These are the sync tests; §21 is the whole guarantees checklist (these plus shop prices, head-office orders,
retried POSTs and secrets), one test per guarantee.

1. Push the same batch twice → one set of rows, identical replies.
2. Reply is lost, the till retries a batch that overlaps the previous one → no duplicates, `acknowledgedSeq`
   still correct.
3. Create a product on the portal → it reaches the till (`pull`) → the till's next `push` does **not**
   contain it.
4. Change a product's price at shop A → the portal gets it once → shop B receives it → shop A does not get it
   back.
5. Change the same product on the portal and at the till before either syncs → one conflict, the portal's
   row wins, both sides end up identical.
6. A delayed, older version of a row arrives after a newer one (either direction) → the newer stays.
7. Delete a product on the portal, then a late till update of that product arrives → it stays deleted.
8. Two tills of one shop both sell offline for an hour, then reconnect → every sale arrives exactly once,
   numbered per till (section 2.4).
9. Kill the connection mid-push and mid-pull a dozen times → the final data on both sides is identical to
   a clean run.
10. Times (6.1): every push reply carries `receivedAt` in UTC with `Z`; a batch pushed twice gets the same
    `receivedAt` both times; every stored row shows its till time and its `received_at`; a product created on
    the portal arrives on the till with the portal's `createdAt` / `updatedAt`; a sale at 23:30 UTC in June
    counts on the next day's trading day.
11. Customer ledger (10.1): an account sale of £8.40 at shop A and a £5.00 payment at shop B for the same
    customer, both offline, then both reconnect → the portal's balance and both tills' balances all move by
    +£3.40, once; relaying the same ledger row twice changes nothing; a `Customer` row you send never changes the
    till's balance or points.
12. Stock transfer (10.2): shop A dispatches a transfer to shop B → B receives the header and every line
    (`lineCount` of them) and can receive it; the relay sent twice is still one transfer; B's receipt is relayed
    to A, whose list then shows Received; neither side ever gets its own rows back.
13. Settings (10.3): change the receipt footer on the portal → it reaches the till and is not pushed back;
    change it at the till → it comes up once as a `Setting` row with `version` = `seq`; send `sync.hub_url`,
    a register-scope row or any key on the deny-list → the till refuses it and keeps its own value; take a
    permission away from a role → the till removes it (never from the Owner role).
14. Order references (10.4): two tills of one shop take a customer order in the same second → two different
    references, each stored once, keyed by `id`.

## 20. Everything reaches you; the till never needs you to trade; how future changes arrive (owner, 2026-09-26)

### 20.1 Everything the shop does comes up

Every till-owned table is pushed — the 115 `"branch"` tables of the 149 names in `samples/ownership.json`, not
just sales — and so is every portal-owned row the shop edits. So the portal can build **every report the till
has**, per business, shop, till and person:

| Report area | Entities that arrive by push |
|---|---|
| Sales, refunds, voids, discounts, VAT | `Sale`, `SaleLine`, `SalePayment`, `SaleVat`, `SalesDaily`, `TenderDaily` |
| Cash-up, shifts, Z reports | `Shift`, `ShiftTender`, `ZReport`, cash movements |
| **Staff: who clocked in and out, when** | `ClockEvent` (each clock in/out with user, till and time), `RotaShift`, `TimesheetApproval`, `WageRate` |
| Stock | `BranchProduct`, `StockMovement` |
| Who did what (voids, refunds, price changes, drawer opens…) | `AuditLog` |
| Customer orders, purchasing, finance | `CustomerOrder…`, `PurchaseOrder`/`GoodsReceipt` (+ lines — including the receiving of your head-office orders, §10.6), `JournalEntry`/`JournalLine`, `VatReturn`… |
| Customer accounts and loyalty | `CustomerTransaction` (the ledger, §10.1) |

`Setting` and `RolePermission` rows come up too since revision 1.4 (§10.3; secrets and device settings never
do). Child rows (`SaleLine`, `SalePayment`, `SaleVat`, order and receipt lines …) carry no `branchId` /
`registerId` of their own — by design: take the branch from `X-SSPOS-Branch-Id` and the till from the parent row
(§16). Customer balances and points are worked out from the `CustomerTransaction` ledger, not read from
`Customer` (§10.1). The only rows that never come up are the local ones (§13) and the few a secondary till keeps
on its own PC (§2 point 2).

**Who approved a refund (revision 1.4).** `Sale.approvedBy` (unchanged field) is the manager whose PIN was keyed —
and now also the operator themselves when a rule asked for a manager and the operator is one. Every approved refund or
exchange also writes an `AuditLog` row: `action: "RefundApproved"`, `entityName: "Sale"`, `entityId` = the refund's
`Sale` id, `userId` = the approver, `at` = the refund's `completedAt`, `afterJson` = its receipt number, total,
operator and approver. Whether refunds need a manager at all is the shop's setting (§10.3).

### 20.2 Offline first — the till never waits for the portal

Written as a rule for both sides (`specs/architecture.md`: "Internet down → full trade, sync later";
`specs/performance.md`: "Cloud sync never slows the till"):

- **Net on:** changes go up and down about every 30 seconds in the background.
- **Net off (minutes or weeks):** the till trades exactly as normal — sales, refunds, cash-up, reports,
  labels, clock-in, everything. Its changes wait in the ChangeLog; the portal's changes wait on the portal.
- **Net back:** both queues drain by themselves, in order, without duplicates (§19), throttled so the till
  stays fast (§18.9). Nobody presses anything.
- **Portal down or slow:** same as net off. A failing portal never shows an error to a cashier — only a
  quiet "last synced …" on the Sync status screen.
- **The one exception is the licence:** a cloud licence that cannot check in for **14 days** locks the till
  (§17.9), with a daily warning before that. Nothing else about the portal can stop a shop from trading.

### 20.3 How future changes reach you

The till will keep growing (new features, new fields, new tables). The contract grows with it, the same
way every time:

1. **Additive only** within `/api/v1` (§17.11): new endpoints, new optional fields, new entities, new enum
   values that older code treats safely. Nothing is renamed or removed without a `/v2`.
2. **The till cannot add a table without deciding who owns it** — a guard test fails otherwise (§10), and
   the schemas and samples are regenerated from the till's code, so this package can never silently fall
   behind.
3. **Every change ships as a new package** named with its date, containing the whole contract plus a
   "What changed" list at the top of `START-HERE.md`: new/changed entities and fields, new endpoints, and
   anything the portal must do.
4. **Your side stays safe in the meantime:** because you keep the full `payload` JSON (§18.8) and ignore
   unknown fields, a new field the till starts sending is already stored before you build a screen for it.
5. **Between packages**, a till-side change the portal should know about is noted in
   `docs/web-portal-api/UPCOMING-CHANGES.md`; the next package folds every note into this document (v1.4 folded
   them all in: the file now says "Nothing pending — everything is in v1.4.").

## 21. Guarantees checklist — what the till promises, what the portal must do, the test that proves it (v1.4)

Each guarantee below is **built on the till** (§16) and holds only if the portal does its part. Run every test
against your test portal with a real test till (§14) before a real shop is connected; §19.4 has the detailed sync
cases the tests refer to.

### 21.1 Every table is synced while the shop is online

- **Till:** every change to a till-owned table (the 115 `"branch"` names in `samples/ownership.json`) and every
  shop edit of a portal-owned row enters the ChangeLog and goes up in the next push — about every 30 seconds, at
  Close Shop and on "Sync now"; a second till's work arrives inside the main till's push (§2 point 2). Every
  portal-owned table (the 30 `"hub"` names), relays (§10.2), settings and role permissions (§10.3), shop prices
  (§10.5) and head-office orders (§10.6) are applied from the pull. Only the local tables (§13) and a secondary
  till's own device rows (§2 point 2) never travel.
- **Portal:** accept every entity name, known or not (store unknown ones raw with their `payload`, §18.8); never
  fail a batch for one row (§9, 422); answer within 2 seconds (§18.9).
- **Test:** on a two-till test shop, within one sync cycle each of these appears on the portal: a sale on till 2
  (with its lines, payment and VAT rows), a refund, a paid-out, a shift opened and closed with its Z report, a
  clock in / out, a stock adjustment, a customer account payment (`CustomerTransaction`), a dispatched stock
  transfer, a price edited at the till, a changed receipt footer (`Setting`). And the other way: a product, a
  barcode, a promotion, a user, a role permission, a setting, a shop price and a head-office order made on the
  portal all show on the till as applied (Sync status), and none of them comes back in the next push.

### 21.2 Times: made at the till, reached the portal

- **Till:** every time is UTC with `Z` (§6.1). `createdAt` / `updatedAt` and the business times (`completedAt`,
  `at`, `openedAt`…) are the till's clock; a sale queued by a second till keeps the time the customer paid
  (earlier than its `createdAt`). The till stores your push reply's `receivedAt` on every acknowledged ChangeLog
  row and shows *Last sent / Last acknowledged / Reached the portal*. Rows you send down keep your `createdAt` /
  `updatedAt`.
- **Portal:** set `receivedAt` from your own clock after the commit; keep `first_received_at` (the row's first
  version) and `last_received_at` (each newer version) on every row, and a `received_at` per `(branchId, seq)` in
  your push log; answer a retried batch with the `receivedAt` its rows were first stored with. Bucket reports by
  the business time in Europe/London (the trading day), sync health by `received_at`.
- **Test:** 19.4 test 10, plus: push version 1 of a row → `first_received_at` = `last_received_at` = t1; push
  version 2 → `first_received_at` stays t1, `last_received_at` = t2; push version 2 again → neither changes and
  the reply's `receivedAt` is still t2; a product you create arrives on the till with your `createdAt`.

### 21.3 No duplicates — several tills, several branches

- **Till:** one sender per branch (its main till), one `seq` series and one pull cursor per branch; every row
  keyed by a ULID made on the till; sales and refunds numbered per till (`(registerId, number)` unique);
  customer-order references `CO-{branch}-{till}-{number}`, unique per shop (§10.4); several entries of one row in
  a push share one triple (§7); a command a second till retries over the shop LAN is run once.
- **Portal:** key rows by `id` (upsert, never a second insert), batches by `(branchId, seq)` (or
  `(uploadId, seq)`), versions by `(entity, entityId, version)`; never key by a receipt number, an order reference
  or a collection token.
- **Test:** 19.4 tests 1, 2, 8, 9 and 14, plus: two tills of one shop and a second shop all sell offline for an
  hour, then reconnect while you cut the connection mid-push several times → every sale is stored exactly once,
  the counts per till equal the tills' own X / Z reports, and Leeds' `seq` 5120 and Bradford's `seq` 5120 are two
  different rows; a push carrying the same row three times (same triple) → one row, `accepted` = 3.

### 21.4 Transfers and head-office purchase orders are relayed

- **Till:** a dispatched `StockTransfer` (+ every line, `lineCount`) can be received once it holds every line,
  and only once; its receipt goes up as the receiving shop's rows; a relayed row is held read-only, never
  overwrites the till's own rows and never goes back up (§10.2). A head-office order (`origin: "headOffice"`)
  shows "From head office" as `HO-…`, is received with the normal goods-in, and may be sent or cancelled at the
  shop; its receipt, status and `receivedQty` go up as the shop's rows; a change from you after the shop sent,
  cancelled or started receiving it is refused and flagged, and a cancelled order is never re-opened (§10.6).
- **Portal:** relay a dispatched transfer and its lines to `toBranchId`, the receipt (+ lines) back to
  `fromBranchId`, every ledger row to every other branch — unchanged, never to the owning branch; draft
  head-office orders with your own per-shop `number`, `status` `draft` / `sent` / `cancelled`, `receivedQty` 0 and
  the `Supplier` sent first; take the shop's pushed status as the truth and stop changing an order once the shop
  has sent, cancelled or started receiving it (draft a new one instead).
- **Test:** 19.4 test 12, plus: send `samples/pull-reply.head-office.json` (with the test till's ids) twice → one
  order `HO-000123` with two lines, nothing pushed back; the shop books a goods-in against it → your next push
  brings the `GoodsReceipt` (+ lines, the shop's `branchId`), the order at `partReceived` / `received` and the
  lines' `receivedQty`; then send a changed order → the till keeps its figures and shows a clash naming
  `HO-000123`; draft a second order as `draft`, cancel it at the shop → your push shows it `cancelled`, and a
  `sent` from you afterwards is refused and flagged; send an order with `origin: "branch"` → refused.

### 21.5 Shop prices (`BranchPrice`)

- **Till:** applies a live `BranchPrice` for its own shop from memory beside the barcode index (scan → line stays
  ≤ 50 ms), under the price-marked-pack rule and above the product's own price; the latest `validFromUtc` wins; a
  price for another shop is skipped; it never edits or pushes one (§10.5). The main till copies the shop's prices
  to its secondary tills over the LAN, and labels, electronic shelf labels, the scale PLU export and customer orders
  use the same price.
- **Portal:** send whole rows (price 2 dp, UTC validity), one row per price period, `op: "D"` to remove; send the
  product first; never expect a `BranchPrice` in a push.
- **Test:** send the two Leeds rows of `samples/pull-reply.head-office.json` (test ids, the dates moved to today)
  → the main till's product form shows "This shop: … — Set on the portal", scanning the loaf rings the live price
  on the main till and, within about 20 seconds, on a second till, and a printed shelf label shows it; send the
  live row again with `validToUtc` = now → the next scan rings the next period's price (or the product's own);
  send `D` → gone; send the same rows twice → nothing changes; a row for another shop → ignored there; a
  price-marked pack still rings its marked price.

### 21.6 Offline catch-up, in order

- **Till:** trades fully offline for minutes or weeks; its changes wait in the ChangeLog and go up oldest `seq`
  first (at most 5 batches per run, a run every 30 seconds until the queue is empty; back-off only after
  failures); your changes are pulled oldest `version` first, up to 10 pages per run while `hasMore`; a child that
  beats its parent is parked on disk for up to 7 days; the pull runs even after a failed push (§8, §9). Nobody
  presses anything.
- **Portal:** store rows in `seq` order and acknowledge only a contiguous prefix; serve pull pages oldest first
  with a truthful `hasMore`; keep your pull `version` strictly increasing; bucket late rows by their business
  time, not by arrival.
- **Test:** take a two-till test shop offline for a day while it trades and you change prices, a setting and a
  head-office order → on reconnect `acknowledgedSeq` only moves forward, every row arrives once, the day's
  reports equal the tills' Z reports, and every portal change is on the till; send a `ProductBarcode` before its
  `Product`, restart the till, then send the product → the barcode is applied.

### 21.7 Retries are idempotent

- **Till:** retries a push after any failure with the same rows (possibly a newer state under a newer version,
  §7); repeats every POST with the same `Idempotency-Key` and the first attempt's body byte for byte until you
  answer — across restarts, for up to 12 hours (§17.11 rule 5).
- **Portal:** push: same triple → same effect and the same reply (incl. `receivedAt`); POST: store `(key,
  endpoint, caller, body hash) → reply` for 24 hours and replay it for the same body, 422
  `request.idempotency_mismatch` for a different one, 409 `request.in_progress` while the first still runs; never
  store a 408 / 429 / 502 / 503 / 504 / 409 `request.in_progress` reply under the key.
- **Test:** replay each POST of the Postman collection with the same key and body → the same status and body; the
  same key with another body → 422; two at once → one 409 `request.in_progress`; make `licence/activate` time out
  after you committed, then let the till retry → the same binding and a token, never 409 `key.already_used`;
  answer a history-upload batch 503 once → the retry with the same key is stored once.

### 21.8 Secrets never leave the till

- **Till:** never sends `User.remoteApprovalSecret` / `remoteApprovalSecretSetAt`, a deny-listed setting
  (`sync.*`, `licence.*`, keys, passwords, device and printer settings…) or a register-scope setting; never
  applies one from a pull; keeps a user's PIN when a pulled `User` has no `pinHash`; never writes a key, code or
  token to its log (§10.3, §10.7).
- **Portal:** keep the private signing key in a secret store (§17.2); store API keys, sync keys, licence keys and
  codes hashed; never put one in a URL, a log line or any e-mail other than the one that delivers it; never send a
  deny-listed setting down.
- **Test:** search every payload you stored for `remoteApprovalSecret`, `hub_api_key`, `password`, `secret` →
  none; send a `User` row without `pinHash` → that user still signs in with their PIN; send `sync.hub_api_key` as a
  `Setting` row → the till refuses it (see its log) and keeps its own; your access and error logs hold no
  `Authorization` header, licence key, sync key or token.
