# Hissa A — aap ke sawalon ke jawab

## Licence

**1. `devices/deactivate` per-till — haan, theek hai.** Per-till till ko `registerId` + `installId` se pehchanein
(§17.7). `apiKeyRevoked: false` theek hai — till 200 par apna cloud link (sync key) aur licence **khud** bhool jata
hai, is flag par nahi chalta; yeh sirf AuditLog mein likha jata hai. Aik baat: agar woh till branch ka **main till**
tha aur aap ne licence reply mein us ko branch ki sync key (`apiKey`) di thi, to us key ko portal par bhi band ya
rotate karein (restore kiya hua purana PC push na kar sake) — tab `apiKeyRevoked: true` bhejein.

**2. `expiresAt` mein grace days — mat daalein.** `graceDays` (14) sirf **offline** ki mohlat hai: kitne din
`validate` ke baghair chal sakta hai (§17.9). Expiry ki koi grace nahi. Till `expiresAt` ko hi "Your licence ends
on …" mein dikhata hai, 7 din pehle warning deta hai, aur `expiresAt` guzarte hi lock karta hai
(`LicenceEvaluator`). Agar aap 14 din jorein ge to banner 14 din aage ki tareekh dikhayega aur shop 14 din muft
chalegi. `expiresAt` = asal paid end date. Payment ki mohlat deni ho to admin `expiresAt` barha kar naya token
bheje (validate par till le leta hai) — aur `messages[]` se "renewal pending" batayein.

**3. `minimumAppVersion` / 426 — policy:**
- `minimumAppVersion` validate reply mein **bhejte rahein** (abhi till is par kuch nahi karta, §17.5 note) — sab
  se purana supported version, abhi `0.1.0` rakhein (till abhi `X-SSPOS-App-Version: 0.1.x` bhejta hai, §3 ka
  "3.x.y" nahi — semver ki tarah compare karein). Owner ke kahe baghair na barhayein.
- **426 kabhi `licence/*` par na dein.** Till ise "check nahi hua" samjhta hai: 14 din yahi chala to shop lock ho
  jayegi — sirf is liye ke update nahi hua.
- 426 sirf `sync/*` par, aur sirf tab jab koi version aap ka data **kharab** karta ho (owner se poochh kar). Till
  trading jaari rakhta hai, sirf sync restart/update tak ruk jata hai.

## Sync

**4. Kam `acknowledgedSeq` — haan.** Till `min(acknowledgedSeq, batch ka aakhri seq)` tak sab ko sent mark karta
hai aur baaqi `acknowledgedSeq + 1` se **agle run** mein (~30 s, ya "Sync now") dobara bhejta hai — us run mein
aage ka koi batch nahi bhejta (`HubSyncAgent.PushAsync`). 200 ke saath `acknowledgedSeq: 0` bhi theek hai: kuch
mark nahi hota, poora batch dobara aata hai. 422 sirf tab — aap ka tareeqa bilkul sahi hai.

**5. `X-SSPOS-Store-Protocol` — sirf informational.** Till ke andar store server ke protocol ka number hai (abhi
`3`). Portal ke liye koi matlab nahi — log kar lein, koi bhi number qubool karein, is par kuch reject na karein
(§3). Version check ke liye `X-SSPOS-Contract` (1) aur `X-SSPOS-App-Version` hain.

**6. Till apne edit ka naya version kaise seekhe — use seekhne ki zaroorat nahi.** Abhi till `baseVersion` bhejta
hi nahi (§16), is liye aaj kuch nahi karna. Jab aayega to portal side par: har portal-owned row par
`origin_branch` aur `prev_version` (is branch ke edit se pehle ka version) rakhein. Push ka `baseVersion` = current
version → theek; row aakhri dafa **isi branch** ne likhi thi aur `baseVersion ≥ prev_version` → bhi theek, conflict
nahi. Row wapas (echo) mat bhejein: identical row till par no-op hai aur version record bhi ho jata hai, lekin agar
shop ne beech mein dobara edit kiya ho to till jhoota clash dikhayega. §19.3 mein yeh likh diya hai.

**7. "Same content" check — haan.** Till `id`, `companyId`, `createdAt`, `updatedAt` aur `rowVersion` ko
nazarandaaz karta hai (`HubRowMaps.TillStampedColumns`); baaqi har column EF ke comparer se milata hai. Sirf times
mukhtalif hon to kuch nahi likhta (koi ChangeLog nahi). Identical row ka version phir bhi "applied" record hota hai.

**8. `receivedAt` — haan, pehle se hai.** v1.4 mein `schemas/push-reply.schema.json` mein **required** hai (UTC `Z`,
aap ke commit ke baad ka waqt; retry par wahi pehla waqt — §7). Till use `PortalReceivedAt` ke taur par save karta
hai.

# Hissa B — aaj (29 Sep) till mein jo badla

Koi endpoint, envelope ya header nahi badla; `X-SSPOS-Contract` abhi bhi `1`. Sirf naye rows / fields aur kuch rows
ke naye likhne wale. Schemas aur samples package mein update hain.

1. **Shop par price, offer, discount — "sirf yeh shop ya har shop"** (poori tafseel `SHOP-OR-EVERY-SHOP.md`):
   - **`BranchPrice` ab till bhi push karta hai** (`I` nayi row, `U` purani row ka `validToUtc` band) — aap ki rows
     bhi band ho sakti hain. Qubool karein, sirf usi branch ki (`branchId` ≠ push karne wali branch → refuse).
     Apni nayi price hamesha **nayi row** (baad wala `validFromUtc`) ke taur par bhejein, till ki row edit na
     karein. Ownership wahi hai (`hub`).
   - "Har shop" = `Product.sellPrice` badalta hai + us shop ki apni `BranchPrice` band hoti hai; doosri shops ki
     apni price rehti hai (clear karni ho to portal ka faisla).
   - **`PromotionRule.branchId`** ab bhara aata hai (multi-shop mein shop ka offer/discount = us shop ki id, har shop =
     `null`). Jaisa aaye waisa rakhein; aik target par shop wala aur har-shop wala **do alag rows** hain, merge na
     karein.
   - Nayi permission **`business.apply_all_shops`** (Manager, Owner) — `RolePermission` mein aati hai, apne role
     editor mein daal lein.
   - `PriceChangeLine.branchId` ab bhara aata hai (`null` = har shop).
   - `ProductUnit` save par ab wahi `id` rehti hai (`U`), pehle ki tarah `D` + `I` nahi.
   - AuditLog: `BranchPrice` / `PriceThisShop`, `PriceEveryShop` (`approvedBy`).
2. **Purchase returns — 2 naye branch-owned tables:** `PurchaseReturn`, `PurchaseReturnLine` (schemas
   `schemas/entities/`). Portal ke liye read-only, `GoodsReceipt` / `SupplierCreditNote` ki tarah. Damaged maal wala
   goods-in return kholta hai (`goodsReceiptId`); `status` Draft → Sent → Credited (ya Cancelled); `reference`
   `PR-{shop code}-00012`. Credit milne par aam `SupplierCreditNote` row bhi aati hai (`reason` "Purchase return PR-…").
3. **`PurchaseOrder`: naye fields `branchCode` aur `reference`** (`PO-LDS-000001`, head office ka `HO-LDS-000123`).
   Portal par `reference` dikhayein — do shops dono ka `PO-000001` ho sakta hai. `branchCode` till khud likhta hai,
   pull mein `""` bhejein ya chhor dein. Purane orders upgrade par dobara `U` ho kar push hue (naya `rowVersion`).
   Key hamesha `id`.
4. **Naye fields:** `GoodsReceiptLine.damagedQty` (decimal), `SupplierInvoice.goodsReceiptId` (invoice kis delivery
   ka hai, `null` ho sakta hai).
5. **`CustomerOrder.token`** ab aik shop ke **khule** orders mein unique hai (till par index); band order ka code
   dobara aa sakta hai — is par key na karein. Upgrade par duplicate codes `…-2`, `…-3` ho kar `U` push hue.
   Customer order line jis ka order doosri shop ka ho, till refuse karta hai.
6. **Naye settings, sirf till ke (kabhi sync nahi hote):** `till_ease.big_text`, `cash.count_on_close`,
   `till.keypad_price_in_pence` (`samples/settings-local-only.json`).
7. Aaj ki baaqi tabdeeliyan (category colours, shift close, card payment, printers, refunds) sirf till screen ki
   hain — portal par koi asar nahi.

Test server chalu hote hi base URL, public key aur test licence keys bhej dein — phir end-to-end test karte hain.
