# Portal v1.4.1 ke sawalon ke jawab — 2026-09-29 (b)

Har jawab till ke code se check kiya gaya hai (file:line neeche). Jahan till mein kami thi wo isi change mein theek
ki gayi hai — woh cheezein **agli till release** mein jayengi (aakhir mein list).

## A. Sync / pull

1. **pinHash / rfid.** Haan, dono pull se parhe jaate hain (`User` hub-owned hai). Jo member payload mein **na ho**
   uski purani value till rakhta hai — yeh har column ke liye hai (`HubRowMap.TryRead` sirf maujood fields parhta hai).
   `pinHash` ke liye `null` / `""` bhi "na hona" samjha jata hai — PIN kabhi nahi mit-ta. **Naya (v1.4.1 till):** `rfid`
   bhi ab isi tarah — `null` / `""` / missing = fob wahi rehta hai; fob till par hi hataya jata hai
   (`Domain/Sync/SyncSecretColumns.cs` KeptWhenBlank). Purani till par `rfid: null` ya `""` fob mita deta tha — is liye
   jab tak value pata na ho, `rfid` field **bhejein hi nahi**.
2. **I aur U.** Dono upsert hain. Till `op` nahi dekhta (sirf `D`): row na ho to insert, ho to update
   (`Infrastructure/Persistence/Sync/HubEntityApplier.cs:245-247`). Test:
   `HubEntityApplierTests.IAndU_AreBothUpserts_UOnAMissingRowInserts_IOnAHeldRowUpdates`.
3. **NewsTitle doosri shop mein.** **Naya (v1.4.1 till):** purani shop ko nayi `branchId` wala **U kaafi hai** (ya D —
   dono chalte hain). Till dekhta hai ke yeh row uske paas apni shop ki thi aur ab doosri shop ki hai → apni copy
   soft-delete (`deletedAt` = envelope `at`), doosri shop ki values nahi leta (`HubEntityApplier.MoveAwayAsync`, :415).
   Wapas laane ke liye poori row is shop ki `branchId` aur `deletedAt: null` ke saath bhejein. Yahi `BranchPrice` par bhi
   lagu hai. **Purani till** (0.1.8 tak) aisi U ko "doosri shop ki row" keh kar skip karti hai — us par move ke liye
   **D bhejein, envelope `branchId` = purani shop, aur payload ya to na ho ya purani `branchId` ke saath**.
4. **Gzip.** Till pehle se har sync call (hello, pull, push, migrate) par `Accept-Encoding: gzip` bhejta hai
   (`Infrastructure/Sync/HubRequests.cs:79`) aur `Content-Encoding: gzip` reply khud khol leta hai
   (`HubHttpChannel.cs:49`). Push body gzip hai. Naye tests: `HttpsHubTransportTests.PullAsync_AsksForGzip_AndReadsAGzippedPage`,
   `PushAsync_AlsoAsksForAGzippedReply`. Aap ko header nahi mil raha to beech ka proxy / CDN check karein — till bhejta hai.
   Licence calls (`licence/*`) gzip nahi maangte — un ka jawab plain JSON.
5. **Till yeh sab qubool karta hai:**
   - **Relay rows** (doosri shop ka transfer / receipt, customer ledger): haan. Shart: envelope `branchId` = **receive
     karne wali** shop (ya `""`), payload ki `branchId` = **maalik** shop; is shop ki apni row kabhi relay na ho (§10.2,
     `HubRelay`).
   - **Setting / RolePermission** ids till ke formula se: haan — aur koi bhi id ho, till payload ki key se apni id bana
     leta hai (`KeyedRows.Canonical`, `KeyedRows.cs:119`; test `KeyedSyncTests.ThroughTheFeed_ThePortalsOwnIdIsReplacedByTheKeyedId`).
     Aap ka formula wala id bhejna best hai (push aur pull ek hi id).
   - **Head-office PO `rowVersion: 0`, `branchCode: ""`**: haan. `rowVersion` pull se kabhi nahi parha jata
     (`HubRowMaps.cs:61` TillStampedColumns); `branchCode` bhi nahi — till apni shop ka code khud lagata hai
     (`HubRowMaps.cs:87`, `HeadOfficeOrders.StampBranchCodeAsync`, `HeadOfficeOrders.cs:70`). Naya test:
     `HeadOfficeOrderRelayTests.Relay_AHeadOfficeOrder_WithRowVersionZero_AndABlankBranchCode_IsTaken` (op `I`).
6. **nextPoNo.** Till isay kabhi kam nahi karta. Purani till ise bilkul nahi parhti thi. **Naya (v1.4.1 till):** agar
   aap ki value till se **ziada** ho to le leta hai (naye PC par PO number dobara use na ho); kam / barabar / `null` /
   ghalat value ignore, aur baqi Branch row phir bhi lagti hai (`HubRowMaps.cs:51` RaiseOnlyCounters,
   `HubColumn.KeepsTillValue`). Test: `HubEntityApplierTests.BranchNextPoNo_IsRaisedByAPull_NeverLowered_AndABadValueNeverCostsTheRow`.
   Head-office PO ke number (`HO-…`) alag silsila hain, is counter se nahi.

## B. Settings — `cash.count_on_close`, `till.keypad_price_in_pence`

**File sahi hai: dono SHARED hain.** Pehle wala "till-only" jawab ghalat tha. Dono Branch scope par hain
(`Domain/Common/SettingDefinitions.cs:171` aur `:328`), deny-list (`Domain/Sync/SettingSyncPolicy.cs`) mein nahi, aur
`samples/settings-local-only.json` isi code se generate hoti hai. Dono shop ki policy hain: count-on-close W7 cash-up
ka qaida hai (specs/workflows.md W7), keypad-pence Cart & Scanning tab par hai jo main till se har secondary till par
copy hota hai (sirf "This till" wale tabs per-PC hain — `Desktop/Features/Settings/SettingsLayout.cs` ThisTillPages).
Portal inhein branch scope par share kare — jaise abhi kar rahe hain. Koi change nahi.

## C. Licence — `licence.ids_conflict` (409)

Haan, code rakhein. Ab `licensing/samples/error-codes.json`, §17.12 table aur `openapi.yaml` mein hai (endpoints:
`licence/activate`, `licence/validate` — agar `licence/redeem` par bhi bhejte hain to batayein). Till ka rawaiya:
- **activate:** kuch save nahi hota, aap ka `message` dikhata hai (na ho to: "already linked to another licence … call
  your dealer") (`ActivateLicenceHandler.PortalRefusalMessage`).
- **validate:** kuch nahi badalta, till **lock nahi hota**, token aur grace chalte rehte hain; "Licence details need
  checking" warning dikhata hai (aap ka `message`, max 500) (`LicenceCheckIn.IdsConflict`).
- **redeem** (local key report): doosre "settled" refusals ki tarah — key rakhi jati hai, dobara report nahi hoti.
`message` en-GB mein aur shop owner ke liye likhein (dealer ka number de sakte hain).
