# Data audit, 2026-10-11

Scope: reporting (`rpt_*`, dirty days, trading day per country zone, VAT/GST, tenders incl. PK wallets, refunds and
voids, stock, shifts and Z, cash), tenant and admin dashboards, report figures against raw till rows, scheduled
commands, queued jobs, migrations, performance on MySQL 8, caching, logging, retention and prunes, the UK clock
change on 2026-10-25, money precision, PK rupee formats.

Method: code read; new Pest tests in `tests/Feature/Audit/DataAuditTest.php` (SQLite, the normal suite); a volume
run on MySQL 8.0.35 (database `retail_v2_audit_data`, MAMP) with EXPLAIN on the heaviest queries. No app code was
changed. Branch `audit/2026-10-11-data`, not pushed. The audit tests pass on SQLite and on MySQL 8
(`phpunit.mysql.xml`).

**How the tests work.** Each `DATA-n` test pins today's behaviour of a finding, so the suite stays green. When a
finding is fixed, its test fails: flip the expectation to the fixed behaviour. The `fine:` tests prove what is
correct.

## DATA-1 (High): queue `retry_after` (90 s) is shorter than the long jobs' timeouts, so a slow job runs twice at once

**What.** Both queue connections hand a reserved job to another worker after `retry_after` seconds, default 90
(`config/queue.php:42` database, `:70` redis; nothing in `.env.production.example` or the repo overrides it). Several
jobs are allowed to run much longer:

| Job | `$timeout` | `tries` | What a second, concurrent copy does |
|---|---|---|---|
| `Sales\Jobs\BuildSalesExportJob` (`:23`) | 1800 | 2 | `isPending()` counts `Running` as pending (`ExportStatus.php:13-16`), so the copy runs too; `BuildSalesExport.php:26` reopens the same CSV with `fopen(…, 'w')`, truncating what the first copy has written. Both write to one file: the customer downloads a corrupt or short CSV, or the export flips Ready → Failed (`failed()` after the second attempt) |
| `Catalogue\Jobs\ApplyProductImportJob` (`:27`) | 300 | 3 | each copy dispatches the next chunk (`:55`): the import chain forks and rows are applied twice |
| `MasterCatalogue\Jobs\MasterImportJob` (`:25`) | 300 | 3 | same fork (`:40`) |
| `Purchasing\Jobs\ReadInvoiceJob` (`:28`) | 300 | 1 | the second pick-up exceeds `tries=1`: `failed()` marks the import Failed while the first copy is still reading (and paying for) the invoice |
| `Reporting\Jobs\ProcessDirtyReportDaysJob` | none | – | the worker's default `--timeout=60` applies (`deploy/supervisor/retail-v2-worker.conf` sets none): a big rebuild (an initial upload, `dirty_passes` × `dirty_batch` = up to 10,000 shop-days) is killed every 60 s. Progress is kept (one transaction per 7 days) and the job retries for 30 min, so it heals, but it fills `failed_jobs`/logs and delays reports |

Laravel's own rule: a job's timeout must be several seconds shorter than `retry_after`. With 2 workers per instance
(`numprocs=2`) the second worker is always free to pick the job up.

**Who.** Any business running a big sales export, product import or invoice read, on the UK and the PK instance.
Realistic volumes: a year's export of one 3-shop business (273,750 sales) took **1,163 s** on the audit MySQL
(see Performance), far past 90 s; even several times faster on production it stays past 90 s.

**Proof.** `DATA-1` test (config and job properties). The server's real `.env` was not read (no ssh): check
`REDIS_QUEUE_RETRY_AFTER` / `DB_QUEUE_RETRY_AFTER` and the worker unit's `--timeout` on both instances.

**Fix.** Put long jobs on their own queue/connection: e.g. a `redis-long` connection with `retry_after` 1900 and a
worker `queue:work redis-long --timeout=1800`; or raise `REDIS_QUEUE_RETRY_AFTER` to 1900 and run the workers with
`--timeout=1790`. Give `ProcessDirtyReportDaysJob` a `$timeout` (e.g. 600) below `retry_after`. Make exports
idempotent against a concurrent copy: claim with `UPDATE … SET status='running' WHERE status='queued'` and write to
`{id}.{attempt}.csv.partial`, then rename. Raise `stopwaitsecs` to the longest timeout.

**Risk of fix.** Low. A larger `retry_after` only delays the retry of a job whose worker died; report rebuilds are
also covered by the minutely sweep. Change config, `php artisan optimize`, `queue:restart`.

## DATA-2 (Medium): `alerts:digest` stops at the first business that fails; a rerun can send twice

**What.** `SendDigests::handle()` (`app/Domain/Notifications/Actions/SendDigests.php:52-59`) walks every business with
`chunkById` and no try/catch. Any exception for one business (a deadlock, a bad row in findings or the morning
summary, `$summary['url'] ?? $sections[0]['url']` at `:124` with no url and no sections) ends the run: every business
after it in id order gets no digest and no morning summary that day, and the same business fails again the next day,
so the same tail of businesses never gets one. The mail is queued (`:108`) before the `AlertDispatch` row that marks
it sent is created (`:126`), with no transaction, so a failure between them and a rerun send the digest twice.

**Who.** Every business with a higher id than a failing one (UK and PK), daily.

**Proof.** `DATA-2` test: a simulated error while handling the first business; the second business's owner gets no
digest.

**Fix.** try/catch per business (log with company id, `report($e)`, carry on, return a failure exit code at the end);
create the `AlertDispatch` row first (or in a transaction with the inbox entry) and queue the mail after commit.

**Risk of fix.** Low.

## DATA-3 (Medium): `privacy:retention --apply` takes the same 500 customers every day; if they owe money nobody else is anonymised

**What.** `ApplyRetention::handle()` (`app/Domain/Privacy/Actions/ApplyRetention.php:44`) takes
`RetentionDue::query()->orderBy('id')->limit(500)`. Customers with a non-zero balance are refused by
`AnonymiseCustomer` (`:58-63`) and skipped, but stay due, so they come back first every day. A business with 500 or
more unsettled old accounts never anonymises anyone else. Also `PrivacyRetentionCommand` has no per-business
try/catch (one failure stops the rest).

**Who.** Businesses that turned on automatic anonymising and have many old accounts with a balance (paper rounds,
tabs). GDPR: personal data kept past the owner's own retention period.

**Proof.** `DATA-3` test: 500 owing customers with low ids and one settled due customer; three daily runs anonymise
nobody.

**Fix.** Exclude unsettled customers in `RetentionDue::query()` for the apply path (a `NOT EXISTS`/`HAVING` on the
ledger balance), or page by id after the last one tried. Count the skipped ones on the privacy page.

**Risk of fix.** Low (changes which customers are picked, not what anonymising does).

## DATA-4 (Low): re-marking a dirty day moves `marked_at` forward, so the sweep skips a shop that keeps pushing

**What.** `DirtyDays::mark()` upserts `marked_at = now` (`app/Domain/Reporting/Support/DirtyDays.php:39`). The sweep
(`reports:process-dirty`) only re-queues businesses with a day marked more than 2 minutes ago
(`ReportsProcessDirtyCommand.php:24`). If a rebuild job is lost while the till keeps pushing every minute, the day is
re-marked before it ever looks 2 minutes old. Bounded in practice: each push dispatches the job again once its
unique lock (`uniqueFor` 600 s) is gone, so the delay is at most ~10 minutes, but the sweep's safety net does not
cover this case.

**Proof.** `DATA-4` test: ten pushes a minute apart, the sweep never queues.

**Fix.** Keep the first `marked_at` (update only `token` on conflict; or add `first_marked_at`).
**Risk of fix.** Very low.

## DATA-5 (Low): daily prunes on tables with no index on the prune column

**What.** `model:prune` runs `prunable()` queries `WHERE created_at < ?` (chunked by id) on `ai_usage`
(`AiUsage.php:84`), `anomalies` (`Anomaly.php:91`), `morning_summaries` (`MorningSummary.php:47`),
`ai_pending_actions` (`AiPendingAction.php:108`) and `WHERE updated_at < ?` on `ai_conversations`
(`AiConversation.php:108`). None of these columns has an index that starts with it, so each chunk is a full table
scan, and on MySQL REPEATABLE READ the delete's scan locks rows it reads (can stall AI usage logging or anomaly
writes for the length of the scan). The tables are small today. `email_logs` and `alert_notifications` are indexed.
The three AI models are pruned by one command: an exception on the first skips the other two.

**Proof.** `DATA-5` test (indexes).
**Fix.** Add `index('created_at')` (and `updated_at` on `ai_conversations`); additive migrations on small tables.
**Risk of fix.** Very low.

## DATA-6 (Medium): "Today" compares up to now against the whole current hour of the compare day

**What.** For Today, the headline tiles compare today so far with the compare day "up to the same hour"
(`DashboardKpis.php:32` → `SalesReport::upToHour()`, `hour <= $currentHour`, `SalesReport.php:87-95`). At 10:05 the
compare day's whole 10:00–10:59 hour is counted while today has five minutes of it. Every morning the change
reads worse than it is (in the test −50 % where the true figure is 0 %), most at the start of each hour and in
quiet shops.

**Who.** Every business dashboard (and the admin trading dashboard, which uses the same `DashboardKpis`) on
Today, UK and PK.

**Proof.** `DATA-6` test.

**Fix.** Compare completed hours only (`hour < currentHour`, and today's figures up to the same point), or pro-rate
the current hour, or compare against raw sales up to the same minute for the one current hour (`sales.completed_at`
within today's and the compare day's partial hour, indexed by `(company_id, branch_id, completed_at)`). Keep DST in
mind: on 25 Oct hour 1 holds two hours.

**Risk of fix.** Low (display only).

## DATA-7 (High): `billing:run` has no per-business isolation; one bad business skips every later business and step

**What.** `RunBilling::handle()` (`app/Domain/Billing/Actions/RunBilling.php:43-48`) runs its steps in sequence;
each loops over businesses with no try/catch: `MarkOverdueInvoices.php:42`, `SuspendForUnpaidInvoices.php:49`,
`SendTrialEmails.php:54`, `GenerateDueInvoices.php:47` (catches only `ValidationException`, `:81`) and the Direct
Debit enforcement. An exception for one business (a DB error, a mailer/recipient error, a bad row) aborts the run:
later businesses are not invoiced, overdue invoices not marked, unpaid businesses not suspended, trial emails not
sent. If the cause is data, it repeats every day. The steps are idempotent, so a rerun after a fix is safe.
`billing:reconcile-gocardless` catches only `GoCardlessException` per business (`ReconcileGoCardless.php:74-79`).

**Who.** UK (GoCardless) and PK (manual billing: overdue and suspension steps); our own revenue.

**Proof.** Code read (same pattern as DATA-2, which has a test).

**Fix.** try/catch per business inside each step, report and continue, exit non-zero at the end and show the failed
businesses on admin System health.

**Risk of fix.** Low; behaviour for healthy businesses is unchanged.

## DATA-8 (Medium): other scheduled commands without per-business isolation

`anomalies:detect` (`DetectAnomalies.php:66-73`: detector errors are caught, `RecordAnomalies` /
`DispatchAnomalyAlerts` are not), `privacy:retention` (`PrivacyRetentionCommand.php:30-40`) and
`labels:queue-offers` (`QueueOfferDayLabels.php:25-31`, one bad rule stops the run) share DATA-2's pattern: one business's error stops all later ones,
and the command still reports success where errors are swallowed. `anomalies:detect --daily` and
`labels:queue-offers` only look at yesterday/today, so a missed run (deploy, scheduler down) is never caught up.
**Fix:** per-business try/catch; remember the last day processed and catch up. **Risk:** low.

## DATA-9 (Low): one failing row can write thousands of error lines per push

`ChunkApplier::apply()` (`app/Domain/TillData/Sync/ChunkApplier.php:40-58`): when a 500-row chunk throws a
`QueryException`, every row is retried alone and each failure is logged with `Log::error`. A schema mismatch (a new
till field too long for a column) fails every row: a 5,000-row push writes 5,000 error lines plus 5,000 single-row
transactions, and the till retries. The logged message is the driver's (`getPrevious()->getMessage()`), which for
"Duplicate entry 'x'" and "Incorrect … value: 'x'" contains the value, against the "never log the payload" comment.
Also noisy every push: `UnknownEntityRows.php:38`, `ApplySyncChanges.php:244`, `NeverStored.php:94`,
`PushChanges.php:210` (no de-duplication).
**Fix:** bisect the chunk instead of row-by-row; log one line per push with counts and the first error's SQLSTATE
and column only; rate-limit the per-push warnings per branch (once an hour). **Risk:** low.

## DATA-10 (Low): admin trading "tills traded" counts sales without a till as one till

`AdminTradingReport::activity()` / `topBranches()` (`AdminTradingReport.php:61,73`) use
`COUNT(DISTINCT register_id)`; the rebuild stores a sale with no register as `register_id = ''` (`ReportRowBuilder::id()`),
which counts as an extra till. Only when tills push sales without `registerId`. **Fix:** `COUNT(DISTINCT NULLIF(register_id, ''))`.

## DATA-11 (Low): stock value nets off negative stock

`StockLevels::summary()` (`app/Domain/Reporting/Reports/Queries/StockLevels.php:38`) sums `qty_on_hand × cost` over
every tracked line, so lines below zero (common before a delivery is booked) reduce the stock value; per-line values
are rounded to pence while the total is rounded once, so the column does not add up to the total by a few pence.
**Fix:** value `GREATEST(qty_on_hand, 0)` (and show the negative lines separately), round per line before summing.
Check with the owner which the till's own valuation does.

## DATA-12 (Low, PK): cash rounding makes takings and tenders differ with nothing explaining it

Pak POS rounds cash to the rupee (contract UPCOMING-CHANGES 2026-10-07): payments less change differ from
`Sale.total` by up to Rs 0.50 per cash sale. Takings (`Σ Sale.total`) and the tender table (`Σ amount − cashback −
change`) are both shown on the dashboard and sales report, and differ by the day's rounding with no line for it.
**Fix:** add a "Cash rounding" line (takings − Σ tenders) to the tenders table on PK. **Risk:** none for the UK.

## DATA-13 (Low): two time-zone settings can disagree

Trading days use `config('reporting.timezone')` (`REPORTS_TIMEZONE` may override, `TradingDay::timezone()`), while the
scheduler (`->timezone(Country::zone())` in `routes/console.php`), report CSV times (`ReportCsv.php`, `cell()`), billing
dates and `SyncStatusRecorder`'s "today" use `Country::zone()`. Equal today on both instances; if anyone sets
`REPORTS_TIMEZONE`, the digest's "yesterday", the anomaly day and CSV times drift from the report days.
**Fix:** drop `REPORTS_TIMEZONE` or make `Country::zone()` the only source.

## DATA-14 (Low): hourly "sales gap" alerts read `rpt_sales_hourly` without checking the rebuild backlog

`SalesGap` (`app/Domain/Anomalies/Detectors/SalesGap.php:41-56`) raises "No sales have reached the portal" from the
`rpt_*` hours. When rebuilds lag (DATA-1's 60 s kills, a long initial upload), sales that did reach the portal are
not in `rpt_sales_hourly` yet and the owner gets a false alert. **Fix:** skip shops with dirty days for today
(`rpt_dirty_days`), or read `sync_branch_status.last_push_at`.

## DATA-15 (Low): the sync ledger is never pruned

`sync_applied_changes` gets one row per pushed change (more rows than sale lines) and has no prune; DECISIONS
"Open items (4)" planned 90 days in module 2.7, not done. It is the biggest-growing table after the raw till rows.
**Fix:** prune by `applied_at` (index exists) older than N days, keeping the highest seq per stream. **Risk:** a till
re-pushing a change older than N days would apply it again (rows are idempotent by row version, so low).

## DATA-16 (Medium): product figures read the business's whole history in `rpt_product_daily`, whatever the date range

**What.** `ProductReport::top()/byDepartment()/byCategory()` (dashboard) and `ProductBreakdown` (product and
department reports) group `rpt_product_daily` by product. MySQL picks the PRIMARY key
`(company_id, branch_id, trading_day, …)` with only `company_id` usable (no shop filter), i.e. every row the
business ever had, then filters the dates (`EXPLAIN`: `type=ref key=PRIMARY rows=670,018`, `Using where; Using
temporary; Using filesort`), not `rpt_product_daily_company_day_index` (66,690 rows for the 30 days), also after
`ANALYZE TABLE`. `rpt_product_daily` is by far the biggest rpt table (about 800 rows per shop-day: one per product
per till). The cost grows every month the business trades, not with the range asked for.

**Measured** (audit MySQL, see Performance): business dashboard Last 30 days **60 s**, a 1-year custom range
**243 s**; the three product queries are the slowest three each time (17–20 s each for 30 days). The same query
forced onto the day index: 10.2 s instead of 17.3 s on this machine. Absolute numbers are inflated by the audit
machine (load ~30, 128 MB buffer pool); production (6 GB buffer pool) will be several times faster, but the
history-wide scan stays and repeats on every dashboard load after the 60 s cache.

**Who.** Bigger and older businesses, every dashboard and product/department report load; also the admin
trading dashboard's product tiles if any.

**Fix.** `forceIndex('rpt_product_daily_company_day_index')` in `ReportScope::query()` when no shop is chosen (as
`SaleFacts` already does on `sales`), or a covering index `(company_id, trading_day, product_id)`; longer term a
monthly product summary for ranges over ~3 months. Re-check with `EXPLAIN` on production data.

**Risk of fix.** Low; an additive index on a disposable table (build online, or rebuild the table).

## DATA-17 (Low): "N sales" counts with a rare filter scan the whole range

`SaleSearch::countUpTo()` caps the count at 10,001 matches, but with a rare filter (refunds, ~2 % of sales) over a
long range no cap is reached and every sale of the range is visited: Refunds over a year took 15.4 s on the audit
MySQL versus 0.3–0.7 s for common filters. The page itself stays fast (keyset). **Fix:** for refunds/voids add
`(company_id, type, trading_day)` / `(company_id, status, trading_day)` indexes, or skip the count when the range is
over ~90 days and show "many".

## What was fine (checked, with proof where noted)

- **Report figures equal raw till rows**, UK and PK, on the 25-hour clock-change day 2026-10-25: gross (Σ SaleVat),
  takings (Σ Sale.total), tenders (Σ amount − cashback − change of approved/recovered payments), transactions and
  refunds from `rpt_*` match independent sums over the raw rows of the local day's UTC window; voids, training,
  quotes and open baskets are counted nowhere but `void_count`; hourly transactions add up to the day
  (`fine:` test, both zones). A full `reports:rebuild` after incremental pushes changes nothing and `reports:check`
  is clean (`fine:` test).
- **Trading day and DST.** Stamped in PHP at ingest from the country zone (`TradingDay`, `SaleDayStamper`); 25 Oct:
  both 01:xx hours in hour 1, 23:59:59 GMT on the 25th, 00:00 BST start; shifts, Z reports, cash and card
  reconciliation all filter with `TradingDay::window()` (23/24/25-hour UTC windows). PK uses Asia/Karachi through
  the country profile (`config/reporting.php`).
- **Money precision.** Every SQL sum is `SUM(ROUND(x × 10^scale))` in whole units, added with bcmath, returned as
  fixed-scale strings; no PHP floats in figures (`Units`, `Sums`, `Money`). Decimal columns `decimal(12,2)` /
  `decimal(14,4)`. JS formats only for display. PK whole-rupee display and lakh grouping are done in
  `lib/country.ts` / `MoneyFormat`; CSV exports carry plain decimals (no symbol, no grouping), so PK spreadsheets
  read them.
- **Idempotent rebuilds.** Dirty-day tokens, delete-and-reinsert per shop-day in one transaction, the job unique per
  business and `WithoutOverlapping`; replays, out-of-order children, edits and deletes recompute from raw rows.
- **Tenant isolation of reports and caches.** `ReportScope::tenant()` fails closed; rpt models use
  `BelongsToCompany`; the business dashboard cache key includes company, days, shop, till and hour; admin caches are
  filtered per viewer after reading.
- **UK / PK on one Redis.** docs/deploy.md: separate Redis DBs (0/1 vs 2/3), prefixes (`retail_v2_` / `pak_pos_`),
  session cookie and host, so `onOneServer` mutexes, unique-job locks, the scheduler heartbeat and caches cannot
  collide. (Not verifiable from the repo: confirm the PK `.env` has its own `REDIS_DB`/`REDIS_CACHE_DB`; with the
  same DB and `CACHE_PREFIX` copied from the UK, `onOneServer` would let only one of the two instances run each
  scheduled command.)
- **Scheduler times.** UTC entries act on UTC instants; local ones (`alerts:digest` 07:00, `anomalies:detect --daily`
  06:30, `labels:queue-offers` 00:10) use `->timezone(Country::zone())`; none sits in the 01:00–02:00 hour that
  repeats/skips at a clock change. Overlap guards are on the long and frequent commands.
- **Prunes delete only what they should.** Every prunable is time-based on its own table, none touches sales, VAT or
  ledger rows; no company filter mistakes (global by design). Backups (`deploy/backup-db.sh`): single-transaction
  dump, completeness check, offsite before local retention, per-instance directory.
- **Migrations** run on MySQL 8 (the whole set ran on the audit database) and SQLite (the suite); no index name over
  64 characters, no index over 3072 bytes; sales have no cascading foreign keys.
- **Exports** walk the sales by keyset (`SaleSearch::chunk`), never OFFSET, with flat memory.
- **Logging of secrets.** Licence keys masked, sync keys never logged, AI client logs only exception classes.

## Not in this audit's scope, passed on

- `IdempotentTillRequest` keys replies by route + caller-chosen install id + key and the body fingerprint excludes
  `Authorization`: two branches with the same install id, key and body could get each other's reply (security
  audit).
- `SyncAuthLimiter` counts failed sync auth per IP (`sync-auth:ip:…`): one till with a revoked key behind a shop's
  shared IP can lock out the good tills on that IP for 15 minutes; `ThrottleLicenceApi` keys redeem attempts by an
  unverified `X-SSPOS-Branch-Id` header.
