# Sync and till API audit, 2026-10-11

Scope: everything a till talks to: `/api/v1/sync/{hello,push,pull}`, `/api/v1/licence/{activate,validate,redeem}`,
`/api/v1/devices/deactivate`, `/api/v1/cloud/migrate` and `migrate/complete`, plus `app/Domain/Sync`,
`app/Domain/TillData` (sync path), `app/Domain/Licensing/Api` and the till API middleware. Checked against the UK contract
`docs/contracts/portal-api-v1.4.1` and the Pakistan pack `docs/contracts/pak-pos-2026-10-07`. The two packs have
identical schemas and enums, so every finding below applies to both instances unless it says otherwise.

Branch `audit/2026-10-11-sync` (from `origin/main` 97412ae). No app code was changed. Each finding has a proof test that
**fails today** and passes once the finding is fixed. All proof tests are in the Pest group `audit-sync`:

- `tests/Feature/Audit/SyncAuditTest.php`: store and push level (SYNC-1, 2, 7, 8, 9, 10)
- `tests/Feature/Audit/SyncAuditLicenceTest.php`: sync key delivery and release (SYNC-3, 4)
- `tests/Feature/Audit/SyncAuditMigrationTest.php`: `cloud/migrate` and the history upload (SYNC-5, 6)

Run them with `php artisan test --group=audit-sync`, and leave them out of `composer check` with
`--exclude-group=audit-sync` until they are fixed. SYNC-9 fails on MySQL only. Run it with
`DB_CONNECTION=mysql DB_PORT=8889 DB_DATABASE=retail_v2_audit_sync DB_USERNAME=root DB_PASSWORD=root php artisan test --group=audit-sync`.
Every other proof test fails on both SQLite and MySQL.

## Findings

### SYNC-2 (high): a reused seq is acknowledged and its new row silently dropped

- **What.** The push dedupes on `(company, branch, stream, seq)` only. When a seq the ledger already holds arrives
  carrying a different row (another `entity`/`entityId`/`version`), it is answered as a `Duplicate`. The till is told
  the row is stored (`acknowledgedSeq` covers it) and marks it sent. The row never reaches the portal and nothing
  is logged.
- **When it happens.** The till's ChangeLog counter goes back while the branch keeps its sync key. That happens when
  the main till moves to a new PC and restores a backup older than its last push. The contract's own transfer flow
  says "restore the backup there first", but a dead PC's last backup is usually hours old. It also happens on a
  fresh install linked again with the branch key, and after `cloud/migrate` when `pushResumesAfterSeq` is lower than
  the seqs an earlier PC pushed. Every sale, refund and stock movement made after that point, up to the old highest
  seq, is lost from reports, VAT and stock with no error anywhere.
- **Where.** `app/Domain/TillData/Actions/ApplySyncChanges.php:92` (and the repeat inside the transaction,
  `app/Domain/TillData/Sync/ChunkApplier.php:77`). `ChangeLedger::applied()` (`ChangeLedger.php:24`) returns seqs
  only, though the ledger also stores `entity`, `entity_id` and `version`.
- **Proof.** `SyncAuditTest` "SYNC-2: a seq the ledger already holds but carrying a different row is not silently
  dropped (restored backup / new PC)".
- **Suggested fix.** Have `applied()` return `seq => [entity, entity_id, version]`. Treat a change as a duplicate only
  when its triple matches the stored one. A different triple under a known seq should be applied by its own triple
  (it is idempotent by `(entity, entityId, version)` anyway). Do not insert it into the ledger again (unique key), but
  log a warning and raise a "seq reused" admin alert for the branch so support can check the till. Ask EPOS whether
  a restored or new main till should start a new seq space (for example a new `X-SSPOS-Stream`/install marker) so
  the portal can tell the two apart.
- **Risk of the fix for live customers.** Low to medium. Retries of a normal batch carry the same triple and stay
  duplicates, so the §19.4 #1-2 tests guard the fix. The edge case: a resend after a lost reply may carry a newer
  state under the same seq (§7, "a resend may carry a newer state"). With the fix that newer row is applied by its
  triple, which is still correct ("keep the highest version"). The receivedAt bookkeeping must still treat the seq
  as already in the ledger.

### SYNC-1 (medium): one shop's till can overwrite and re-branch another shop's rows

- **What.** For a branch-owned row that already exists, the writer checks the stored row's company but never its
  branch. A push from Bradford carrying the id of a Leeds row, with `branchId` = Bradford and a higher version, is
  applied. The row moves to Bradford and Bradford's till. On a completed sale only the money columns are frozen:
  `branch_id` and `register_id` are in `ALWAYS_MUTABLE`, so a historic sale changes shop and till, and reporting
  moves it. Rows with `sender` scope are re-branded to whichever branch pushes them. After the move, Leeds's own later
  pushes for that sale's lines are refused (`sync.wrong_branch`, `ParentResolver`), and that blocks Leeds's queue.
- **Where.** `app/Domain/TillData/Sync/EntityWriter.php:54` (company check only),
  `app/Domain/TillData/Sync/EntityWriter.php:31` (`ALWAYS_MUTABLE` includes `branch_id`, `register_id`), and
  `app/Domain/TillData/Sync/PayloadMapper.php:196` / `:201` (the scope checks look only at the incoming row).
  Child rows are checked against their parent's branch (`ParentResolver`). Parent rows themselves are not.
- **Who.** Businesses with more than one shop. A legitimate trigger is a PC moved between shops (re-keyed to another
  branch) or a till bug. A hostile or compromised till of the same business could also trigger it.
- **Proof.** `SyncAuditTest` "SYNC-1: another shop of the business cannot take over (re-branch) a completed sale of
  Leeds".
- **Suggested fix.** In `EntityWriter::write()`, for branch-owned, non-relayed and non-drafted rows whose stored
  `branch_id` is set and differs from the sending branch, reject with `sync.wrong_branch` (as `ParentResolver` does
  for children). Remove `branch_id` and `register_id` from `ALWAYS_MUTABLE`, or allow them to change only while still
  null (the child backfill case).
- **Risk.** Medium. A shop whose till legitimately re-homes rows would start getting 422s, which block its queue. Check
  production first (`sales`, `shifts`, `stock_movements`: rows whose `branch_id` differs from the branch of their
  first push ledger entry) and roll out with a log-only phase.

### SYNC-3 (medium): a rotated key lost in transit is never re-sent

- **What.** An admin rotation (`RequestSyncKeyRotation`) issues the new key in the next `licence/validate` reply and
  marks it delivered to that install. If that reply is lost (timeout, network), the till keeps syncing with the old
  key. Every later validate answers `apiKey: null`: the current key "was sent here" and the till reports a
  `lastSyncAt`. Seven days later the old key stops (401 `auth.key_revoked`) and the shop's dashboard freezes until
  staff rotate again. Activation already handles this case (re-issue when the key was never used). Validate does not.
- **Where.** `app/Domain/Sync/Support/SyncKeyDelivery.php:109`.
- **Proof.** `SyncAuditLicenceTest` "SYNC-3: a rotated sync key whose validate reply was lost is sent again before the
  old key dies".
- **Suggested fix.** In `needsKey()` for validate, also return true when the current key was delivered to this
  install, has `last_used_at === null`, and a replaced key of the branch is still being used (its `last_used_at` is
  after the current key's `created_at`). Simpler but noisier: re-issue while the current key is unused and older
  than one validate interval.
- **Risk.** Low. It only adds a delivery. Each extra delivery rotates the key (the old one keeps its 7-day grace), so
  test that a till which did receive the key and uses it is not rotated again.

### SYNC-4 (medium): a Connect-linked main till is released without its key, and the key survives

- **What.** `delivered_install_id` is written only when a key goes out in a licence reply (`IssueSyncKey` with
  `$installId`). A main till that linked by typing the sync key (SIMPLE-SETUP route A `cloud/migrate`, or route B
  `hello`) never gets one. The contract describes route A as the standard Connect path. For such a till:
  - `devices/deactivate` does not ask for the Bearer key (the H2 hardening is skipped);
  - `RevokeTillSyncKeys` finds nothing delivered to the install, so `apiKeyRevoked` is false and the branch key keeps
    working. The contract's aim that "a restored old PC cannot push" fails.
- **Where.** `app/Domain/Licensing/Api/DeactivateDevice.php:166`, `app/Domain/Sync/Actions/RevokeTillSyncKeys.php:33`,
  `app/Domain/Sync/Actions/MigrateToCloud.php:79` (the sync-key route returns the code as `apiKey` without recording
  the install).
- **Proof.** `SyncAuditLicenceTest` "SYNC-4: a main till linked with a typed sync key (Connect) must prove the key to
  be released, and its key is revoked".
- **Suggested fix.** Record the holder when the key is first used. On `cloud/migrate` with a sync key, set
  `delivered_install_id` to the migrating install. On `sync/*`, map `X-SSPOS-Register-Id` to the register's bound
  licence (`device_id`) and record it. Alternatively, let `ensureBranchKey`/`RevokeTillSyncKeys` treat the main
  till's licence as the key holder whenever the branch has a usable key.
- **Risk.** Medium. Main tills that today deactivate with no Bearer would get 401 `auth.invalid_key`. §17.7 says a
  till sends the key when it holds one. Check that in production logs (deactivate requests with and without a Bearer)
  before rollout.

### SYNC-7 (medium): company details from a second shop's till are dropped as stale

- **What.** Each branch's main till pushes its own `Company` row (aliased to one portal company). The two tills keep
  separate `rowVersion` counters. `TenancyRowApplier` keeps one `till_row_version` per company and drops any version
  `<=` it as `Stale`. With Leeds's till at version 50, every company edit made on Bradford's till (VAT number, legal
  name, company number, address) is acknowledged and ignored, with no conflict, until Bradford's counter passes 50.
  A related gap: a till edit made before a portal edit, but pushed after it, overwrites the portal's newer values,
  because no `updated_at`/`hub_edited_at` is compared.
- **Where.** `app/Domain/TillData/Sync/TenancyRowApplier.php:43`.
- **Proof.** `SyncAuditTest` "SYNC-7: a company detail changed at the second shop's till is not silently dropped
  because the first shop's till counts higher".
- **Suggested fix.** For `Company` (and for `Branch` when the main till moves PC), order by the till's `updatedAt`, as
  keyed rows are ordered, or keep `till_row_version` per sending branch. Compare with the portal's own last edit and
  record a conflict instead of overwriting a newer portal edit.
- **Risk.** Low to medium. Company name and VAT number feed invoices and the licence token's `company` block. Expect
  some multi-branch businesses to see their stored details change to the latest till's values on the first push
  after the fix.

### SYNC-5 (low): migrate with a just-replaced key returns that key

- **What.** `cloud/migrate` accepts a sync key that is still in its 7-day grace and echoes it as `apiKey`. The till
  stores a key that dies within 7 days. As in SYNC-3, no later validate re-sends one to a till that syncs.
- **Where.** `app/Domain/Sync/Actions/MigrateToCloud.php:79` (`$apiKey = $in->activationCode`), with
  `MigrationCredential::syncKey()` accepting `isUsable()` keys.
- **Proof.** `SyncAuditMigrationTest` "SYNC-5: Connect with a sync key that was just replaced answers with a key that
  keeps working".
- **Suggested fix.** When the code is not the branch's current key, answer with a fresh key
  (`IssueSyncKey(..., installId)`), as the licence-key route already does.
- **Risk.** Low. Route A is idempotent per `(code, installId)`, so a retried migrate would get a new key each time.
  Return the same issued key on retries (store it on the upload, encrypted) or accept that the last one wins.

### SYNC-6 (low): a skipped history row keeps the upload open for ever

- **What.** In an initial upload, rows the portal acknowledges but never stores (`NeverStored`: deny-listed settings,
  `local` tables, blank-company bookkeeping rows) are not written to the ledger. `migrate/complete` requires seqs
  1…`highestSeq` with no gap, so it answers `incomplete` with `resumeFromSeq` before the skipped seq. The till resends,
  the row is skipped again, and the upload never closes. While it is open the till runs no normal push or pull
  (§17.8, §9). Today's tills should not send such rows, but a deny-list drift between a till version and the portal
  is enough to trigger it (the deny-list already changed on 2026-10-02).
- **Where.** `app/Domain/TillData/Actions/ApplySyncChanges.php:95` (Skipped, not recorded),
  `app/Domain/Sync/Support/CloudUploads.php:61`, `app/Domain/Sync/Actions/CompleteCloudMigration.php:60`.
- **Proof.** `SyncAuditMigrationTest` "SYNC-6: a history row the portal acknowledges but never stores does not keep
  the upload open for ever".
- **Suggested fix.** Record skipped changes in the ledger with outcome `skipped` (they never reach any table, and
  `countsByEntity` can leave that outcome out), or compute contiguity over every acknowledged seq.
- **Risk.** Low. Delta pushes would also start recording skipped seqs, which only makes a retry of them a duplicate.

### SYNC-8 (low): a till delete with no payload bypasses portal-wins

- **What.** For a portal-owned (hub) row, a `D` with `payload: null` takes the tombstone branch before
  `portalWins()`. A late till delete therefore soft-deletes a row the portal edited afterwards (the same delete with
  its payload becomes a conflict). The tombstone also leaves `hub_version` and `origin_branch_id` alone, so the
  delete is never stamped and no other shop is told. The contract says a `D` carries its payload, so only a till bug
  or an older till would send this.
- **Where.** `app/Domain/TillData/Sync/EntityWriter.php:75`-`77`.
- **Proof.** `SyncAuditTest` "SYNC-8: a till delete without a payload of a portal-owned row obeys the portal-wins rule
  and reaches the other shops".
- **Suggested fix.** For hub-owned rows, run the `portalWins()` checks before the tombstone. On apply, set
  `hub_version = null`, `origin_branch_id = sender` and recompute `hub_hash`, as a normal applied change does.
- **Risk.** Low.

### SYNC-9 (low, MySQL only): a long unknown entity name crashes the push

- **What.** Unknown entities are stored raw by `UnknownEntityRows::store()`, outside `ChunkApplier`'s QueryException
  fallback. `till_unknown_rows.entity` and `sync_applied_changes.entity` are `varchar(64)`, and the envelope reader
  accepts any length. On MySQL strict mode a longer name throws, and the whole batch answers 500 on every retry. That
  stalls the shop's queue. SQLite does not enforce the length, so the dev suite cannot see it.
- **Where.** `app/Domain/TillData/Sync/UnknownEntityRows.php:36`, `app/Domain/TillData/Actions/ApplySyncChanges.php:122`.
- **Proof.** `SyncAuditTest` "SYNC-9: an unknown entity whose name is longer than the ledger column never crashes the
  whole push (MySQL)". It passes on SQLite and fails (500) on MySQL `retail_v2_audit_sync`.
- **Suggested fix.** Reject entity names over 64 characters in `EnvelopeReader` (`change.invalid`), or catch
  `QueryException` per row in `UnknownEntityRows` as `ChunkApplier` does.
- **Risk.** None for real tills (entity names are short).

### SYNC-10 (low): RolePermission ids clash across businesses

- **What.** Keyed rows are stored under an id derived from the payload. For `Setting` the payload includes our
  company or branch id, so the id is unique per business. For `RolePermission` it is only
  `RolePermission|roleId|permissionKey`. If two businesses' tills share a role id (for example a system role seeded
  with a fixed id), the second business's grant hits `entity.id_taken`. That is a permanent 422 which stops its push
  queue at that row. Role ids are ULIDs, so this needs fixed seeded ids; ask EPOS whether system roles are seeded
  with fixed ids.
- **Where.** `app/Domain/TillData/Sync/KeyedRows.php:51` (no company in the derived id).
- **Proof.** `SyncAuditTest` "SYNC-10: a role permission of one business never blocks the same permission of another
  business".
- **Suggested fix.** Derive the stored id from `company|roleId|permissionKey`. The pull already sends the id the till
  expects (`SyncRowIds::rolePermission`, worked out from the payload), so only storage changes.
- **Risk.** Medium if done: existing `till_role_permissions` ids must be migrated, in one transaction per company.
  Do it only if EPOS confirms fixed role ids.

## Observations (not proven by a test, worth a look)

- **Seat limit race.** `LicenceBinder::bind()` counts the bound tills of the branch while holding a lock on the
  licence row only. Two different keys of one branch activated at the same moment can both pass `maxRegisters`. Low;
  it needs simultaneous activations.
- **Main-till flag vs the real main till.** Sync keys go to whichever register the portal marks as main. When the
  portal promotes another till (deactivating the main promotes the lowest code; reactivating does not swap back), that
  till's first validate (`lastSyncAt` null) rotates the branch key. The PC that really syncs then loses its key 7
  days later. This is by design, but staff should be warned on the "set main till" and "deactivate" screens.
- **Failed-auth lockout is per IP before the key lookup** (`SyncAuthLimiter`: 30 failures in 15 minutes). Shops
  behind one carrier-grade NAT share the bucket. A misconfigured till elsewhere can make a healthy till get 429 for
  15 minutes. Low.
- **`ProductRecall` derived columns** (`status`, `returned_qty`, `closed_at`, `note`, `closed_by_user_id`) are stored
  from a push as the last shop's values on the business-wide row. The pull never sends them, so tills are unaffected,
  but portal screens must use `ProductRecallBranchState`. Some list code still reads `product_recalls.status`.
- **Impossible dates roll over.** An offset date-time such as `2026-02-30T09:41:00+01:00` is accepted and parsed as
  2 March (`Values::dateTime()` → `ApiDate::parse`). Only the `Z` form is checked with `checkdate`.
- `sync_branch_status.last_acknowledged_seq` is overwritten by every push, including one answered with a lower
  acknowledgement or a 422. It is display only, but it can go backwards on the admin's cloud-link screen.

## Checked and found fine

- **Auth.** Missing, malformed, unknown, revoked, replaced-past-grace keys; cancelled or deleted business; deleted or
  inactive branch; wrong branch or company header (translated through the business's own `id_map` only); a register
  header from another branch. Failed checks are throttled per IP and key, and the per-key request limit (240/min)
  applies only after auth. Redeem and `migrate/complete` reuse the same check.
- **Tenancy.** Payload `companyId` must be the caller's. Ids held by another business are refused (`entity.id_taken`,
  plus the post-upsert check). Children of another business's or branch's parent are refused. Pull reads only the
  caller's company, with visibility per branch (hub rows, branch settings, relays to `toBranchId`/`fromBranchId`,
  ledger to other branches, drafts to their shop, departures). `IdTranslator` uses one business's map only, and
  `RecordTillIds` refuses ids mapped to another business.
- **Error envelopes.** Push fuzzing over 40 malformed envelopes (wrong types, nulls, huge numbers, bad dates, a list
  instead of an object, deep JSON, unknown and local entities, keyed rows with odd payloads) gave 200, 400, 413 or
  422 with the contract body on SQLite and MySQL. The only exception is SYNC-9. Licence, redeem, deactivate and
  migrate fuzzing (32 bodies) gave 400 `request.invalid` or a contract code, never a 500. Malformed or damaged gzip
  gives 400, a gzip bomb gives 413 (streamed inflate), and more than 5,000 rows gives 413.
- **Idempotency.** Retried batches give the same reply and the first `receivedAt`. An `Idempotency-Key` replay,
  mismatch (422) and in-progress (409) work on push and the licence routes; 408, 409 in_progress, 429 and 5xx are
  not stored. Replays are encrypted. Two pushes of one branch never interleave (Redis lock in production).
- **Ordering.** Seq order inside a batch, duplicate seqs inside a batch rejected, ack stops at the first rejection,
  a stale version is accepted and keeps the newer one. Hub-owned rows use the portal-wins rules with and without
  `baseVersion`, and echoes are detected by content hash.
- **Pull.** The version counter is locked per company, so a lower version never becomes visible after a higher one.
  Parents come first in the order, lines go with their transfer or receipt, `since`/`max` are validated, `hasMore`
  and `highestVersion` are correct, and gzip is used only when accepted. Secrets are never sent (dropped members,
  `pinHash` only when changed, deny-listed settings), and derived columns are left out except the ledger sums.
- **Keyed settings.** Deny-list equal to the contract file, register scope refused, scope id checked against the
  caller, ordered by the later `updatedAt`.
- **Licence tokens.** `signerCert` in every token, `country` = PK only on the PK profile (absent on GB by the
  contract's pak-pos-only note), features in the till's names with `multi_branch` following the company,
  `expiresAt` without our grace days, validFrom ≤ expiresAt. A lost validate reply keeps the previous token valid
  (H2).
- **Sync key delivery.** Main till only, active branch and till, licence trading with `cloud_sync`. Revoked by an
  admin means nothing until an admin issues a new key. Activation re-sends a key that was never used.
- **Suspended and expired businesses.** Pushes are still accepted (DECISIONS "Suspension": data is never lost), and
  the till locks through validate. Cancelled or deleted businesses get 401 `auth.key_revoked`.
- **GB vs PK.** Same schemas and enums in both packs. Trading day, day counters and dates follow the country time zone
  (`Country::zone()`). App-version gates go through `TillProfile` (PK 1.0.x is never compared with UK 0.1.x), and the
  426 block list is per instance. Nation, STRN/NTN and money ranges are per profile.
- **Size and speed.** The existing performance tests cover 5,000-row pushes and pulls. The pull union uses
  `(company_id, hub_version)` indexes with top-N sort, so first pulls of large businesses scale linearly. Request
  bodies are allowed up to 64 MB (nginx and PHP) against the contract's 50 MB.
