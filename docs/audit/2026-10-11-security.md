# Security audit (2026-10-11, read-only)

Branch `audit/2026-10-11-security` from `origin/main` 97412ae. No app code was changed. The proof tests are:

- `tests/Feature/Audit/SecurityAuditTest.php` (group `audit-gap`). Each test states the secure behaviour, so it
  **fails on main while the finding is open** and passes once the finding is fixed. Run it with
  `php artisan test --group=audit-gap`. Until the fixes land, exclude it with `--exclude-group=audit-gap`.
- `tests/Feature/Audit/SecurityAuditRouteCoverageTest.php` walks every registered route. It **passes on main** and
  will fail when someone adds an unprotected route.

**Scope:** web and admin authentication, sessions, password reset, two-factor, remember me, login throttling and
impersonation. Authorisation on all 440 routes. Tenant isolation: scopes, raw queries, binding, exports, uploads, AI,
search and notifications. Secrets. Input handling. Webhooks. Public endpoints. Headers and CSP. Inertia shared props.
Held emails. The new admin features (change plan, email control, held emails, per-till fees, features reset). The
previous review (`docs/security-review.md`, 2026-10-01) was re-checked: none of its fixes have regressed.

**Summary: Critical 0 · High 1 · Medium 4 · Low 3 · Info 5.**

## Findings

### SEC-1 · High · Admin sign-in is password-only in production

- **What.**
  - Two-factor is switched off for every guard: `TWO_FACTOR_ENABLED=false` in `.env.production.example:171`
    (owner decision, 2026-10-01).
  - `RequireTwoFactor::handle` returns at once when it is off (`app/Http/Middleware/RequireTwoFactor.php:34`), so the
    admin area needs only a password.
  - Admin login throttling is per email+IP (`app/Http/Requests/Admin/Auth/LoginRequest.php:89`). An attacker using many
    IPs is not slowed down (see SEC-7).
  - Earlier finding H1 was fixed in code but is open in practice.
- **Exploit.** One phished or reused admin password (Owner or Support) gives full control:
  - impersonate any business ("log in as customer");
  - issue, reissue and email licence keys;
  - generate branch sync keys (full read/write of a shop's till data);
  - change billing and plans.

  This affects both the UK and Pakistan instances.
- **Proof.** `SEC-1` test: with the production setting, an admin with no second factor gets 200 on `/admin`. Expected:
  a redirect to two-factor set-up.
- **Fix.** Split the switch so the admin guard is always on. For example, `security.two_factor.admin_enabled`
  defaults to true, and `TWO_FACTOR_ENABLED` then only means "portal". The code, set-up screens and recovery flow
  already exist and are tested.
- **Risk to live customers.** None: customers are untouched. Each SSPOS admin enrols an authenticator once, at
  their next login. An owner can reset an admin who loses their phone.

### SEC-2 · Medium · Held welcome-email preview shows full licence keys to the Accounts role

- **Where.**
  - `app/Http/Controllers/Admin/HeldEmailController.php:39` (`preview`).
  - `app/Domain/Mail/Support/HeldEmailMessage.php:54`: a welcome email is previewed exactly as held.
  - Route `GET /admin/emails/held/{held}/preview`, behind `billing.manage` (Owner, Accounts).
- **What.**
  - With the Welcome category switched off (P11), `held_emails.payload` keeps the serialised `WelcomeTenantMail`,
    with every till's plain licence key, encrypted with APP_KEY (`EmailControl.php:123`). It stays there until the
    email is sent or discarded.
  - The held-email list deliberately shows only the last 4 characters (`HeldEmailData`). The preview, however, renders
    the full email, keys included, to an Accounts admin. Accounts does not have `licences.manage` and cannot otherwise
    see or create keys.
  - This conflicts with the CLAUDE.md rule "Secrets: store a hash + last 4 characters only". Keeping the payload was a
    conscious decision; showing it to Accounts was not.
- **Exploit.** An Accounts user, or anyone who has taken over that account (see SEC-1), opens the preview. They then
  activate a till on a new customer's unused key, or pass the key on.
- **Proof.** `SEC-2` test: an Accounts admin's preview contains the full `SSP-…` key.
- **Fix.** Mask the keys in the preview (render with `TillKeyData` replaced by a `…1234` value), as the list does.
  Optionally, allow the full preview to `licences.manage` only.
- **Risk to live customers.** None. Admin screen only; the email that is actually sent is unchanged.

### SEC-3 · Medium · Markdown link and image injection in emails a tenant sends to other people

- **Where.**
  - Laravel's `Markdown::withSecuredEncoding()` is not turned on (`app/Providers`, `bootstrap`).
  - `{{ }}` escapes HTML but not Markdown, so `[text](https://…)` and `![](https://…)` inside a tenant-typed value
    become a real link or tracking image.
  - The L3 fix (`MailFormat::plain`) covers only the admin new-lead email and parts of the digest.
- **Emails reaching people outside the business:**
  - `resources/views/mail/portal-invitation.blade.php:2,4,12`: business name, inviter name, invitee first name, shop
    name. Sent by `POST /app/users/invitations` to any address.
  - `resources/views/mail/customer-statement.blade.php:2,4,14`: business name and phone. Sent by
    `POST /app/customers/{customer}/statement/email`.
- **Emails to SSPOS staff (lower severity):** `admin-till-request.blade.php:4,10` and
  `admin-subscription-request.blade.php:4,10` carry the tenant user's message, name and business.
- **Emails to the owner (lower severity):** `owner-alert*`, `anomaly-alert` and `owner-digest` carry shop and till
  names that a manager or a till can set.
- **Exploit.** A trial tenant sets its business name to `[Verify your account](https://evil.test/login)`, then
  invites strangers. They get a Switch & Save-branded email from our sending domain with a working phishing link and a
  tracking pixel. This damages the domain's reputation and deliverability for every customer.
- **Proof.** Two `SEC-3` tests: the rendered invitation and statement HTML contain `href="https://evil.test`.
- **Fix.** Call `Markdown::withSecuredEncoding()` once in `AppServiceProvider::boot` (Laravel 11.40+). It escapes
  Markdown in every `{{ }}` of every mail template.
- **Risk to live customers.** Low. A business name containing `*`, `_`, `[` or `#` will show the literal character
  instead of bold or italic. Re-run `tests/Feature/Mail` and check a few rendered templates, because some templates
  might rely on a value rendering as Markdown; `owner-digest` already builds its `**` markers outside `{{ }}`.

### SEC-4 · Medium · Support can change a business's plan, bypassing the billing "Change plan" flow

- **Where.**
  - `routes/admin.php:196`: `PUT /admin/tenants/{company}/plan` with `apply_to_licences`.
  - `routes/admin.php:220`: `POST /admin/licences/{licence}/plan`.
  - Both are behind `licences.manage` (Owner, Support) and call `ChangeCompanyPlan` / `ChangeLicencePlan`.
- **What.**
  - The owner's 2026-10-07 decision made "Change plan" a `billing.manage` action (Owner, Accounts) with a preview,
    setup fee, Direct Debit amount sync, plan-changed email and `billing.plan_changed` audit.
  - The older routes still move `companies.plan_id` and every live licence to another plan with none of that. Licence
    and company audits are written, but not `billing.plan_changed`.
- **Exploit.** A Support user moves a business (their own, or a friend's) from Pro to a cheaper or setup-only plan,
  with `apply_to_licences=1`. The next invoices are built from the licences' plan, so the business pays less. The
  Direct Debit subscription amount is not re-synced, so collection and invoices disagree. Nobody in Accounts is told.
- **Proof.** `SEC-4` test: a Support admin's PUT returns a 302 with success. Expected: 403.
- **Fix.** Put both routes behind `billing.manage` as well, or remove the company-level route and keep only a
  per-licence plan move for the same plan's features. Alternatively, have them call `ChangeBusinessPlan`.
- **Risk to live customers.** None for customers. Support staff lose a button; existing tests
  (`LicenceAdminScreensTest` "renew all and the company plan…") must be updated.

### SEC-5 · Medium · Email change needs no password, and the new email is never verified

- **Where.**
  - `PATCH /settings/profile` (`routes/settings.php:13`) runs `UpdateOwnProfile`. Only name and email are asked for;
    there is no `current_password` (unlike password change and account delete).
  - `UpdateOwnProfile` says "A new email must be verified again" and clears `email_verified_at`. But `User` does not
    implement `MustVerifyEmail` (`app/Models/User.php:28`), so the `verified` middleware on every `/app` route does
    nothing.
  - No notice goes to the old address.
- **Exploit.** Someone with brief access to a signed-in session takes over the account permanently. Shop PCs and
  manager laptops are often left signed in, and remember-me lasts long (see SEC-6).
  1. Change the email to the attacker's address.
  2. Use "Forgot password" for that address.
  3. Set a new password.

  The real owner cannot reset it: reset links go to the attacker. If this is the owner account, the attacker holds
  the business: users, billing, Direct Debit, staff PINs.
- **Proof.** Two `SEC-5` tests:
  - the email changes with no password;
  - after the change `/app` still answers 200. Expected: the verify-email notice.
- **Fix.**
  1. Require `current_password` when the email changes.
  2. Send a "your email was changed" notice to the old address.
  3. Either implement `MustVerifyEmail` on `User` or keep the old email until the new one is confirmed by a signed
     link. The second option is preferred: it does not lock anyone out.
- **Risk to live customers.** If `MustVerifyEmail` is turned on, every user with `email_verified_at = null` is sent to
  verify at their next request. Check how many such users exist on UK and PK before choosing (owner-created accounts
  are set as verified when the set-password link is used). The "confirm new email" option has no impact on existing
  users.

### SEC-6 · Low · A password change does not sign out other sessions or remember-me cookies

- **Where.**
  - `ChangeOwnPassword` (`app/Domain/PortalUsers/Actions/ChangeOwnPassword.php:19`) only updates the hash.
  - An owner setting a new password for an admin (`UpdateAdmin.php:42`) does the same.
  - `AuthenticateSession` is not used, and `remember_token` is not rotated. A forgot-password reset does rotate the
    token (`NewPasswordController`), but other live sessions still stay valid.
- **Exploit.** A user who suspects a stolen session or remember-me cookie changes their password, and the attacker
  stays signed in.
- **Proof.** `SEC-6` test: `remember_token` is unchanged after the password change.
- **Fix.** Rotate `remember_token` in both actions. Delete the user's other rows in `sessions`, or add
  `AuthenticateSession` to the web group and call `Auth::logoutOtherDevices()`.
- **Risk to live customers.** Adding `AuthenticateSession` signs out existing sessions once at deploy (no stored
  password hash in them). Rotating the token on change only affects the user who changed it.

### SEC-7 · Low · Login throttling is per email+IP only

- **Where.**
  - `app/Http/Requests/Auth/LoginRequest.php:84` (portal) and `Admin/Auth/LoginRequest.php:89` (admin): 5 failures per
    email+IP per minute.
  - `POST /login` and `POST /admin/login` have no route throttle.
- **Exploit.**
  - From one IP: password spraying, one common password across thousands of customer emails, is never slowed.
  - From many IPs: one account can be brute-forced. With SEC-1, that includes admin accounts.
- **Proof.** `SEC-7` test: after 30 failures for 30 different emails from one IP, the 31st is still processed.
- **Fix.**
  - Add a per-IP limiter on both login routes, for example `throttle:30,1`, plus a per-account ceiling (for example 20
    an hour, across all IPs) that adds a delay or a captcha.
  - Log `Lockout` events.
  - Behind Cloudflare, set `TRUSTED_PROXIES=cloudflare` first (M3), or every visitor shares one bucket.
- **Risk to live customers.** Low. A per-IP limit that is too tight could block a busy office or shop network that
  shares one IP: keep it generous.

### SEC-8 · Low · Two purchasing lists look up till-supplied ids without the company

- **Where.**
  - `app/Domain/Purchasing/Queries/Lists/InvoiceRows.php:50`: `DB::table('goods_receipts')` by
    `supplier_invoices.goods_receipt_id`.
  - `CreditNoteRows.php:53`: `DB::table('supplier_invoices')` by `supplier_credit_notes.linked_invoice_id`.
  - Neither has a `company_id` filter. These are the same kind as the L4 fix in `DeliveryRows.php:52`. The ids are plain
    till fields, not parents, so `ParentResolver` does not check them.
- **Exploit.** A tenant whose till pushes another business's goods-receipt or invoice ULID sees that business's
  delivery-note or invoice number in `/app/purchasing/invoices` or `/app/purchasing/credit-notes`. This needs the other
  business's 80-bit-random ULID, and leaks one field, read-only.
- **Proof.** `SEC-8` test: `DN-SECRET` of another business shows in the invoice list.
- **Fix.** `->where('company_id', $rows[0]->company_id ?? null)`, as `DeliveryRows` does.
- **Risk to live customers.** None.

### Info

- **I-1.** `NewsTitleForm.php:57` and `TitleRows.php:71` join `vat_rates` on a till-supplied `vat_rate_id` without
  `v.company_id`. The same crafted-ULID trick as SEC-8 would show another business's VAT rate name and percentage.
  Negligible impact; add `->on('v.company_id', '=', 'p.company_id')` when next in the file.
- **I-2.** On rate-limited routes, `throttle` runs before `company.can`, so an unauthorised user sees 429 before 403
  once over the limit. The per-user throttle counter is also shared between routes (already accepted in AI11). Harmless.
- **I-3.** `app/alerts/unsubscribe/...` links are signed without expiry. They change only that user's own alert
  preferences, so this is accepted.
- **I-4.** Direct Debit set-up links (`/direct-debit/{company}/setup`, signed for 14 days) work for whoever holds the
  email. By design: no login, and the mandate is the payer's own.
- **I-5.** An impersonating admin can do every business action of the user they view: invite users, change roles, set
  up Direct Debit. Account screens are blocked (`Impersonation::BLOCKED_ROUTES`). Every action is audited with the
  admin as actor, and the same admin can already add users from `/admin`, so this is not an escalation. With SEC-1
  open, the impact of a stolen admin password is the whole customer base.

**Tenant isolation.**

- All 176 tenant models use `BelongsToCompany`.
- The models without it are admin or system tables: Lead, EmailLog, HeldEmail, AuditLog, AiUsage, AiPendingAction
  (owner-checked), LocalLicenceKey, CompanyMembership and GoCardlessEvent.
- Tenant controllers take string ids and look them up through the scope. There is no `DB::`, `*Raw` or
  `withoutCompanyScope` in `app/Http/{Controllers/App,Requests/App,Middleware}`.
- Every `DB::table` reachable from a tenant request filters by the `CurrentCompany` id, joins carry `company_id`, and
  one-shop users are pinned through the Filters classes. The only exceptions are SEC-8 and I-1.
- `Builder::toBase()` keeps the scope.
- `withoutCompanyScope` outside admin code is used only in jobs and commands for a known company, or keyed by a
  company the caller already resolved (labels, alerts, invitations, ShopHours).
- One-shop managers: every company-wide write extends `CompanyWideWriteRequest`, and the shop-level writes (prices,
  promotions, labels, opening hours, invoice import, news, shop settings) check the shop.

**Exports, uploads and PDFs.**

- Every CSV escapes formulas (`CsvText::safe` or an equivalent).
- Sales exports are per user, on a private disk, `no-store`.
- Uploads: product CSV (20 MB, `mimes`, private, never served) and invoice import (content-checked, private, served
  scoped with `nosniff`). Nothing uses the public disk. There is no XML or zip parsing.
- dompdf runs with remote and PHP off.

**XSS.** `dangerouslySetInnerHTML` appears only for the legal Markdown (escaped, unsafe links off) and the TOTP QR SVG.
`{!! !!}` appears only in vendor mail layouts and `nl2br(e())`.

**SQL injection.** `TableQuery` whitelists sort columns and direction. No request value reaches a raw fragment.

**Mass assignment.** No `$guarded = []` and no `$request->all()`. `company_id` is never filled from input.

**SSRF and open redirects.** Outbound HTTP goes only to configured hosts. There are no `next` or `returnTo`
parameters.

**Secrets.**

- Licence keys are HMAC + last 4; sync keys are hashed. Keys are never in a URL and `dontFlash` covers them.
- 2FA secrets are encrypted and hidden from `auth.user`. Recovery codes are hashed.
- The only plain keys at rest are the held welcome email (SEC-2) and fob codes (accepted risk L9).

**Inertia shared props.** `auth.user` hides the password, remember token and 2FA fields. Company, branches and
abilities come from the current membership; branches are pinned for one-shop users.

**Sessions and headers.**

- The nonce CSP, `frame-ancestors 'self'`, HSTS, `nosniff`, Referrer-Policy and Permissions-Policy fixes are in place.
- The secure cookie is on in production; `SESSION_ENCRYPT=true` is in the production example.
- Held-email preview: sandboxed CSP, `form-action 'none'`, `no-store`.

**Impersonation.**

- Requires `tenants.manage`, an active membership and a business that is not cancelled.
- Pinned to the business it was started for, and expires after 60 minutes.
- Ends if the admin signs out or loses the ability.
- Admin area blocked while it runs. Start and stop are audited.

**AI.**

- Tools run in `CurrentCompany::runAs` and take no company id.
- Conversations are bound to user and company.
- Confirm and cancel are owner-locked and HMAC-signed (AI1–AI12 unchanged).

**New admin features.**

- Email settings, held emails, send-held, welcome and password-link: `billing.manage`.
- Change plan: preview and apply, `billing.manage`, cancelled businesses refused.
- Per-till setup fee and the setup-fee charge: `billing.manage`.
- "Use the plan's features" reset: `licences.manage`, branch found within the company.

Each was hit by the role test above. The gaps are only SEC-2 and SEC-4.
